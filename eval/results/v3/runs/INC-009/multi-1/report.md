# Incident investigation report: INC-009
*System: multi_agent | outcome: **root_cause_identified** | ended: critic_accepted*

## Summary
Root cause identified with medium confidence (0.72): portfolio-service deploy dep-5905 (v4.5.0, 2026-05-05T08:56:00Z) shipped a new unindexed query on the shared ledger-db, 'SELECT * FROM trades WHERE account_id=$1 AND executed_at > $2 ORDER BY executed_at', which executes as a Seq Scan over ~48.2M rows at 4-9s of CPU per call. This single statement accounts for essentially all of the ledger-db slow-query volume (1 -> ~139/min in the same minute), driving ledger-db CPU from ~30% to ~96% and connections from ~60 to ~185-200; order-service's INSERT INTO orders then queues behind the saturated CPU and is cancelled by the server-side statement timeout, producing the reported p99 > 5s. The 1-minute-resolution timeline confirms causation: ledger-db CPU/slow_queries/connections step simultaneously in the 08:58:00Z minute while order-service p99 stays ~148ms until 08:59:00Z, one minute later. The competing origins (autovacuum config change cfg-2903, untracked storage/IOPS event, order-service-local saturation) are each contradicted by timing, mechanism, or signature evidence.

## Probable root cause
**portfolio-service deploy dep-5905: new unindexed query on trades (account_id + executed_at) drives ledger-db CPU/scan saturation** -- bad_deployment in `portfolio-service`, triggered by `dep-5905` (confidence 0.72, medium)

### H1: portfolio-service deploy dep-5905: new unindexed query on trades (account_id + executed_at) drives ledger-db CPU/scan saturation
portfolio-service v4.5.0 (dep-5905, 2026-05-05T08:56:00Z) added a new query 'SELECT * FROM trades WHERE account_id=$1 AND executed_at > $2 ORDER BY executed_at' on the shared ledger-db with no accompanying migration/index. Immediately after the deploy the query executes as a Seq Scan on trades over ~48M rows (F33), each execution consuming 4-9s of CPU (F34). Because ledger-db is shared (F11, F31) this drives ledger-db CPU from ~30% to ~96%, slow_queries_per_min from ~1 to ~140 and connections_active from ~60 to ~185-200, all stepping together in the 08:58Z minute (F21, F22, F23). order-service writes (INSERT INTO orders) then wait behind the CPU-bound DB work and are cancelled by the server-side statement timeout (F5, F19), which surfaces as order-service p99 stepping to seconds one minute later at 08:59Z (F24, F25, F26).
