# Incident investigation report: INC-009
*System: multi_agent | outcome: **root_cause_identified** | ended: critic_accepted*

## Summary
Root cause (confidence 0.78, high): portfolio-service v4.5.0 (dep-5905, deployed 08:56:00Z) introduced a new unindexed query on the shared ledger-db 'trades' table (`SELECT * FROM trades WHERE account_id=$1 AND executed_at > $2 ORDER BY executed_at`), which runs as a Seq Scan over 48.2M rows and saturated the shared ledger-db (CPU 95-96%, connections ~3x, ~140 slow queries/min), causing order-service's INSERT INTO orders to hit statement timeouts. All three ledger-db saturation metrics are flat through 08:55 and first rise together in the 08:57-08:59 bucket, ~2 min after the deploy and 57-58 min after the DBA autovacuum change, which is ruled out on both timing and mechanism (no vacuum log activity, flat disk usage, no IO metric, zero historical precedent). The reporter's cues are red herrings: order-service was indeed unchanged, and the autovacuum change at 08:00 is not the trigger. Residual uncertainty is confined to metadata-inferred details (index absence, query novelty, full blast radius), which do not change the fix.

## Probable root cause
**portfolio-service v4.5.0 deploy introduced a new Seq-Scan trades query that saturated shared ledger-db** -- bad_deployment in `portfolio-service`, triggered by `dep-5905` (confidence 0.78, high)

### H1: portfolio-service v4.5.0 deploy introduced a new Seq-Scan trades query that saturated shared ledger-db
portfolio-service v4.5.0 (dep-5905, deployed 08:56:00Z, live, not rolled back) added a new query on the shared 'trades' table filtered by account_id + executed_at with no migration/index. Each execution performs a Seq Scan (rows=48,211,907), driving ledger-db CPU to ~95-96%, slow_queries_per_min to ~140 and connections_active to ~190-210. Because ledger-db is a shared postgres co-tenant datastore, that saturation slows and times out order-service's own INSERT INTO orders, producing 284 statement-timeout ERRORs; portfolio-service itself degrades even more (~7s p99). order-service and ledger-db were not changed, so the reporter's 'no release this week' reassurance is true but irrelevant.
