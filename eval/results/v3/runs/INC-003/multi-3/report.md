# Incident investigation report: INC-003
*System: multi_agent | outcome: **root_cause_identified** | ended: critic_accepted*

## Summary
H1 is confirmed as the root cause: the vendor-owned external partner API (exchange-api / api.exchange-partner.example) began failing at ~11:01:25Z, and exchange-gateway — which calls it synchronously on placeOrder/quoteSnapshot — propagated that upstream failure to order-service as 504 Gateway Timeout on placeOrder, producing the ~30% submit failure rate. Confidence 0.82 (high, capped by the Critic). The order-service v2.15.2 rollback at 11:16Z did not restore service (errors still 31.42% at 12:52Z), and the affected fraction is a constant ~44-48% of upstream calls with flat request volume — both incompatible with the deployment hypothesis. The deepest telemetry is exchange-gateway's own (exchange-api has no telemetry), so the partner-side origin is inferred from the caller's timeout logs plus a matching historical precedent; this is the reason confidence is capped rather than higher.

## Probable root cause

### H1: External exchange-partner API (exchange-api) outage degrades exchange-gateway, surfacing as order-service 504s
The external, vendor-owned exchange partner API (api.exchange-partner.example, node exchange-api, has_telemetry:false) began failing at ~11:01Z. exchange-gateway, which calls it synchronously on placeOrder/quoteSnapshot with a 5000ms connect timeout, saw ~44-48% of those calls time out or return 503, opened its circuit breaker at 11:03:26Z, and slowed to 3-5.5s p99. order-service, which calls exchange-gateway on the submit path, then blocked and surfaced the upstream failure as exchange-gateway 504 Gateway Timeout on placeOrder, producing the ~30% submit failure rate. No deployment or config change on any internal component in the path caused it; the failure is load-independent and unaffected by the 11:16Z rollback.

**Causal chain**
1. exchange-api / api.exchange-partner.example stops serving a large fraction of calls: 5000ms connect timeouts on op=placeOrder and quoteSnapshot plus 503 Service Unavailable, first timeout logged 11:01:25Z [F11, F27, F15]
2. Because ~44-48% of upstream_error_rate is affected while request_rate is flat (245-292 req/s, no step), the failure is a fixed-fraction, load-independent upstream defect, not a capacity/load effect [F26, F29, F30]
3. exchange-gateway's own error_rate and upstream_error_rate step together from ~0.29% to 44.52% at the 11:01:00Z bucket and stay elevated; the previously cited 10:58Z onset was a coarse-bucket artifact and per-minute buckets show baseline through 11:00Z [F25, F26, F28]
4. exchange-gateway's circuit breaker for exchange-api opens at 11:03:26Z (failure ratio 0.47 over 60s), confirming sustained upstream failure rather than transient blips [F11]
5. order-service, calling exchange-gateway synchronously on placeOrder, blocks until it fails; the single dominant error signature is exchange-gateway 504 Gateway Timeout on placeOrder (349 lines, first_seen 11:02:45Z, still occurring 12:58:54Z) [F9, F3]
6. order-service error rate steps 0.2% -> 23-31% and p99 147ms -> ~4-5.4s, sustained through 12:52Z, with zero restarts and flat inbound request_rate, i.e. the symptom is upstream-propagated latency, not an internal order-service defect or load surge [F7, F8, F12, F30]
7. Onset ordering is internally consistent: first gateway upstream timeout 11:01:25Z -> gateway error bucket 11:01:00Z -> first order-service error 11:02:45Z (~1m20s later) [F27, F28]
8. No internal component in the failing path received any change: zero deploys and zero config changes on exchange-gateway over a full 48h window, zero deploys on exchange-api, and the only window changes (order-service v2.15.2, pricing-engine cache TTL) are on other components/paths [F14, F20, F21, F19, F2]
9. Rollback of v2.15.2 at 11:16Z did not restore service (order-service still 31.42% avg at 12:52Z), severing any causal role for the only nearby deploy [F16, F1]
10. The signature matches the historical dependency_failure precedent HIST-103 (external exchange API outage producing 504 on order submit / upstream timeouts in order-service + exchange-gateway, resolved by partner fix), and no internal-change precedent produces a circuit-breaker open on exchange-api [F23, F24]
