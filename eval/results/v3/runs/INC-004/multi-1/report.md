# Incident investigation report: INC-004
*System: multi_agent | outcome: **root_cause_identified** | ended: critic_accepted*

## Summary
The three OOMKills of notification-service are best explained by H1 (confidence 0.70, medium, accepted at cap 0.80): the v3.8.0 deploy dep-5402, which added an in-memory TemplateCache to the email render path, is followed within ~2h by the onset of a steady ~3-4%/h linear heap ramp from a flat ~48% baseline, producing exit-137 OOMKills on a ~23-24h cycle (F1/F9/F12/F15). The reporter's Kafka-replay theory is rejected on positive evidence: the retention cut cfg-2410 post-dates two of three OOMs (F16), the broker was undisturbed across 17:00-21:00Z with no reassignment/rebalance in logs (F26/F27), and notification-service lag is flat-normal until after the 19:59:21Z restart, so the "replay backlog" is post-restart drain (F28) — the sibling consumer on the same broker shows neither lag nor memory growth (F29/F30). The load-bearing unproven hop is that TemplateCache is genuinely unbounded; no tool exposes code or a cache-policy config, so this is recorded as an assumption rather than a verified fact. Mitigation should proceed now (roll back or bound the cache), because H1 and "unknown leak origin in the same deploy" point to the same fix.

## Probable root cause
**v3.8.0 in-memory TemplateCache leak causes linear heap growth → periodic OOM** -- bad_deployment in `notification-service`, triggered by `dep-5402` (confidence 0.70, medium)

### H1: v3.8.0 in-memory TemplateCache leak causes linear heap growth → periodic OOM
notification-service dep-5402 (v3.8.0, 2026-03-21T00:00Z, 'Add in-memory template cache for email rendering', TemplateCache = hand-rolled ConcurrentHashMap keyed by template+locale+userSegment, no documented bound/TTL/eviction) introduced an in-process cache on the render path whose footprint grows monotonically with render volume. Heap grows ~linearly at ~3-4%/h from a flat ~48% baseline, reaches ~97-98%, and the container is OOMKilled (exit 137) roughly every 23-24h; each restart resets heap to ~48% and the cycle repeats. The transient consumer-lag spikes are a CONSEQUENCE of each restart (backlog drained after restart), not the cause. The single load-bearing unproven hop is that the cache is unbounded; onset+mechanism-shape+exclusivity of the change are all verified.

**Causal chain**
1. dep-5402 adds an in-memory TemplateCache (ConcurrentHashMap, keyed template+locale+userSegment) on the render path, with no bound/TTL/eviction documented in the change record [F1, F13, F19, F22]
2. No config/flag bounds the cache: notification-service config query is count 0 and the only config change in the window is the unrelated Kafka retention edit [F21, F17]
3. Cache entries accumulate across distinct keys as renders occur; heap grows ~linearly at ~3-4%/h [F9, F12]
4. Growth onset (~2026-03-21T02:00Z) follows the 00:00Z deploy with a ~2h lag; baseline before is flat ~48% [F9, F12, F15]
5. Heap nears 100%, old-gen heap/GC-pressure warnings appear (heap >90%, full GC 1.0-8.1s) with no application exception [F11]
6. Container exceeds its memory ceiling and is OOMKilled (exit 137) at ~23-24h intervals [F7, F8]
7. Restart resets heap to ~48% and drains the backlog accumulated during the stall, producing the transient consumer-lag spike that begins only AFTER the restart [F9, F10, F28]
8. The other consumer on the same shared broker (settlement-service) shows neither the memory sawtooth nor any lag spike, isolating the fault to notification-service rather than the shared dependency [F29, F30]

### H2: Kafka retention-cut maintenance (cfg-2410) triggers a replay/rebalance backlog that notification-service chokes on
Reporter's theory: the Kafka platform change cfg-2410 (log.retention.ms 7d→3d at 2026-03-23T18:00Z) triggered segment deletion/reassignment and a consumer replay; notification-service buffered the replayed backlog, raising memory and causing the OOMKill ~2h later. Kafka is a shared broker so a broker-side event is structurally plausible. Now rejected on both timing AND direct broker-side evidence: the retention cut post-dates two of the three OOMs, AND the broker telemetry/logs show no disruption at 18:00Z and the only lag burst begins AFTER the restart.

**Causal chain**

### H3: Shared-Kafka / broker-side rebalance or partition-reassignment storm (à la HIST-104/HIST-112)
A broker-side event (partition reassignment / consumer-group rebalancing storm during Kafka maintenance) stalled the notification-service consumer, producing lag and delayed emails, with an indirect memory effect. Precedents HIST-104 and HIST-112 show this symptom set for the notification/settlement/Kafka trio — but neither has an OOMKilled signature, and broker telemetry now shows no such event in-window.

**Causal chain**
1. A partition reassignment / broker maintenance event occurs on shared Kafka *(assumed)*
2. Consumer group rebalances and loses/regains partitions [F6]
3. Lag spikes and email delivery is delayed [F10, F18]
4. Memory blowup and OOMKilled restart follows *(assumed)*
5. Contradicted: broker shows zero under-replicated partitions and no throughput disruption in-window, and the other consumer shows no lag or memory growth [F26, F29, F30]
6. Contradicted: observed signature is a linear heap sawtooth with GC-pressure warnings and fixed periodicity, not a transient stall [F8, F9, F11, F12]
