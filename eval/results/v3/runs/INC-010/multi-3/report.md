# Incident investigation report: INC-010
*System: multi_agent | outcome: **inconclusive** | ended: critic_inconclusive*

## Summary
The failure mechanism is established: settlement-service's consumption collapsed at ~07:42Z (61.6 → 0.4 req/s in the 07:40Z bucket) exactly as consumer lag began climbing monotonically, and the logs show a verbatim deserialization failure on a single record (orders-3@8841207, "missing required field qty; schema v1 expected, header says v2") followed by a poison-message hot-loop with attempt counters ~92k and an explicit "partition blocked", with CPU pinned at 60-71% consistent with busy retry rather than an idle or dead consumer. Broker/producer ingress stayed flat (~2.5k msg/s) and the downstream ledger-db path showed no distress, and four complete keyword searches positively excluded rebalance/revocation/assignment/session churn, so H3 and H4 are dead. However, the origin is not established: the one load-bearing hop of H1 — that order-service dep-6010 authored the orders-3 record — is supported only by strong naming/field correlation (qty→quantity, "venue", header v2) and by the absence of any other producer schema change in the window, because no queryable artifact in the toolset binds any producer to the orders-3 topic. Because the decisive hop is unprovable with the available data and the alternative origin (payment-service as publisher, and v2-body vs mislabeled-v1-body) remains open, the ranking cannot be defended at 0.66 confidence, and this report is honestly inconclusive.

## Probable root cause
**Inconclusive** -- the evidence does not single out one cause. See ranked hypotheses and data gaps.

### H1: order-service v2.16.0 event schema change (qty→quantity, header v2) produced records settlement-service cannot deserialize, causing a poison-record hot-loop that blocks partition orders-3
order-service v2.16.0 (dep-6010, deployed 07:40Z) renamed 'qty' to 'quantity', added a 'venue' field and an event schema version header v2 on the OrderExecuted event. settlement-service's OrderExecuted deserializer, asserting schema v1, rejects the first v2-header record (orders-3@8841207) at 07:42:14Z with 'missing required field qty (schema v1 expected, header says v2)'. The consumer retries the same offset endlessly (attempt counters ~92k), the partition is explicitly reported 'blocked', throughput flatlines at ~0.4 req/s, lag grows ~1k msg/10min and CPU pins at 60-71% from busy retry-looping. Broker ingress and the downstream DB path are both demonstrably healthy, and four complete untruncated keyword searches positively rule out rebalance/assignment churn, so the fault originates in the producer's schema/header change, not in the consumer's settings, the broker, or the DB. OPEN DETAIL (not a separate hypothesis): whether the payload body is a genuine v2 body the consumer must learn, or a v1-shaped body mislabeled v2 by the producer. Either way the trigger is the producer-side schema/header transition introduced by dep-6010 (the only producer schema change in the window) and the blocker is the consumer's inability to cope; the fix owner is the same.

**Causal chain**
1. order-service v2.16.0 (dep-6010) deployed 07:40Z renames 'qty'→'quantity', adds 'venue', emits schema version header v2 on OrderExecuted — the sole producer-side schema change and sole deployment in the window [F2, F32, F33, F35]
2. Settlement stalls at the same time: throughput collapses in the 07:40Z bucket (61.6→0.4 req/s) and lag climbs monotonically from ~48 to ~62k [F7, F8, F14]

The reporter's own suspicion, retained because a poll-batch change is the only config change in the window and precedes onset.

**Causal chain**
1. Only config change in the window: max.poll.records 500→200 at 07:35Z by m.das, verified applied at runtime 07:35:37Z, preceding onset ~07:42Z [F1, F17, F3]
