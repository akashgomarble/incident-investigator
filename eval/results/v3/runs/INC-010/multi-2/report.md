# Incident investigation report: INC-010
*System: multi_agent | outcome: **root_cause_identified** | ended: critic_accepted*

## Summary
The settlement stall is best explained (confidence 0.60, medium) by H1: order-service deployment dep-6010 (v2.16.0, "Order events v2", 07:40Z) changed the OrderExecuted contract — renaming qty to quantity, adding venue, and introducing a v2 schema header — while settlement-service still deserializes schema v1. The first error appears at 07:42:14Z, ~2 minutes after the deployment, and lag and the processing collapse both start in the same 07:42Z bucket (F1, F3, F4, F11). The failure is an unambiguous error-driven poison-message retry loop pinned to a single offset (orders-3@8841207): 409 ERROR lines split entirely between deserialization failure and "partition blocked" retries, with attempt counters in the tens of thousands and still spinning at 09:58Z (F4, F27, F28, F40, F41). All alternatives are contradicted: the config change cfg-3004 cannot produce a deserialization error (F4, F20, F27), the shared broker is clean with no triggering change (F13, F19, F21), and producer volume is flat (F14, F35). One link remains inference-only — that order-service actually emitted a well-formed v2 payload at that offset — because no producer publish telemetry (F31), raw record bytes (F30), or text record of the offset (F42, F43) exists; this is treated as a stated assumption and an open detail of the established origin rather than a rival origin, since both the clean-v2-payload and malformed-v2-bytes variants stem from the same change and the same fix family.

## Probable root cause
**order-service v2.16.0 schema change introduced an OrderExecuted v2 record that settlement-service's v1 deserializer rejects as a poison message** -- bad_deployment in `order-service`, triggered by `dep-6010` (confidence 0.60, medium)

### H1: order-service v2.16.0 schema change introduced an OrderExecuted v2 record that settlement-service's v1 deserializer rejects as a poison message
The sole deployment in the window, dep-6010 order-service v2.16.0 at 07:40Z ('Order events v2'), changed the produced OrderExecuted contract: field qty renamed to quantity, venue added, and an event schema version header v2 introduced (F7, F11). settlement-service still expects schema v1, so the record at offset orders-3@8841207 fails with 'failed to deserialize OrderExecuted at orders-3@8841207: missing required field qty (schema v1 expected, header says v2)' at 07:42:14Z, ~2 min after the deployment. The consumer treats it as a poison message, blocks partition orders-3 and retries the same offset tens of thousands of times (still active at 09:58Z), collapsing request_rate from 61.58 to ~0.4 req/s and driving lag monotonically to ~61.6k. The origin is the producer-side contract change in dep-6010. Two hops remain unproven and are now known to be permanently unverifiable from logs/bytes: (a) that order-service emitted a well-formed v2 payload at that offset, and (b) whether the blocked record is a clean v2 payload or malformed/truncated bytes. Both sub-mechanisms share the same origin (dep-6010's v2 change) and the same fix family (reconcile the OrderExecuted contract between producer and consumer), so they are one hypothesis with an open detail; the malformed-bytes variant would add a producer serialization fix. Round-2 evidence closes the corrupt-bytes-vs-clean-v2 question negatively at the text level: no service ever logs 'quantity' (F43) and no text record of offset 8841207 exists on producer or co-consumer (F42), so neither variant can be positively confirmed or discriminated. Confidence is held at 0.6, not raised, because the emission hop is inference-only.

**Causal chain**
