# Incident investigation report: INC-012
*System: multi_agent | outcome: **root_cause_identified** | ended: critic_accepted*

## Summary
The payment-service failures in INC-012 were not caused by the v6.0.0 mandate release (dep-6203). The root cause is ledger-db disk exhaustion: the inactive replication slot 'analytics_cdc' retained WAL for hours, filling /var/lib/postgresql/data (78.16% at 11:00Z, monotonically to 100% by 14:55-14:58Z), after which PostgreSQL could not extend files or write WAL and 'No space left on device' propagated up the direct DB write path to every writer inserting into ledger-db. Confidence is high (0.83, capped at 0.88 by the Critic) — the disk-fill metric series, the slot WAL-retention logs, the PG PANIC/storage error text, and the identical 14:55-14:58 onset across three of four ledger-db writers (payment-, settlement- and order-service, including services the deploy never touched) all cohere, while rollback of v6.0.0 did not clear the ~60% error rate. The deploy is coincidental: it postdates the start of the disk climb by ~3h48m.

## Probable root cause
**ledger-db disk exhaustion from WAL retained by inactive replication slot analytics_cdc (state/monitoring failure, not app code)** -- resource_exhaustion in `ledger-db`, triggered by `null` (confidence 0.83, high)

### H1: ledger-db disk exhaustion from WAL retained by inactive replication slot analytics_cdc (state/monitoring failure, not app code)
The shared postgres datastore ledger-db exhausted its /var/lib/postgresql/data filesystem because the inactive replication slot 'analytics_cdc' retained WAL for hours (log-visible from 12:19:34Z, but the disk was already 78% full at the start of the observable window, 11:00Z, and the metric climbs monotonically from there to 100% by 14:55-15:00). PostgreSQL then could not extend files or write WAL, and 'No space left on device' propagated up the direct DB write path to every writer that was actively INSERTing (payment-service, settlement-service, order-service all break within the 14:55-14:58 buckets with identical storage error text), while portfolio-service — which emitted zero errors — did not. The v6.0.0 mandate deploy (dep-6203) is coincidental: it postdates the start of the disk climb by ~3h48m, and its rollback at 15:12Z did not clear the ~60% error rate.

**Causal chain**
1. Replication slot 'analytics_cdc' went inactive and began retaining WAL; earliest log evidence 12:19:34Z shows 63157MB retained, and retention oscillated 63-92GB all morning (12:19-14:16), sitting at 69518MB at 14:46:32Z inside an ongoing pattern, not a step at deploy. [F30, F31]
2. The retained WAL plus normal growth filled ledger-db's data volume: disk_used_pct rises monotonically 78.16% (11:00) -> 89.18% (13:00) -> 98.38% (14:35-40) -> 99.93% (14:56) -> 100.0% (14:58 onward), mean 97.27, 0 missing points. [F25, F26, F27, F33]

4. With the volume hard-full, PostgreSQL failed to write WAL / extend relation files: PANIC 'could not write to file pg_wal/xlogtemp.37478: No space left on device' starting 15:01:01Z and 'could not extend file base/16402/2619'; 47 ERROR lines in ledger-db 14:34-15:19. [F10]
5. That DB storage error propagated verbatim up the direct payment-service -> ledger-db edge (no intermediate ledger-service exists): 'ledger write failed: ERROR: could not extend file: No space left on device', 59 occurrences, first 15:00:26Z. [F9, F1, F17]
6. order-service, another direct ledger-db writer, emits the same signature: 'INSERT INTO orders failed: No space left on device', 236 ERROR entries, first 15:00:42Z through 16:57:47Z. [F20]

### H5: Second ledger-db write-path failure (order-service's datastore) or a second, independent shared-dependency origin
order-service's error signature is 'INSERT INTO orders failed: No space left on device' — a write to its own orders table/datastore, not necessarily the ledger write path. If order-service writes to a *different* postgres instance (or a different volume) that also filled, then the simultaneous 14:55-14:58 onset across payment-service, settlement-service and order-service could reflect a cluster-wide / shared-volume / shared-host disk exhaustion (e.g. a common host or shared storage layer) rather than one ledger-db volume — a different origin, and a different fix (free the shared volume / host), even though the proximate mechanism (no space) is the same.

**Causal chain**
1. order-service errors on 'INSERT INTO orders failed', a table that need not reside in ledger-db. [F20]

4. ledger-db itself shows the no-space errors and 100% disk, so at minimum the ledger volume is full; whether order-service shares it is unresolved. [F10, F25]
