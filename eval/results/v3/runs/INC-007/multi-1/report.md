# Incident investigation report: INC-007
*System: multi_agent | outcome: **inconclusive** | ended: critic_accepted*

## Summary
The origin of the 14:02Z 401 storm is firmly localized to auth-service and to the two changes that landed there 1-2 minutes before onset (dep-5710, auth-service v7.3.0 at 14:00Z; cfg-2705, jwt.signing.key_id rotation at 14:01Z), with api-gateway's simultaneous step being propagation rather than an independent fault and the shared-dependency (redis-cache/user-db) leg positively contradicted by flat, complete indicator series. However, which of those two co-located changes is the actual trigger remains undecidable: the top hypothesis H1 (jjwt/TokenValidator validation regression, confidence 0.45) is below the 0.50 threshold, and the decisive discriminator (the 401 error text) is permanently unavailable because the identity-namespace log pipeline is down, with no per-kid, per-replica, deployed_version or build_version dimension exposed by auth-service. The fix direction is the same either way, so we recommend acting on the change pair rather than waiting for further discrimination. Residual uncertainty is limited to user-db cpu_pct/disk_used_pct and api-gateway's request-rate denominator (both never retrieved) plus possible sub-180s transients.

## Probable root cause
**Inconclusive** -- the evidence does not single out one cause. See ranked hypotheses and data gaps.

### H1: JWT library upgrade (dep-5710) introduced a token-validation regression
The auth-service v7.3.0 deployment dep-5710, which upgraded jjwt 0.11->0.12 (breaking parser API) and rewrote TokenValidator, changed token-validation semantics so a class of otherwise-valid tokens now fails, surfacing as a clean step to ~36% HTTP 5xx on auth-service in the single 14:02Z bucket and propagating to api-gateway. Origin is the code release itself; the open detail (parser default change vs new bug vs a partial class of tokens) does not change the fix direction.

**Causal chain**
1. auth-service v7.3.0 deployed 2026-04-15T14:00:00Z: jjwt 0.11->0.12 breaking parser API, TokenValidator rewritten; live, never rolled back. [F3, F7, F4]
2. It is one of only two changes across ALL services in the window (the other being cfg-2705 on the same service), and the only auth-service deploy. [F9, F21, F4]
3. The rewritten validator mis-handles a class of tokens (parser defaults / skew / algorithm / key handling), producing invalid_token for a fraction of validations. *(assumed)*
4. auth-service error_rate steps from ~0.2% to 36.08% in the single 60s bucket at 14:02Z with no intermediate value (14:00 0.26, 14:01 0.16, 14:02 36.08) and holds at 34-38.5%. [F13, F14, F25, F26, F27, F28]
5. The step is all-at-once with no staggered/partial-availability shape, which is the shape a code/version switch produces and does NOT match a rolling multi-pod key propagation. [F26, F30]
6. api-gateway flips in the identical 60s bucket (0.19 -> 20.72%) with flat latency and zero restarts, i.e. it propagates auth-service's failures rather than originating them, and its ~21% is a diluted ~half of auth's 36%. [F31, F32, F33]
7. No saturation/restart/throttle signature in auth-service's own metrics, consistent with a pure validation-logic fault rather than resource exhaustion. [F16, F28]
8. Users logged out / 401 invalid_token reported from this sustained elevated auth-service response-error rate. [F15, F18, F33]
