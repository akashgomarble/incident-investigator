# Incident investigation report: INC-001
*System: multi_agent | outcome: **root_cause_identified** | ended: critic_accepted*

## Summary
The order-service 500s on POST /v1/orders are caused by dep-5101 (order-service v2.14.0, deployed 2026-03-03T12:10Z), whose refactor replaced the legacy OrderRules.validateMargin() with the new MarginCheckValidator, which dereferences a null marginProfile on the F&O/derivatives path and throws an in-process NullPointerException at MarginCheckValidator.java:88 that is converted to HTTP 500. Confidence is medium (0.72, top hypothesis clearly ahead of the alternatives). Evidence is strong on mechanism, timing, and scope: onset is pinned to ~12:12:30Z, ~2 minutes after the deploy, the error signature is a pure in-process NPE with no timeout/downstream-5xx/saturation signature, all 426 errors are FNO-only, and the ~18% error rate has not recovered with no rollback. The main residual uncertainty is the provenance of the null marginProfile (H2), but no producer of marginProfile is discoverable in the catalog, dependency graph, config history, or incident history, and the fault emanates from the newly deployed code path regardless.

## Probable root cause
**dep-5101 order-service margin-check refactor dereferences a null marginProfile for F&O orders** -- bad_deployment in `order-service`, triggered by `dep-5101` (confidence 0.72, medium)

### H1: dep-5101 order-service margin-check refactor dereferences a null marginProfile for F&O orders
The order-service v2.14.0 deployment dep-5101 (2026-03-03T12:10Z) replaced legacy OrderRules.validateMargin() with the new MarginCheckValidator in the order validation chain. On the F&O/derivatives path the new validator dereferences a marginProfile that is null for the relevant accounts (MarginCheckValidator.java:88), throwing a NullPointerException that is converted in-process to HTTP 500. The change is scoped to F&O margin checks, so only derivatives orders fail. The null's ultimate provenance (new code's own default-profile population vs an unlocated upstream source) is unresolved; the fault ORIGINATES in the new order-service code path regardless, because the legacy path either tolerated or did not perform this dereference and the refactor replaced it.

**Causal chain**
1. dep-5101 (order-service v2.14.0) is deployed at 12:10Z; it is the only deployment touching order-service in the window and is never rolled back. [F1]
2. dep-5101 replaces the margin logic in the validation chain: it adds MarginCheckValidator and removes legacy OrderRules.validateMargin(), scoped to F&O margin checks. [F2]
3. Error onset at ~12:12:30Z follows the deploy by ~2 minutes: metric step in the 12:10-12:12Z buckets and the first ERROR log at 12:12:31Z, immediately after the 12:10:08Z 'rollout complete' entry. [F7, F8, F26, F28]
4. The new margin-profile dereference returns null on the F&O path, raising NullPointerException at MarginCheckValidator.validate line 88. [F9, F13, F14]
5. The exception is thrown inside order-service's validation chain and converted immediately to HTTP 500, so all 426 errors are NPE-based with no timeout/downstream-5xx/connection-exhaustion signature. [F13, F14, F27]
6. Only orderType=FNO appears in every error, matching the F&O-scoped change and the report's 'mostly derivatives orders'. [F10, F15]
7. Failures persist at a steady ~18% with no recovery and no rollback, consistent with a live bad build. [F7, F18, F28]
