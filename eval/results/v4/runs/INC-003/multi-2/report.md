# Incident investigation report: INC-003
*System: multi_agent | outcome: **root_cause_identified** | ended: critic_accepted*

## Summary
The order-submit failures are caused at the exchange-gateway → external exchange-api (api.exchange-partner.example) hop, not by the order-service v2.15.2 release. From ~10:58-11:02Z, exchange-gateway's upstream_error_rate stepped from ~0.3% to ~46% and upstream_latency from ~120ms to ~9.4s while its own callers (order-service 30%, market-data-service 6.5%, api-gateway 6.2%) degraded at the same instant, and order-service's errors are exclusively 504s on its placeOrder call to exchange-gateway with flat local CPU and DB-pool. The order-service release was rolled back at 11:16Z yet failures persisted to 12:58Z, and no change on the failing path is recorded, ruling out the deployment and the pricing-engine TTL change. Confidence in the fault location (the gateway↔external-exchange edge, downstream of and below order-service) is high; confidence in the top hypothesis as ranked is medium (0.62) because the vendor-owned exchange-api has no telemetry, so an application failure at the partner (H1) and a network/path failure to the partner (H4) are indistinguishable from our side — both name the same system to remediate.

## Probable root cause
**External exchange partner (exchange-api) outage degrading exchange-gateway, surfacing as 504s on order submit** -- dependency_failure in `exchange-api (api.exchange-partner.example, vendor-owned external)`, triggered by `null` (confidence 0.62, medium)

### H1: External exchange partner (exchange-api) outage degrading exchange-gateway, surfacing as 504s on order submit
The vendor-owned external exchange API (api.exchange-partner.example) began failing around ~11:00Z. exchange-gateway, the component that calls it, hit 5s upstream connect timeouts and returned 503s; order-service's synchronous placeOrder call to exchange-gateway then timed out, producing the 30% 504 error rate. order-service v2.15.2 is coincidental - it is only the most-visible victim of a fault one layer below it. This is the leading hypothesis: the failing layer is now directly localized to the exchange-gateway→exchange-api hop, whose upstream_latency (9.4s) and upstream_error_rate (46%) are both larger and nearer the failure than any caller's metrics, and every downstream-facing caller (order-service, market-data-service) is co-affected at the same instant, while no order-service-local resource moved.

**Causal chain**
1. External exchange API api.exchange-partner.example degrades / becomes unreachable around ~11:00Z *(assumed)*
2. exchange-gateway's calls to it time out: 470 ERRORs from 11:01:25Z - 'upstream connect timeout after 5000ms host=api.exchange-partner.example op=placeOrder' (163), 'exchange-api returned 503 Service Unavailable' (161), 'op=quoteSnapshot' timeouts (146) [F12]
3. exchange-gateway's own upstream metrics show the step one layer below it: upstream_latency ~117ms → 9,402ms and upstream_error_rate 0.31% → 45% at 11:02Z, while its inbound p99 pins to ~5,100ms - the 5s client-side connect timeout - confirming the failing layer is the gateway→exchange-api hop, not the gateway's own inbound handling [F27, F26, F12]
4. exchange-gateway is a direct http callee of order-service on the placeOrder path, and its upstream exchange-api has has_telemetry=false, so the vendor failure is only observable as timeouts reported at exchange-gateway [F15, F5, F22]
5. order-service's synchronous placeOrder call hangs and returns 504; all 349 order-service ERROR logs are the single pattern 'exchange-gateway call failed: 504 Gateway Timeout (placeOrder)' from 11:02:45Z [F8, F9]
6. Only placeOrder fails and p99 latency rises ~35x to ~4-5s (matching the 5s upstream connect timeout) while order-service CPU (~40%) and db_pool_in_use (~14) stay flat, so order-service itself is not saturated [F9, F10, F11]

Blast radius is consistent with one gateway-side fault propagating to its callers: market-data-service (other direct callee of exchange-gateway) steps to 6.48% error at exactly 11:02Z, and api-gateway steps to ~6% at 11:00Z, i.e. the fault is visible tier-wide rather than at order-service alone [F28, F29, F23, F32]
8. Failure persists at ~30% through 12:50Z and order-service 504 logs continue to 12:58:54Z, long after the 11:16Z rollback of v2.15.2, and exchange-gateway's error rate holds ~42-47% flat - an ongoing external-side condition, not a removed deployment [F7, F14, F25]

### H2: order-service v2.15.2 (idempotency-keys release) introduced a defect that hangs its exchange-gateway call
The reporter's suspicion: order-service v2.15.2 deployed at 10:48Z changed the placeOrder path (e.g. client config, timeout or connection handling around the idempotency-key wrapper) so that calls to exchange-gateway hang and return 504s. In this reading the ~11:00Z onset is the release's latent effect, and the rollback at 11:16Z simply had not yet taken effect or did not fully remove the fault.

**Causal chain**
1. order-service v2.15.2 (dep-5333, 'Add idempotency keys to order submit') deployed 10:48:00Z [F1, F13]
2. The new submit/idempotency code path mishandles timeouts or connection reuse on the outbound exchange-gateway call *(assumed)*
3. placeOrder calls to exchange-gateway hang and return 504 Gateway Timeout; error onset ~11:00Z [F8, F9, F7]
