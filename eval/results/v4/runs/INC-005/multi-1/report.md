# Incident investigation report: INC-005
*System: multi_agent | outcome: **root_cause_identified** | ended: critic_accepted*

## Summary
H1 is identified as the root cause with high confidence (0.82): payment-service's outbound mTLS client certificate (CN=payments-client.orangeinvest.internal) expired at exactly 2026-04-02T12:15:00Z, causing 100% of bank-partner-api calls to fail at the TLS handshake while the HTTP error-rate dashboard stayed green (~0.22%). The failures are deferred as PENDING_RETRY on an async outbound rail, so no HTTP 5xx was generated — 311 in-window ERRORs, bank_api_error_rate 0.21%→100%, payment_success_rate 99.4%→~2.5%, restarts flat at 0, all flipping in the same 12:15:00Z bucket and first error logged at 12:15:27Z. Every change-based alternative is excluded by mechanism and path: no deploy or config change falls in the symptom window, and the only relevant config change (cfg-2502, timeout 3000→5000ms at 11:20Z) cannot cause a TLS handshake rejection and precedes onset by ~55 minutes. The one residual uncertainty is H1 vs H2 (bank-side TLS/CA change), which is permanently unobservable because bank-partner-api has has_telemetry=false; the untruncated log text explicitly names OUR client cert and its notAfter matching the onset to the second, so the payer-side origin is established and H2 remains only an unfalsifiable fallback.

### H1: Client mTLS certificate on the bank rail expired at 12:15Z (our side), failing 100% of outbound bank calls while HTTP error-rate stays green
payment-service's outbound mTLS client certificate (CN=payments-client.orangeinvest.internal) had notAfter=2026-04-02T12:15:00Z. At that exact instant every outbound call to bank-partner-api began failing at the TLS handshake (alert 45, expired certificate), so transfers were marked PENDING_RETRY (async/deferred) rather than returning 5xx. Because the failure is on a non-HTTP dependency path handled asynchronously, the payment-service HTTP error-rate panel stayed flat (0.16-0.28%) while payment_success_rate collapsed from 99.4% to ~2.5% and bank_api_error_rate went to 100%. No deployment, config change or cert-rotation event sits near the onset; the expiry is a certificate lifecycle event invisible to change tooling.

**Causal chain**
1. payment-service's client certificate for bank-partner-api reaches notAfter=2026-04-02T12:15:00Z [F4, F25, F27]
2. At 12:15Z the TLS handshake to bank-partner-api is rejected ('tls: expired certificate (alert 45)'); first error log 12:15:27Z, identical CN/notAfter signature repeating 80+ times through 12:59Z (sustained, unchanging) [F4, F24, F27]
3. The rejection is specifically a certificate expiry — no other TLS alert code (42/48) appears anywhere in the window — and the peer-reported 'remote error' prefix denotes where alert 45 was surfaced, not that the peer's cert expired [F26, F28, F30]
4. The identical expired-certificate signature is absent from every other component swept in 12:10-13:00Z (kafka, api-gateway, settlement-service, ledger-db, auth-service, order-service, portfolio-service, pricing-engine — 8 components, 0 matches), localizing the event to payment-service's bank-rail cert [F29, F31, F32, F33, F34]
5. bank_api_error_rate flips to a sustained 100.0% for every bucket 12:15-13:55 and payment_success_rate collapses to ~2.5% [F2, F3]
6. Payment attempts fail fast and are deferred as PENDING_RETRY rather than crashing the request path; p99 latency drops 320ms->140ms, restarts stay 0 [F5, F24]
7. Because the failure is on an async/deferred dependency path outside the HTTP handler's error accounting, the synchronous HTTP error_rate panel remains green — the reported dashboard discrepancy [F1, F3, F5]
8. No deploy/flag/cert-rotation event correlates with the 12:15Z onset, consistent with an automatic certificate lifetime expiry invisible to change tooling [F7, F13, F15, F19, F22, F35, F36]
