# Incident investigation report: INC-010
*System: multi_agent | outcome: **root_cause_identified** | ended: critic_accepted*

## Summary
Settlements stopped because settlement-service hit a poison message on topic partition orders-3 at offset 8841207: its consumer failed to deserialize an OrderExecuted event ('missing required field qty, schema v1 expected, header says v2') and entered a retry loop that locked that partition, so offsets stopped committing and lag climbed from ~40 msgs at 07:38Z to ~60k by 09:55Z. The onset is tightly coupled to the only change in the window that declares a v2 event schema: order-service v2.16.0 (dep-6010) deployed at 07:40Z, one minute before throughput collapsed from ~62 req/s to ~0.4 req/s and lag began rising at 07:41Z. Dependency-side and broker-side causes are affirmatively contradicted by measurement: ledger-db p99 flat at ~238 ms with an unsaturated pool and zero WARN logs, and the kafka broker healthy (~35% CPU, ~2500 msg/s, under_replicated_partitions flat 0, no rebalance logs). Confidence is medium (0.68), capped because the message-level attribution of the v2 event to order-service rather than the second producer payment-service is inferred from deploy timing and schema-declaration evidence rather than verified from message headers or offsets.

## Probable root cause
**order-service v2.16.0 schema change produced OrderExecuted v2 events that settlement-service cannot deserialize, blocking a partition** -- bad_deployment in `order-service`, triggered by `dep-6010` (confidence 0.68, medium)

### H1: order-service v2.16.0 schema change produced OrderExecuted v2 events that settlement-service cannot deserialize, blocking a partition
order-service v2.16.0 (deployed 07:40Z, tc-001/F1/F19) renamed the OrderExecuted field qty -> quantity and emitted a v2 schema header. settlement-service still deserializes with schema v1 expectations, so the first v2 message on partition orders-3 (offset 8841207) fails to deserialize ('missing required field qty, schema v1 expected, header says v2'), entering a poison-message retry loop that blocks that partition and halts offset commitment, so zero settlements post and consumer lag climbs monotonically. The consumer process stays alive, no dependency saturates, and the broker keeps delivering ~2500 msg/s, ruling out dependency- and broker-side causes.

**Causal chain**
1. order-service v2.16.0 (dep-6010) deployed at 07:40Z changes OrderExecuted schema: qty->quantity, adds venue, header v2; it is the ONLY deployment in the window and the only change declaring a v2 event-schema header [F1, F19, F20]
2. Producer emits v2 OrderExecuted messages onto the shared kafka topic; the broker keeps delivering normally at ~2500 msg/s with no dip and under_replicated_partitions flat at 0 [F16, F29, F26, F21, F23]
3. settlement-service consumer fails to deserialize the v2 message at orders-3@8841207: 'failed to deserialize OrderExecuted ... missing required field qty (schema v1 expected, header says v2)' [F9]
4. Consumer retries the same offset indefinitely ('retrying orders-3@8841207 (attempt <n>), partition blocked'; 196 occurrences, all errors cite the same offset, no other partition appears) [F9, F10]

Zero settlements post for the whole window; no crash/restart (restarts 0.0), no dependency saturation (ledger-db p99 flat ~238ms, pool flat ~6, ledger-db cpu/connections/slow_queries flat), no broker failure — consumer receives work but completes none, i.e. failure is downstream of fetch [F11, F13, F14, F15, F16, F17, F18]
