# Incident investigation report: INC-010
*System: multi_agent | outcome: **root_cause_identified** | ended: critic_accepted*

## Summary
Settlement processing on settlement-service is stalled because order-service deployment dep-6010 (v2.16.0, live 2026-05-12T07:40:00Z) renamed the OrderExecuted field 'qty'->'quantity' and stamped the event header 'v2', while the settlement-service consumer still expects schema v1; the resulting message at orders-3@8841207 cannot be deserialized and becomes a poison message that blocks partition orders-3 and is retried tens of thousands of times, so consumption collapses (~62 -> ~0.4 req/s) and consumer lag climbs monotonically to 60k+. The conclusion is supported by verified, content-specific evidence (exact schema-vocabulary match between the deploy's declared changes and the consumer's error, tight temporal ordering, fixed-offset poison retry, stall-shaped resource profile) with confidence 0.72 (medium, capped) because the producer->partition hop is circumstantial. H2 (cfg-3004 poll settings), H3 (broker/DB event), H4 (volume burst) and H5 (metrics artifact) are each contradicted by verified observations, not merely dismissed, though a silent unrecorded broker/DB event can only be weakened, not positively excluded. The one open sub-question - producer shipped uncoordinated v2 vs. consumer is stale v1 - names the same origin and the same causal chain, so it does not change the ranking or the fix direction.

## Probable root cause
**order-service v2 OrderExecuted schema (qty→quantity, v2 header) produced a record the v1 settlement consumer cannot deserialize** -- bad_deployment in `order-service`, triggered by `dep-6010` (confidence 0.72, medium)

### H1: order-service v2 OrderExecuted schema (qty→quantity, v2 header) produced a record the v1 settlement consumer cannot deserialize
dep-6010 (order-service v2.16.0, live at 07:40:00Z, the only deployment in the fleet window) renamed the OrderExecuted field 'qty'→'quantity' and stamped the event schema version header 'v2'. settlement-service's consumer still expects schema v1 and requires field 'qty'; on orders-3@8841207 it fails deserialization ('missing required field qty (schema v1 expected, header says v2)'), the record becomes a poison message, the retry loop re-attempts the same offset tens of thousands of times ('partition blocked'), the consumer never commits past it, so consumption collapses to a ~0.4 req/s floor and lag grows monotonically to 60k+. The fault ORIGIN is the uncoordinated OrderExecuted v2 schema change introduced by dep-6010; the two readings of the same origin are (i) the producer shipped a schema change without the consumer being upgraded — fix = revert/coordinate the producer, or (ii) the consumer is stale (v1) relative to an intended v2 rollout — fix = upgrade the settlement consumer. Both readings share the same origin and the same causal chain and are therefore ONE hypothesis; the open detail is which side is 'at fault' and the producer's exact identity.

**Causal chain**
1. order-service deploys v2.16.0 at 07:40:00Z, renaming OrderExecuted 'qty'→'quantity' and adding event schema version header v2; it is the only deployment anywhere in 06:00-09:59 and the only order-service change in the whole 2026-05-11→05-12 window [F2, F14, F23, F6]
2. order-service's sole event-emission channel is queue-produce to kafka ('orders'), so any v2 OrderExecuted it emits must traverse that single producer edge [F21, F20]
3. ~2 min later settlement-service hits a deserialize failure on orders-3@8841207 with exactly matching vocabulary: missing required field 'qty' (schema v1 expected, header says v2) [F7, F14, F26]
4. The undeserializable record is treated as a poison message and retried against the same fixed offset tens of thousands of times, blocking partition orders-3 [F8, F27]
5. Because the partition cannot advance, consumption collapses to a ~0.4 req/s floor while CPU stays ~70% busy-spinning on retries and HTTP 5xx stays flat [F10, F11, F12, F16]
6. Lag inflects at the 07:40 bucket and climbs every bucket thereafter to 60k+, matching 'no settlements posted' [F9, F13, F30]
