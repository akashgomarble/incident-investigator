# Incident investigation report: INC-008
*System: multi_agent | outcome: **inconclusive** | ended: critic_accepted*

## Summary
Login degradation on auth-service (p99 ~3.8s, 503s on /v1/auth/login) began in the 06:48-06:52Z bucket and persists through 08:59Z; the 503s are self-generated accept-queue overflows from auth-service itself. The best-supported hypothesis is H3, auth-service-local CPU saturation (CPU pinned ~97%, no external load or change driver), but at 0.46 confidence it is below the 0.50 bar for a root-cause verdict, so this report is inconclusive. The reporter's bcrypt-regression framing (H1) is falsified: auth-service had zero deployments in 2026-04-15→04-22 (F3, F16) and the only change anywhere in the window is a logging-verbosity config edit (F2, F15). The shared redis-cache branches (H2/H4) are strongly weakened by flat redis-cache resource/health metrics and a clean co-consumer (F26, F29, F31-F37, F44, F45), but H3's own driver (genuine surge vs retry feedback vs an unknown CPU-bound code path) remains unresolved.

**Inconclusive** -- the evidence does not single out one cause. See ranked hypotheses and data gaps.

### H3: Auth-service-local CPU saturation (pathological CPU-bound work in auth-service) with no external load or change driver
Something inside auth-service began consuming essentially all available CPU at 06:52Z, pinning cpu_pct at ~96-98% and starving request acceptance so the accept queue overflowed and auth-service self-generated 503s on POST /v1/auth/login, with p99 rising to ~3.8s. The driver is auth-service-local; it is NOT shared-cache degradation (redis-cache telemetry is flat and co-consumers are clean), NOT a new auth-service release (none exists), and the load rise is a consequence (retry/feedback), not a preceding cause. The exact nature of the CPU-bound work (hashing path, lock/queue spin, retry feedback loop) is unresolved.

**Causal chain**
1. At 06:48-06:52Z auth-service CPU steps from a 36-40% baseline to ~97% and stays pinned through 08:59Z; memory and restarts stay flat, so this is compute-bound, non-crashing saturation [F9, F11]
2. Latency rises in the same bucket: p99 goes from ~88-94ms to ~3.8s and stays there [F8]
3. The saturated CPU starves request acceptance, so the accept queue overflows and auth-service rejects its OWN requests with 'accept queue full, returning 503' (372 occurrences, first 06:55:42Z) [F10]
