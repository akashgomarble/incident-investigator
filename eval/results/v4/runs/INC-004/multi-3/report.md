# Incident investigation report: INC-004
*System: multi_agent | outcome: **root_cause_identified** | ended: critic_accepted*

## Summary
Root cause (confidence 0.72, medium): the unbounded in-memory template cache added by notification-service deployment dep-5402 (v3.8.0, deployed 2026-03-21T00:00Z) retains memory monotonically at flat load until the container limit is crossed, producing the ~24h OOM sawtooth. The decisive evidence is the timing discontinuity: the only obtainable 24h window immediately before the deploy is flat at ~48% with no ramp and no reset, and the +2.3%/h sawtooth begins only after the 00:00Z deploy, while request volume is statistically identical before and after (139.95 vs 140.24 req/s). The reporter's Kafka-replay story is refuted: the maintenance REDUCED retention (7d→3d), the memory curve shows no step at 18:00Z, memory was pinned at 93–98% for ~2h while lag was a normal 54 messages, and lag/error bursts follow the kill rather than precede it. Confidence is capped below high because no heap or cache metric exists for this service, so the retained object cannot be measured directly — the conclusion rests on the shape of memory_pct plus the deploy-boundary discontinuity, and the residual alternative is a generic in-process allocation rather than specifically the ConcurrentHashMap.

## Probable root cause
**Unbounded in-memory template cache in v3.8.0 leaks until OOM** -- bad_deployment in `notification-service`, triggered by `dep-5402` (confidence 0.72, medium)

### H1: Unbounded in-memory template cache in v3.8.0 leaks until OOM
notification-service deployment dep-5402 (v3.8.0) added an in-memory ConcurrentHashMap template cache keyed by template+locale+userSegment with no eviction. It grows monotonically at steady load, ramping memory ~+2.2-2.3%/hour from a ~48% baseline to 93-98%, OOMKilling the pod on a ~24h cadence (03-21T22:59Z, 03-22T21:59Z, 03-23T19:59Z). The two decisive discriminators now hold: (a) the full 24h immediately BEFORE dep-5402 is FLAT at ~48% with no ramp and no reset (F29), and the sawtooth ramp begins only in the 03-21T02:00Z bucket, AFTER the 00:00Z deploy (F29/F30); (b) workload is unchanged across the deploy — mean 139.95 req/s pre vs 140.24 req/s post, same diurnal shape (F34/F35/F36) — so growth is not volume-driven. Incident-day scoped config queries return count 0 (F31/F32/F38... F32), so no lowered memory limit / raised heap / batch / concurrency change can shrink the denominator or inflate the burst. The Kafka maintenance and its lag spike are coincidental; lag spikes are a CONSEQUENCE of the restart (consumer offline), not the driver of memory growth.

**Causal chain**
1. dep-5402 (v3.8.0) deploys an in-memory template cache with no eviction/bound; it is the only memory-affecting change in the window for this service [F1, F15, F3, F17, F33, F32, F31]
2. Memory behavior changes discontinuously at this deploy: the 24h before it is flat ~48% with no sawtooth, and the +2.3%/h ramp with resets starts only after 2026-03-21T00:00Z [F29, F30]

### H4: Generic in-process allocation growth in notification-service, not specifically the template cache
notification-service accumulates retained in-process memory at steady load (flat ~25% CPU, flat 55-65 lag, flat ~140 req/s) and crosses the container limit on a ~24h cadence. The ORIGIN is ambiguous between (a) the v3.8.0 template cache and (b) any other steady in-process allocation/leak. Because no heap/cache/cache-entry metric exists (F19, F24, F27), telemetry cannot name the retained object; the only discriminating evidence is the timing discontinuity at the deploy (F29/F30), which shortens the odds for a non-cache allocator but does not eliminate it (a JVM-level accumulation such as metaspace/native buffers, or a pre-03-20 allocator the retention wall hides). This hypothesis is NOT independently falsifiable with available data; it differs from H1 in mechanism label only, and would be closed by a heap dump rather than a different operational fix. Ranked as the residual alternative rather than a co-equal actionable origin.

- Memory and restart series are hard-truncated at 2026-03-20T00:00Z; no pre-deploy memory series older than the single 24h before dep-5402 exists, so a sawtooth pre-dating 03-20 cannot be tested.
- get_deployments for 2026-03-01..2026-03-16 returned count 0, so no pre-v3.8.0 baseline deployment could be compared.
- Kafka broker metrics (partition reassignment, segment deletion volume, per-partition lag) were never pulled, though kafka has_telemetry is true; the maintenance-burst story is refuted on direction and temporal order rather than on broker-side data.
- No message-volume / replayed-message-count metric and no cache hit/miss, eviction or template-render-count metric exist, so cache growth could not be tied to template+locale+userSegment cardinality and batch-consumption amplification could not be quantified.
- Cross-service fan-out was not completed: memory pressure, restarts and error spikes in kafka, order-service, payment-service, settlement-service and email-provider were not checked; queries against 'trade-service' and 'email-service' failed with unknown service.
- The final planned calls (notification-service cpu_pct/error_rate re-check and a WARN-level log scan) were not executed due to budget exhaustion, so lower-severity warning logs leading into each OOM remain unverified.
- Config-change tooling records only instrumented keys and exposes no manifest history, so a memory-limit edit made outside the config system cannot be fully excluded.
- memory_pct is a percentage with no absolute byte/limit denominator, so the +2.2%/h ramp could not be converted to MB/h to size the per-key cache cost.

## What would change this conclusion
- A memory series reaching before 2026-03-21T00:00Z showing the same ~24h sawtooth prior to dep-5402 (e.g. from a longer-retention store or an exported copy) would undercut H1 and point to a pre-existing/generic in-process leak (H4).
- A heap dump or profiler sample attributing the retained bytes to a source other than the ConcurrentHashMap template cache — e.g. metaspace, native buffers, or an unrelated allocator — would move the conclusion from H1 to H4 and change the fix from cache rollback to locating that allocator.
- Evidence that cache-key cardinality (template+locale+userSegment) does not grow with the memory ramp, or that memory grows even with the cache disabled, would falsify the specific cache mechanism.
- Discovery of a notification-service memory-limit or JVM/heap config change on the incident days outside the config tool (e.g. in a manifest history) would re-open the 'shrunk denominator' explanation and re-rank the origin.
- Broker-side data showing a large replay or rebalance coincident with — and preceding — the ramps would revive the maintenance-driven hypothesis (H2).
- A post-rollback 24h cycle that still shows the +2.3%/h monotonic ramp to OOM would refute H1 and prove the growth is independent of v3.8.0.
