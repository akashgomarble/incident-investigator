# Incident investigation report: INC-009
*System: multi_agent | outcome: **root_cause_identified** | ended: critic_accepted*

## Summary
The most likely root cause of INC-009 is the portfolio-service v4.5.0 deployment at 2026-05-05T08:56:00Z, whose new, unindexed query 'SELECT * FROM trades WHERE account_id=$1 AND executed_at > $2 ORDER BY executed_at' performs a 48.2M-row Seq Scan on the shared ledger-db instance, saturating its CPU/connections and starving order-service's INSERTs into statement-timeout failures (H1, confidence 0.72, medium). Onset is established at the 08:48–08:56Z bucket from four independent signals (order-service p99 and 5xx, ledger-db CPU/connections/slow_queries), and the DB-side slow-query population is 100% portfolio-service's Seq Scan with zero occurrences before 08:58:38Z; the only cleanly ordered pair is 08:58:38Z (first portfolio Seq Scan) → 09:00:42Z (first order-service statement timeout). The competing hypotheses are closed or contradicted: the DBA autovacuum change is excluded on mechanism and timing (autovacuum only ever touches audit_log; a 48–56 min flat gap after 08:00Z), no storage/host/maintenance event exists in the change inventory, and order-service's own resources were flat with its pool rising only with the latency jump. Confidence is held below high because two load-bearing sub-details remain assumptions rather than verified facts — that v4.5.0 introduced a genuinely new unindexed query (vs. a plan regression at the same instant) and whether the binding shared resource is CPU/IO or pooled connections — but both collapse to the same origin and the same fix family, so they cap confidence without creating a competing origin.

## Probable root cause
**portfolio-service v4.5.0's new unindexed trades query saturates shared ledger-db, starving order-service writes** -- bad_deployment in `portfolio-service`, triggered by `tc-006` (confidence 0.72, medium)

### H1: portfolio-service v4.5.0's new unindexed trades query saturates shared ledger-db, starving order-service writes
The portfolio-service v4.5.0 deployment at 2026-05-05T08:56:00Z introduced the query 'SELECT * FROM trades WHERE account_id=$1 AND executed_at > $2 ORDER BY executed_at' with no supporting index ('no migration included'). On the shared ledger-db instance this query performs a Seq Scan over 48.2M rows, driving ledger-db CPU ~30%->~96%, connections_active ~61->~190 and slow_queries ~1/min->~140/min. ledger-db is shared by four db callers, so order-service's INSERT INTO orders statements lose the CPU/IO (or pooled-connection) budget, exceed statement_timeout and fail, giving p99 ~5.4s and ~9.6% 5xx. The fault originates in the portfolio-service release, not in order-service or the DB config. NOTE: whether the fault is a genuinely new unindexed query or a pre-existing query whose plan regressed at the same moment is an open sub-detail (same origin, same fix family: add index / revert release); whether the binding shared resource is CPU/IO or pooled connections is likewise an open sub-detail (same origin, remediation shifts to pooler/limit tuning). Neither sub-detail changes the origin.

### H3: Storage/IOPS infrastructure degradation on the ledger-db host coinciding with (not caused by) the change window
The ledger-db host's underlying storage (cloud volume burst credits / IOPS) degraded independently, throttling I/O on the shared instance; the CPU, connection and slow-query saturation and order-service statement timeouts are downstream of that storage fault. HIST-110 (2026-01-15) had a near-identical symptom set (order latency + ledger-db statement timeouts).

**Causal chain**
1. Cloud volume burst credits on the ledger-db host are exhausted / IOPS throttled (no finding - pure lead from HIST-110 precedent). *(assumed)*
2. I/O throttling would slow the trades scan and order-service inserts, raising CPU/connections/slow queries from the 08:56Z bucket. This is consistent with the observed saturation. [F9]
3. order-service INSERT INTO orders statements hit statement_timeout, giving p99 ~5.4s and ~9.6% 5xx. [F11, F7, F8]
4. But no storage-tier event exists anywhere: the change inventory contains only the autovacuum config change and the portfolio deploy, with no IOPS provisioning change, disk resize, host/DB maintenance entry or storage-tier migration; ledger-db's dependency graph has no storage/host/volume node; and replication_lag_ms is flat ~39-43ms across the window. [F19, F20, F12]
5. More fundamentally, a storage fault is not needed: 100% of DB-side slow-query volume and the exact onset are attributable to one new portfolio-service Seq Scan appearing immediately after the deploy, with zero occurrences before it. [F10, F21, F22, F23, F42]

## What would change this conclusion
- Discovery that trades(account_id, executed_at) already had a usable index before 08:56Z, or evidence in the logs/catalog that the plan changed from Index Scan to Seq Scan at 08:56Z — this would shift the origin from 'v4.5.0 introduced a new unindexed query' to 'plan regression / lost index at the same moment' (same origin, same fix family, but would change the long-term prevention emphasis).
- Discovery that portfolio-service's trades query existed before v4.5.0 and was already Seq-Scanning at volume — this would break the causal link to the deploy and weaken H1 substantially.
- Evidence of a storage/host/infrastructure event on the ledger-db host (IOPS throttling, volume burst-credit exhaustion, disk-latency spike, or a maintenance entry outside the deployment/config APIs) at the 08:48-08:56Z onset — this would revive H3 and could displace H1 as the origin.
- A ledger-db autovacuum, lock, or bloat event on the trades table at 08:56-08:58Z (or slowing of queries on trades concurrent with vacuum runs) — this would revive H2 and contradict the log-based closure.
- Evidence that order-service's own CPU, memory, restarts, thread pool or a pre-onset db_pool saturation degraded BEFORE the 08:45-08:56Z bucket — this would revive H4 and make order-service a contributor rather than a pure victim.
- Confirmation that order-service writes and portfolio-service reads do NOT contend on the same ledger-db budget (e.g. separate instances, a pooler isolating them, or writes going to a different node) — this would break the second load-bearing hop of H1 and require re-attributing the order-service timeouts.
- Confirmation of a pooler in front of ledger-db plus a known max_connections much lower than ~199 — this would move the binding resource from CPU/IO to connections and shift remediation toward pooler/limit tuning (origin and primary fix unchanged).
- Any evidence that the order-service statement timeouts are client-side (connection-timeout/pool-exhaustion errors of the HIST-115 type) rather than server-side CPU/IO starvation — this would change the mechanism attribution and the remediation.
- Evidence that payment-service and/or settlement-service show the same onset with error rates, or that portfolio-service's 5xx also rose — this would widen the measured blast radius and further support the shared-ledger-db saturation mechanism.
