# Incident investigation report: INC-009
*System: multi_agent | outcome: **root_cause_identified** | ended: critic_accepted*

## Summary
Root cause: the portfolio-service v4.5.0 deploy dep-5905 (2026-05-05T08:56:00Z) introduced an unindexed query on the shared ledger-db node — SELECT * FROM trades WHERE account_id=$n AND executed_at > $n ORDER BY executed_at — which runs as a Seq Scan over ~48.2M rows, saturating the shared ledger-db node. Per-minute telemetry shows ledger-db CPU 32%->96%, slow_queries 1.3->139/min and connections_active 60->185 all turning in a single minute at 08:58Z, with the first Seq Scan log at 08:58:38Z attributed to application_name=portfolio-service and no 'trades' fingerprint anywhere in the preceding 30+ hours. order-service (a co-tenant on the same node) then had its write path starved: db_pool_in_use stepped 14.18->45.07 and p99 148ms->5607ms simultaneously at 08:59Z, and 284 'canceling statement due to statement timeout (INSERT INTO orders)' errors began at 09:00:42Z. Confidence is medium (~0.72 after critic review): the top hypothesis is clearly ahead of the rejected alternatives, which were positively weakened (autovacuum cfg-2903 on five independent signals; the connection-storm and order-service-local-retry hypotheses on simultaneity/ordering), but three mechanism details remain assumption-borne rather than measured. Immediate mitigation is to revert dep-5905 / add the supporting index on trades.

## Probable root cause
**portfolio-service deploy dep-5905 added an unindexed ~48M-row Seq Scan on shared ledger-db, saturating the node; order-service's write path (INSERTs through its DB pool) is the only client exposed to the resulting statement timeouts** -- bad_deployment in `portfolio-service`, triggered by `dep-5905` (confidence 0.68, medium)

### H1: portfolio-service deploy dep-5905 added an unindexed ~48M-row Seq Scan on shared ledger-db, saturating the node; order-service's write path (INSERTs through its DB pool) is the only client exposed to the resulting statement timeouts
The portfolio-service v4.5.0 release (dep-5905, 08:56:00Z) introduced 'SELECT * FROM trades WHERE account_id=$n AND executed_at > $n ORDER BY executed_at' with no supporting index ('no migration included'). On the shared ledger-db node this runs as a Seq Scan over trades (~48.2M rows). Per-minute telemetry shows a single-minute transition at 08:58Z — CPU 32->96%, slow_queries 1.3->139/min, connections_active 60->185 — with the first Seq Scan log at 08:58:38 attributed to application_name=portfolio-service, and no 'trades' or 'portfolio-service' slow-query log anywhere in the preceding 30+ hours. The node saturation then causes order-service's INSERT INTO orders statements to be cancelled by statement timeout (284 ERRORs from 09:00:42), with p99 going ~150ms -> ~5.3s. The critic's scope objection is addressed by the post-revision pool evidence: order-service's db_pool_in_use steps 14.18 -> 45.07 in the same minute (08:59) that p99 goes 148ms -> 5607ms (F42, F43), i.e. order-service's write connections are held/blocked and its pool triples, while payment- and settlement-service show flat p99/error_rate/ERROR logs (F31, F32, F33) — they are not blocked because they are not issuing the cancelled write class on the saturated node during this window, and their latency budget/metrics differ. The mechanism is shared-node resource starvation, but the visible blast radius is asymmetric because only order-service's workload class (INSERT INTO orders under a statement_timeout) gets cancelled on this node.

### H5: order-service-local connection-pool exhaustion (self-inflicted), with ledger-db saturation as a co-occurring but non-originating condition
The origin is order-service's own connection handling rather than any change: its DB pool is exhausted in-place (db_pool_in_use 14 -> 45+ in one minute at 08:59, sustained), and the resulting queueing produces the p99 >5s and the INSERT statement timeouts. On this reading ledger-db's 08:58 CPU/slow-query/connection saturation is a neighbouring condition rather than the cause of order-service's failures. This hypothesis is kept as the genuine order-service-local competing origin and explains why only order-service was impaired while the other three ledger-db co-tenants were flat (F31, F32, F33) — if order-service alone saturated its own pool, no other co-tenant would be touched.

4. Order-service has no pool_size / queue-depth / pool-wait metric, so true exhaustion (cap reached) versus elevated-but-healthy occupancy cannot be proven numerically; ledger-db connections_active is simultaneously at 185. [F40, F19, F10]
5. Requests then hit the statement timeout on INSERT INTO orders, surfacing as p99 >5s. [F12, F9]

### H2: DBA autovacuum config change cfg-2903 on ledger-db triggered vacuum bloat/contention that degraded queries (reporter's suspicion)
The dba-team config change cfg-2903 (autovacuum_vacuum_scale_factor 0.2 -> 0.1 at 08:00:00Z, 'More aggressive autovacuum') caused more frequent/aggressive autovacuum runs on ledger-db, and the added vacuum CPU/IO saturated the node, raising query latency and causing order-service statement timeouts.

**Causal chain**
1. cfg-2903 lowers autovacuum_vacuum_scale_factor 0.2 -> 0.1 at 08:00:00Z on ledger-db, making autovacuum more aggressive. [F1, F13]
2. More aggressive autovacuum runs earlier/more often, consuming CPU and IO on the node. *(assumed)*
3. The vacuum-induced CPU/IO contention saturates the node, raising slow_queries and connection wait times. *(assumed)*
4. Shared-node contention then starves order-service INSERTs, producing statement timeouts and p99 degradation. [F4, F12, F9]
