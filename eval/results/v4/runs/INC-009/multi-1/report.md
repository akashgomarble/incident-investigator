# Incident investigation report: INC-009
*System: multi_agent | outcome: **root_cause_identified** | ended: critic_accepted*

## Summary
Root cause (confidence 0.62, medium): portfolio-service v4.5.0 (dep-5905, deployed 08:56Z) added an unindexed query on trades filtered by account_id + executed_at with no accompanying migration; that query drives sequential scans of a ~48M-row trades table on the shared ledger-db, pinning the DB host at ~96% CPU, tripling connections and lifting slow queries from ~1/min to ~140/min, which in turn causes order-service's INSERT INTO orders to exceed its statement timeout (p99 ~5s, error rate ~9%). The alternative hypotheses are actively contradicted rather than merely unproven: the 08:00Z autovacuum config change (cfg-2903) showed zero effect for 55 minutes and no vacuum log lines in the onset window, order-service's own CPU/memory/request-rate are flat with only DB statement-timeout errors, and disk_used_pct and replication_lag_ms are flat across onset, ruling out IOPS throttling/disk pressure. Confidence is capped because the micro-mechanism (unindexed, high-volume, live request path) is supported by a logged seq-scan slow query plus the HIST-111 precedent rather than by index/EXPLAIN/pg_stat evidence, which no available tool can provide.

## Probable root cause
**portfolio-service v4.5.0 unindexed query on trades drives ledger-db CPU/connection saturation** -- bad_deployment in `portfolio-service`, triggered by `dep-5905` (confidence 0.62, medium)
