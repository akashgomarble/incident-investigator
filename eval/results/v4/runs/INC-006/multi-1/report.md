# Incident investigation report: INC-006
*System: multi_agent | outcome: **inconclusive** | ended: critic_inconclusive*

## Summary
Quote latency degraded sharply at ~13:20Z: pricing-engine p99 stepped from ~60ms to ~1370ms and market-data-service (its upstream data provider) from ~40ms to ~1161ms, both in the same 2-minute bucket, with the only error signature being "quote computation deadline exceeded: market-data-service took <n>ms". At 13:22:10Z redis-cache's primary (redis-cache-2) failed health checks and an empty, resyncing replica (redis-cache-3) was promoted, with hit ratio collapsing 95.9%→10.8% and memory 71%→6%, and market-data-service's first "cache miss storm ... rebuilding from exchange feed snapshot" WARN followed 15s later at 13:22:25Z. That makes a cold-cache miss storm (H1, best-supported at 0.50) the leading story, but the alternative that market-data-service's CPU saturation is an intrinsic compute fault with the redis failover merely co-occurring (H2, 0.45) is not contradicted by any measurement: its CPU stepped while request_rate (~956 req/s) and memory were flat, with zero restarts and zero ERROR logs, and the decisive discriminator (CPU burn proportional to redis miss volume vs pinned independent of redis state) was never measured. Because the ranking cannot be separated with the available evidence, the outcome is inconclusive; treat redis-cache and market-data-service as the two candidate origins with different fixes.

## Probable root cause
**Inconclusive** -- the evidence does not single out one cause. See ranked hypotheses and data gaps.

### H1: redis-cache primary failure promoting an empty replica -> cold-cache miss storm -> market-data-service CPU-bound rebuilds -> pricing-engine deadline-exceeded
redis-cache's primary node (redis-cache-2) failed health checks (3 consecutive PING timeouts) and failover promoted a resyncing, EMPTY replica (redis-cache-3) at 13:22:10Z. The new primary had essentially no dataset: hit ratio collapsed ~96% -> ~11% and memory fell 71% -> 6%. Every quote lookup therefore became a miss, forcing market-data-service to rebuild quotes from the exchange feed snapshot - a CPU-bound read path - which saturated market-data-service CPU (42-46% -> 67-94%) and pushed its p99 from ~40ms to ~1161-1910ms. pricing-engine, which synchronously calls market-data-service, blocked and surfaced 'quote computation deadline exceeded: market-data-service took <n>ms'. redis-cache's own CPU and evictions were flat, so this was a dataset-loss/topology event, not redis resource saturation. Confidence is capped because the causal direction between the failover and market-data-service's CPU step is bracketed (2-min buckets) not ordered, and the cross-cutting blast radius that a cold-cache storm predicts is not observed on other redis consumers.

**Causal chain**
1. redis-cache-2 primary fails health check (3 consecutive PING timeouts); failover promotes replica redis-cache-3, whose dataset is EMPTY (replica was resyncing) [F26, F27]
2. New primary's memory drops 71% -> 6% and hit ratio collapses ~96% -> 10.8% within the 13:20-13:22Z buckets; clients drop 313 -> ~40 then reconnect in storms [F25, F29, F28]
3. This is not eviction/CPU pressure: redis evictions_per_min and cpu_pct are flat, so dataset loss (failover), not saturation, is the mechanism [F30, F22]

### H2: market-data-service self-inflicted CPU-saturation compute fault as the origin, with the redis failover a co-occurring symptom

Under this reading the fix targets market-data-service (scale it / fix its compute), not redis-cache. The critic is correct that no measurement contradicts it: the only thing that had distinguished H1 was the ordering, which is bracketed not proven, plus the self-authored WARN text.
