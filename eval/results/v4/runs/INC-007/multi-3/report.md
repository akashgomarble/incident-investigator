# Incident investigation report: INC-007
*System: multi_agent | outcome: **inconclusive** | ended: critic_inconclusive*

## Summary
At 14:00–14:02Z auth-service error rate stepped from ~0.2% to a flat ~36% and stayed there for ~2h, with one upstream api-gateway 5xx step (~21%), no load/latency/resource change in auth-service, and no co-degradation of any other service. The change set bracketing onset is exactly two auth-service changes one minute apart: deploy dep-5710 (auth-service v7.3.0, jjwt 0.12 parser + TokenValidator rewrite) at 14:00:00Z and config cfg-2705 (jwt.signing.key_id k-2025-10 -> k-2026-04) at 14:01:00Z. H1 (bad deployment, 0.40) and H2 (signing-key rotation, 0.40) are both well-grounded, both co-located with the 2-minute-resolution onset, name different origins with different fixes, and each rests on one unverified pivotal hop ('parser rejects a subset' vs 'old key no longer resolves') that no available tool can test — no per-kid/audience/per-replica metric exists, auth-service logs are 503, and no JWKS/key-store publish state or TTL/grace config is retrievable. H3 (shared redis-cache) and H4 (client-side) are contradicted by verified telemetry, and api-gateway is ruled out as the origin. Outcome is therefore inconclusive, with the trigger firmly localized to one of auth-service's two changes but not separable from retrievable data.

## Probable root cause
**Inconclusive** -- the evidence does not single out one cause. See ranked hypotheses and data gaps.

### H1: auth-service v7.3.0 (jjwt 0.12 parser rewrite) rejects a subset of otherwise-valid tokens
The 14:00Z deploy dep-5710 of auth-service v7.3.0 rewrote TokenValidator and moved from jjwt 0.11 to the breaking 0.12 parser API. The new parser behaves differently on a class of tokens (stricter claim/header parsing, changed clock-skew default as in HIST-109), so ~36% of validations return invalid_token immediately while the rest pass. Nothing was rolled back, so the step persists flat for 2h.

**Causal chain**
1. dep-5710 deploys auth-service v7.3.0 at 14:00:00Z with 'jjwt 0.11 -> 0.12 (breaking parser API)' and 'TokenValidator rewritten', status live, not rolled back [F1, F13]
2. The rewritten parser rejects a subset of otherwise-valid tokens as invalid_token (mechanism assumed; a uniform parser break would give ~100%, not ~36%) *(assumed)*
3. auth-service error_rate steps instantly from 0.21% (14:00Z bucket) through 18.12% (14:01Z bucket) to 37.28% (14:03Z bucket) and stays flat ~36% for ~2h [F7, F8, F33]
4. Failures are returned fast, not timed out: request_rate flat ~395-410 req/s, p99 ~87-92ms, CPU ~38%, memory ~52%, rate-limited ~2/min, pod restarts 0 [F9, F10, F12, F32]
5. api-gateway, auth's only caller, steps to ~21% sustained 5xx in the matching bucket; other gateway downstreams (order-service) stay flat, so the fault is confined to auth-calling traffic [F11, F16, F34, F35]

## Data gaps
- No per-kid/issuer/audience or per-endpoint breakdown of the ~36% invalid_token 401s exists or was retrievable (available auth-service metrics are aggregate only; error_rate_by_kid and error_rate_by_endpoint both returned 'has no metric'), so the failing population cannot be matched to a token class.
- No pod/instance-level or version/build label metrics exist for auth-service, so partial rollout of v7.3.0 versus a token-class subset cannot be distinguished; restarts are flat at 0, which neither shows nor excludes a subset of stale replicas.
- auth-service logs were unretrievable throughout (query_logs returned 'backend unavailable (503)'), so no log-level error signature (which validation step, key id, audience) could corroborate either hypothesis.
- No tool returns JWKS/key-store publish state, key last-loaded or publish timestamps, or token TTL/overlap/grace configuration, and the dependency graph contains no key-store/JWKS node — so whether k-2025-10 still resolves after 14:01Z (H2's pivotal hop) and what fraction of in-flight tokens carry it are undetermined.
- The auth-service deployment query for 2026-04-01–2026-04-15 returned budget_exhausted, so any earlier auth-service deploy that could bear on validation behaviour is unverified.
- redis-cache and user-db were never queried for deployments/config changes (only api-gateway was checked back to 2026-04-14), and nothing was queried before 2026-04-14, so a change to a shared component or an earlier secret-store change could exist outside the queried windows.
- redis-cache exposes no error_rate/request_rate metric and its cpu_pct/memory_pct for 13:00-14:30Z were not executed (budget_exhausted); sibling-service latency was also not executed — though hit ratio, clients and evictions were verified flat.
- Rollout/apply scope of cfg-2705 is known only at service granularity; no per-pod/per-instance config-apply telemetry exists to confirm atomic fleet-wide application versus propagation lag.

## What would change this conclusion
- A per-kid or per-issuer breakdown of the failing 401s showing failures concentrated on tokens carrying k-2025-10 would confirm H2 (key rotation) and exonerate dep-5710.
- A per-replica/version breakdown showing failures clustered on v7.3.0 replicas, or a rollback of dep-5710 clearing the error rate, would confirm H1 (bad deployment).
- Evidence that k-2025-10 still resolves and is published after 14:01Z (JWKS publish state / key last-loaded timestamp) would refute H2's pivotal hop and shift the conclusion to H1.
- Any additional deploy or config change on auth-service or a shared component (cache, DB, key store, secret store) within the 13:30-14:30Z window, or an auth-service deploy earlier in the two-week window, would reopen the origin question.
- Auth-service logs showing the specific validation error (parser/claim rejection vs unresolved key id) would directly discriminate H1 from H2.
- Restoring cfg-2705 to k-2025-10 without touching dep-5710 and observing the error rate clear (H2) or persist (H1) would be decisive.
- Evidence that redis-cache or another shared component degraded at 14:02Z (e.g. connection errors) or that sibling consumers co-degraded would revive H3, though current telemetry contradicts this.
- Findings that the 401s are actually generated by a client-side or caller/audience subset with no auth-side cause would revive H4, but the matched onset at auth-service and flat order-service make this unlikely.
