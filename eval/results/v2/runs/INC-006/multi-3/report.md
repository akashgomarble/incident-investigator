# Incident investigation report: INC-006
*System: multi_agent | outcome: **root_cause_identified** | ended: critic_accepted*

## Summary
The incident is a redis-cache availability failure, not a pricing-engine defect or a change-driven regression: at 13:22:10 redis-cache-2 failed three consecutive PING timeouts and was marked down, and at 13:22:52 the failover promoted redis-cache-3, which was still resyncing and therefore EMPTY. The resulting cache-wide read-side collapse (hit ratio 95.9%->10.82%, dataset memory 70.54%->6.38%, connected_clients 304->40, with evictions flat) forced market-data-service to rebuild quote entries from the exchange feed (cache-miss storm at 13:22:25, CPU stepping to ~90% at flat inbound request rate), and pricing-engine's synchronous market-data call then breached its computation deadline from 13:23:57, surfacing 2-3s quote loads. Confidence in this as the root cause is high (0.75, critic-accepted): the two alternative origins are contradicted by their own telemetry (exchange feed hop flat throughout onset; no load/retry spike) and the change set is empty in the causal window (the only deployment, dep-5604, is ~108 min early and on the unrelated auth path). Residual uncertainty is limited to why redis-cache-2 died and to sub-bucket ordering, which caps but does not overturn the conclusion.

## Probable root cause
**redis-cache primary node failure with failover to an EMPTY, under-resynced replica wipes the shared quote cache, forcing market-data-service rebuilds that blow pricing-engine deadlines** -- infrastructure_failure in `redis-cache`, triggered by `null` (confidence 0.75, high)

### H1: redis-cache primary node failure with failover to an EMPTY, under-resynced replica wipes the shared quote cache, forcing market-data-service rebuilds that blow pricing-engine deadlines
At 13:22:10 redis-cache's primary (redis-cache-2) failed three consecutive PING timeouts and was marked down; at 13:22:52 the failover promoted replica redis-cache-3, whose dataset was EMPTY because it was still resyncing. Keyspace hit-ratio collapsed from ~95.9% (13:20 bucket) to 10.82% (13:22 bucket) and dataset memory dropped 70.54%->6.38% — reads now miss cache-wide. market-data-service, which serves quotes from redis-cache, logged a cache-miss storm from 13:22:25 and its p99 (already stepping at 13:18) climbed to 665-1908ms as it rebuilt quote entries from the exchange feed snapshot, driving its CPU from ~45% to ~90% (work signature, not inbound load: request_rate flat at ~950 req/s). pricing-engine, which calls market-data-service synchronously, breached its computation deadline from 13:23:57 and surfaced 2-3s quote loads. Origin is the redis-cache failover to an empty replica — not pricing-engine code/config and not a change-driven event.

### H2: External exchange feed / exchange-gateway degradation slowed market-data-service quote rebuilds and cascaded into pricing-engine deadlines
The origin is outside the platform: the external exchange-api (vendor-owned, has_telemetry:false) or exchange-gateway degraded around 13:1xZ, so market-data-service's exchange-feed snapshot fetch became slow. Because cache misses are served by rebuilding from that feed, each rebuild took hundreds of ms to seconds, pricing-engine's synchronous call breached its deadline, and trading screens showed 2-3s quotes.

**Causal chain**
1. External exchange-api / exchange-gateway latency rises at ~13:1xZ *(assumed)*
2. market-data-service rebuilds quote entries from the exchange feed snapshot on cache miss, and that fetch is now slow [F10]
3. market-data-service p99 steps to 665-1908ms beginning in the 13:18 bucket [F11]
4. pricing-engine's market-data-service call breaches the quote computation deadline from 13:23:57 [F9]

## What would change this conclusion
- Evidence that the price-path keys were NEVER written by market-data-service (a write-side failure) rather than removed by the empty-replica failover - e.g. equivalent hit-ratio/miss behaviour on a peer redis instance serving the same keys, or a write-rate metric showing MDS stopped setting keys before 13:22 - would move the root cause to market-data-service's write path rather than the redis failover.
- A redis-cache log/metric showing disk full, an admin FLUSHALL, key expiry or an eviction storm at ~13:22 (instead of the '3 consecutive PING timeouts' + 'empty replica was resyncing' lines) would replace the failover-to-empty-replica mechanism with a different cache-loss cause and change the fix.
- Direct evidence of exchange-api-side degradation (a feed latency/error spike or snapshot-fetch failures that exchange-gateway's upstream_latency_ms does not capture) coinciding with onset would revive the external-feed hypothesis and redirect remediation to the vendor feed rather than redis-cache.
- A traffic/retry step on market-data-service's own request rate or connection pool (hidden because a request_rate query returned budget_exhausted and pool metrics do not exist) coinciding with 13:18-13:22 would revive the capacity-saturation hypothesis and point to rate-limiting/scaling instead of cache recovery.
- A deployment or config change inside the 12:00-15:00Z window (ruled out only because the change stores returned count 0 with partial:false, and one shard was unavailable in an earlier query) would reopen the change-driven hypothesis, particularly if it touched redis-cache, market-data-service or pricing-engine.
- Proof that redis-cache served all reads correctly through 13:22 (e.g. a redis-side latency metric showing normal service while MDS reported misses) would break the causal ordering and imply the misses originated on the market-data-service side.
