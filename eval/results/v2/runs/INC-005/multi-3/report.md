# Incident investigation report: INC-005
*System: multi_agent | outcome: **root_cause_identified** | ended: critic_accepted*

## Summary
Payment-service's own mTLS client certificate (CN=payments-client.orangeinvest.internal) for the bank-partner-api edge expired at 2026-04-02T12:15:00Z; every outbound fund-transfer call is now rejected at the TLS handshake with peer alert 45 (certificate_expired), so transfers are parked as PENDING_RETRY and ~97% fail (F7-F10, F28-F30). The HTTP error-rate panel stays green because it only counts HTTP 5xx and never observes the async bank-call path (F11). This is an internal credential-expiry incident with no recorded rotation or credential change in the prior 7 days (F19) and no relevant deployment (F2/F20); the latent cause is missing/failed renewal automation for a payment-service-scoped credential (F13/F17/F23). Alternative hypotheses — partner-side TLS/outage (H2), the bank API timeout config change cfg-2502 (H3), settlement-service v1.9.0 (H4) and a client-app release (H5) — are contradicted on mechanism and/or timing (F12, F14/F18, F26/F27). Confidence: medium (0.72), capped by the critic because the notAfter value is corroborated from application/cert-watcher logs rather than an authoritative credential-store record.

## Probable root cause
**Expired mTLS client certificate on payment-service's bank call** -- credential_expiry in `payment-service (client certificate CN=payments-client.orangeinvest.internal for the bank-partner-api mTLS edge)`, triggered by `null` (confidence 0.72, medium)

### H1: Expired mTLS client certificate on payment-service's bank call
payment-service's own mTLS client certificate (CN=payments-client.orangeinvest.internal) expired at 2026-04-02T12:15:00Z with no renewal automation and no recorded rotation. Every outbound fund-transfer call to bank-partner-api is rejected at the TLS handshake (peer alert 45, certificate_expired, raised against OUR client cert), so transfers are parked as PENDING_RETRY and ~97% fail, while the HTTP 5xx-only error_rate panel stays green because the async bank-call path is not counted. The latent cause is the missing/failed internal renewal of a payment-service-scoped credential, not a client-app or bank-side fault.

**Causal chain**
1. payment-service's client cert for the bank-partner-api edge reaches notAfter=2026-04-02T12:15:00Z with no renewal and no recorded credential change in the prior 7 days [F8, F19, F20, F30, F13]
2. A local cert-watcher already named that same client cert expiring in 25 minutes at 11:50:26Z, 25 min before expiry and ~25 min before any failure — the earliest credential-specific line [F30]
3. At 12:15:00Z the certificate expires; the receiving peer rejects the handshake and returns TLS alert 45 (certificate_expired), logged by payment-service as a remote error against our client cert CN [F8, F29, F28]
4. First customer-visible failure 27s after expiry at 12:15:27Z ('marked PENDING_RETRY: mTLS handshake with bank-partner-api rejected'), with no earlier error anywhere in 11:00-13:59 [F7]
5. Failure volume builds: 311 ERROR logs to 13:58:39Z, dominated by 171 'tls: expired certificate (alert 45)' and 140 PENDING_RETRY lines; no partner-side CN, trust-anchor or hostname-mismatch string appears in any log line [F8, F28]
6. Bank-facing metric confirms the outbound call is the failure: bank_api_error_rate rises from ~0.20% to 62.58% in the 12:12 bucket then flat 100% from 12:20 to 13:56 [F9]
7. Payment success rate collapses on the same onset, 99.17% -> 38.93% -> ~2.1-2.7%, matching ~40 tickets and far more [F10]
8. The HTTP error_rate panel (5xx-only, sync path) never moves (0.18-0.32% throughout), which is why the dashboard is green while payments fail [F11]
9. Timeout/pool/capacity mechanisms are excluded: p99 latency did not worsen (it fell) and db_pool_in_use stayed flat ~7.1-8.95, so this is a hard immediate rejection rather than saturation [F12]
10. The credential is scoped to payment-service only: bank-partner-api is external, has_telemetry:false, shared:false, and no other service has a bank-partner-api edge or a bank_api_error_rate metric; no other service shows a cert/TLS symptom [F21, F22, F25, F27]

- Evidence that the rejected certificate belonged to the partner side (a bank-side CN, trust-anchor or hostname-mismatch error in payment-service or partner logs), which would flip the owner to H2 and change remediation from internal reissue to vendor escalation.

- Evidence of the same TLS/expiry symptom on another service also calling bank-partner-api, which would widen the blast radius and imply a shared rather than payment-service-scoped credential.
