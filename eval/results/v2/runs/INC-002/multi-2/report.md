# Incident investigation report: INC-002
*System: multi_agent | outcome: **root_cause_identified** | ended: critic_accepted*

## Summary
The portfolio page timeouts (SEV-2, INC-002) were caused by the config change cfg-2207 at 2026-03-10T09:52:00Z, which cut portfolio-service's datasource db.pool.max_size from 50 to 5 ("cost-optimisation profile small"), starving the Hikari JDBC pool. Pre-change demand was ~11.6-12.3 concurrent connections; after the cut the pool pinned at exactly 5 active / 0 idle with 25-57 requests queued, so /v1/portfolio/holdings requests blocked on the 3000ms JDBC-acquire timeout, driving portfolio-service p99 from ~181ms to ~3.7s and error_rate to ~22%, which surfaced at the gateway as p99 ~4.3s and 504 upstream timeouts confined to that route. The reporter's suspicion (the 08:00Z gateway HTTP/2 upgrade) is falsified: gateway latency was flat 204-216ms for 1h52m after that deploy and stepped up in the same 09:52Z bucket as the pool cut, and ledger-db is demonstrably healthy with connections dropping rather than surging. Confidence 0.85 (high); the one residual caveat is that DB-slowness is excluded by inference, since no query-duration metric exists.

## Probable root cause
**portfolio-service DB connection pool cut to 5 (cfg-2207) starves the JDBC pool; gateway is just the symptom surface** -- config_change in `portfolio-service`, triggered by `cfg-2207` (confidence 0.85, high)

### H1: portfolio-service DB connection pool cut to 5 (cfg-2207) starves the JDBC pool; gateway is just the symptom surface
At 09:52Z an infra-automation cost-optimisation profile ('small') reduced portfolio-service's datasource db.pool.max_size from 50 to 5. In-use demand was ~11.6-12.3 connections in the preceding hour, i.e. well above the new cap. The pool pinned at exactly 5 active / 0 idle with 25-57 requests queued, so /v1/portfolio/holdings requests block on the Hikari acquire path up to the 3000ms JDBC-acquire timeout; portfolio-service p99 rises 181ms -> ~3.7s and error_rate 0.2% -> ~22%, and the added upstream wait pushes api-gateway p99 from ~206ms to ~4.3s with 504s confined to that route. Nothing is wrong at the gateway or the database; the pool cap is the binding constraint.

**Causal chain**
1. cfg-2207 at 09:52Z sets portfolio-service db.pool.max_size 50 -> 5 under a 'cost-optimisation profile small' [F2, F19]
2. portfolio-service's real demand for DB connections was ~11.6-12.3 in the preceding hour, i.e. above the new cap of 5 [F15]
3. Pool saturates at exactly 5 active / 0 idle with 25-57 waiters immediately after the cut (09:54Z onward) [F15, F10, F31]
4. Requests block on HikariPool acquire up to the 3000ms timeout (acquire timeout, not a query error); portfolio-service p99 jumps 181ms -> ~3.7s and error_rate 0.2% -> ~22% in the same 09:52Z bucket [F10, F14, F18, F30, F31, F32]
5. Gateway waits on portfolio-service, so its p99 rises ~206ms -> ~4.3s in the same 09:52Z bucket; ~96% of the added gateway latency is added at portfolio-service [F7, F13, F14, F17]
6. The database is not the constraint: ledger-db CPU flat, slow_queries flat, connections_active DROPPED 61.8 -> 54.5 at onset, so the 5-connection client cap is what starves requests [F16, F33, F34]
7. Users see 504s and a spinning portfolio page; gateway emits only 'upstream timeout portfolio-service GET /v1/portfolio/holdings' with no 5xx-from-upstream or connection-refused pattern [F9, F12, F8]
