# Incident investigation report: INC-004
*System: multi_agent | outcome: **root_cause_identified** | ended: critic_accepted*

## Summary
Root cause identified (H1, confidence 0.78, high): notification-service v3.8.0 (dep-5402, deployed 2026-03-21T00:00Z) introduced an unbounded in-memory TemplateCache whose entry counter climbs monotonically at ~9,000 entries/hour with evictions=0 on all 14 samples and resets only at process restarts, driving a sawtooth heap ramp that OOMKills the consumer roughly every 22 hours. The evidence chain is tight at every measurable hop: the ramp begins ~2026-03-21T01:40Z, ~1h40m after the deploy and ~2 days before the only config change, memory climbs ~+5-6%/hour to 95-98% and resets on each restart, and old-gen heap WARNs with 1.6-6.5s full GC pauses cluster in the final 85 minutes before the 19:59:21 OOMKilled. The on-call SRE's Kafka-replay theory (H3) is rejected: two of three OOMs and the ramp onset predate the 2026-03-23T18:00Z retention change by 1-2 days, lag spikes follow rather than lead each restart, throughput/CPU are flat, and settlement-service — a co-consumer of the same shared topic untouched by dep-5402 — is completely flat on memory, restarts, lag, CPU and logs. Residual uncertainty is secondary: no absolute MB/heap or cache-size metric exists, and H2 (high-cardinality userSegment keys vs. plain no-eviction growth) cannot be separated, but H2 shares H1's origin change, so the fix differs only in emphasis. Immediate mitigation is to roll back dep-5402 or bound the cache; the ~25-minute email delays will continue every ~22h until then.

## Probable root cause
**dep-5402's unbounded TemplateCache grows monotonically and OOMs the consumer** -- bad_deployment in `notification-service`, triggered by `dep-5402` (confidence 0.78, high)

### H1: dep-5402's unbounded TemplateCache grows monotonically and OOMs the consumer
notification-service v3.8.0 (dep-5402, 2026-03-21T00:00Z) added a ConcurrentHashMap TemplateCache keyed by template+locale+userSegment. The load-bearing hop is now no longer merely assumed: the cache's own counter rises monotonically at ~9,000 entries/hour with evictions=0 on every one of 14 samples, and it resets ONLY at restarts (never at a TTL/eviction), while old-gen heap warnings and 1.6-6.5s full GC pauses fire in the final 85 minutes before the 19:59:21 OOMKilled. Memory is flat ~48% until ~03-21T01:40 (~1h40m after the deploy), then ramps ~+5-6%/hour to ~97%, resets, and repeats as a perfect sawtooth. Consumer lag spikes occur in the same bucket AS each restart (post-restart catch-up), not leading into them, so lag is a consequence. Emails are delayed ~25 min while the consumer is down/rebuilding.

**Causal chain**
1. dep-5402 (v3.8.0, 2026-03-21T00:00Z) adds an in-memory TemplateCache keyed by template+locale+userSegment to email rendering [F1, F10, F12]
2. Cache entries accumulate monotonically with no eviction: counter climbs ~51,750 per ~5h45m (~9,000/hr), evictions=0 in all 14 samples [F34]
3. The counter resets only at restarts, never at a TTL/eviction boundary (196,650 immediately before each OOM, ~51,750 after), showing nothing ever reclaims the map [F35]
4. Old-gen heap crosses 90% and full GC pauses of 1,646-6,488 ms accumulate in the 85 min before the OOMKilled, i.e. cache growth drives heap pressure, not throughput [F36]
5. Memory is flat ~47-49% through 03-20 and until ~03-21T01:40, then ramps ~+5-6%/hour linearly to ~95-97% and resets to ~48% after each restart (sawtooth) [F15, F16]
6. The ramp onset (~1h40m after deploy) and the first two OOMKills (03-21T22:59, 03-22T21:59) all predate the only config change (Kafka retention, 03-23T18:00Z) by 1-2 days [F13, F14, F16, F11]
7. Pod hits the limit and is OOMKilled (exit 137) at 3 timestamps on the same pod, resetting memory and cache to baseline [F13, F14]
8. Each restart transiently stalls the consumer; consumer_lag spikes thousands of messages in the SAME bucket as the restart and returns to ~60 the next bucket, so lag follows rather than precedes the OOM [F17]
9. Throughput and CPU are flat (req/s ~131-151, cpu ~22-27%), so neither increased load nor CPU saturation drives the ramp [F18]
10. Emails delayed ~25 min while the consumer restarts/rebuilds, consistent with a queue-consumer email flow [F3]
11. settlement-service, a co-consumer of the same shared Kafka topic untouched by dep-5402, shows a completely flat memory baseline (44-56%, no sawtooth), zero restarts, no lag spike at the maintenance time, flat CPU, and no error logs — excluding a shared/Kafka-side origin [F26, F27, F28, F29, F30, F31, F32]

### H2: Cache growth is driven by unbounded/high-cardinality userSegment data rather than the cache code alone
Same origin as H1 (dep-5402 introduced the cache), but the specific failure driver is data: the userSegment part of the template+locale+userSegment key is effectively unbounded in live data, so the map explodes. This matters for the fix — bounding/validating the key space and purging bad data instead of removing the cache — but the change that introduced the fault is still dep-5402, so it is a variant reading of H1 rather than a competing origin.

**Causal chain**
1. dep-5402 introduces the cache keyed including userSegment [F10, F1]
2. Live userSegment values are high-cardinality/unbounded or unvalidated, so key space is effectively infinite *(assumed)*
3. Cache entries accumulate at ~9,000/hr with zero evictions, driving the same memory ramp [F34, F35, F15]

**Supporting evidence**
  - `F34` ✔ The TemplateCache counter rises monotonically and linearly at ~51,750 entries per ~5h45m (≈9,000/hour), and every one of the 14 samples in the window reports evictions=0: 51,750 (03-21T05:45) → 103,500 (11:30) → 155,250 (17:15) → 196,650 (21:51), then the same sequence 51,750 → 103,500 → 155,250 → 196,650 on 03-22, and 49,500 → 99,000 → 148,500 → 188,100 on 03-23.

## What would change this conclusion
- Evidence that the TemplateCache counter does not represent live retained entries — e.g. that evictions=0 is a reporting artifact and entries are in fact being evicted — which would break H1's load-bearing hop.
- Evidence of a kafka broker-maintenance/rebalance event on or before 2026-03-21T01:40Z that correlates with the ramp onset and affects the shared topic, which would revive H5.
- A demonstration that settlement-service (untouched co-consumer) is in fact affected similarly — e.g. a sub-2h memory or lag transient masked by 2h bucketing — which would indicate a shared Kafka-side cause rather than an application-specific one.
- Fine-grained memory/restart data for 2026-03-16..03-19 showing an identical ramp-and-restart pattern BEFORE dep-5402 landed, which would decouple the sawtooth from the deployment.
- A memory-limit change or node-level OOM/eviction signal showing the container's limit was reduced, which would support H6 (usage unchanged, line lowered) instead of behavioral growth.
- Per-key cardinality data showing the growth is driven by unbounded userSegment values from an external data source rather than by the cache code's lack of bounds — this would shift H1 toward H2 and change the remediation emphasis (bound/validate the key space and purge bad data).
- Cache/JVM heap metrics showing heap does NOT track the cache counter (e.g. stable heap with a rising counter), which would point to a different accumulator or to GC-pause-driven OOM.
