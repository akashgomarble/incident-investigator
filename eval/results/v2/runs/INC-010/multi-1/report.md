# Incident investigation report: INC-010
*System: multi_agent | outcome: **root_cause_identified** | ended: critic_accepted*

## Summary
Root cause: order-service deploy dep-6010 (v2.16.0, 07:40:01Z rollout-complete) renamed the OrderExecuted field 'qty'→'quantity' and began emitting a v2 schema header, which settlement-service's v1 deserializer cannot parse. The first v2 event it read failed to deserialize ('missing required field qty ... header says v2'), and the consumer has treated it as a poison message ever since — retrying orders-3@8841207 (92,490+ attempts, 'partition blocked') and never advancing the offset, so settlement posting collapsed to ~0.40 req/s and consumer lag climbed monotonically to ~61.6k starting at the sharp 07:42 boundary. Confidence is medium (0.70-0.80): the onset, error signature, and single-partition block are all directly observed, and every competing origin (poll-setting change cfg-3004, broker rebalance, upstream starvation) is directly contradicted by broker health, flat producer volume, and the unaffected sibling consumer notification-service. The one unverified hop — that dep-6010's v2 producer writes specifically to orders-3 and that offset 8841207 is its first v2-header record — cannot be closed because no per-partition offset/header metrics are exposed.

## Probable root cause
**order-service dep-6010 schema rename (qty→quantity, v2 header) breaks settlement-service deserializer** -- bad_deployment in `order-service`, triggered by `dep-6010` (confidence 0.70, medium)

### H1: order-service dep-6010 schema rename (qty→quantity, v2 header) breaks settlement-service deserializer
order-service deploy dep-6010 (v2.16.0, 07:40Z) renamed the OrderExecuted field 'qty' to 'quantity' and added an event schema version header v2. settlement-service's deserializer still expects schema v1 with required field 'qty', so the first v2 event it reads (orders-3@8841207 at 07:42:14) fails to deserialize; the consumer treats it as a poison message, retries forever, and blocks that one partition, so settlement posting drops to ~zero and lag grows monotonically. Because only settlement-service's consumer path consumes the affected event contract (notification-service, the broker's other consumer of a disjoint topic/partition set, is wholly unaffected), the break manifests as a settlement-path-only single-partition stall.

**Causal chain**
1. order-service deploys dep-6010 at 07:40Z, renaming OrderExecuted 'qty'->'quantity' and emitting a v2 schema header; rollout completes 07:40:01Z [F2, F32]
2. Its new v2 events reach the shared kafka broker 'orders' topic path that settlement-service consumes (both attached to the same broker/topic path); order-service keeps producing at normal rate, so v2 events keep arriving [F4, F5, F16, F17]
3. settlement-service deserializer (v1 contract) rejects the first v2 message at 07:42:14 with 'missing required field qty (schema v1 expected, header says v2)' [F10, F11, F14]
4. The failed message becomes a poison message repeatedly retried, blocking partition orders-3 at offset 8841207 [F10, F11, F29, F30]
5. Blocked partition stops offset advance: throughput falls to ~0.4 req/s and lag steps up and climbs monotonically, only on the settlement path [F8, F9, F30]
6. Retry loop burns CPU (~2.5x) with no DB/connection errors and no broker degradation, matching a busy deserialize/retry loop rather than DB or broker failure [F12, F13, F15, F18]
7. notification-service, the broker's other consumer, is wholly unaffected at 07:42 (flat lag, flat throughput, zero deserialize errors) — consistent with the schema break being scoped to the settlement-service consumer event contract [F24, F25, F26, F27, F28]

The one supporting precedent class (F6) matches a different incident pattern and is contradicted by direct broker health metrics here.

### H4: Upstream producer starved the consumer — genuinely little volume to post
order-service/upstream trade producers stopped or slowed output, so settlement-service had little to post and lag reflects a stuck offset rather than real backlog.

**Causal chain**
1. Upstream producers feed the shared kafka topic settlement-service consumes [F5]
2. Producer output drops, reducing available messages *(assumed)*
3. settlement posting falls and lag rises [F8, F9]

**Supporting evidence**
  - `F5` ✔ The shared kafka broker's upstream producers are order-service (queue-produce) and payment-service (queue-produce), and it has a second consumer, notification-service (queue-consume) — so order-service's 07:40Z schema-changing deploy and cfg-3004 both feed into the same shared broker/app-path as settlement-service.
**Contradicting evidence**
  - `F16` ✔ Broker inbound volume is flat across the onset — kafka messages_in_per_s stays ~2500-2590 msg/s in every bucket (07:36 avg 2533.56, 07:42 avg 2486.58, through 09:00 avg 2463.67, mean 2535.42) — so there is no drop in upstream trade volume coincident with onset.
  - `F17` ✔ order-service throughput was also flat through the window: request_rate is ~225-237 req/s in every bucket (07:36 avg 230.45, 07:42 avg 233.43, mean 230.58), so order-service kept producing at normal rate after its 07:40 deploy — it did not stop or slow producing, consistent with its new v2 events reaching the broker.
  - `F10` ✔ The consumer is actively retrying, not idle: first ERROR log is 07:42:14 ('failed to deserialize OrderExecuted at orders-3@8841207: missing required field 'qty' (schema v1 expected, header says v2)'), and errors continue through the latest data (last seen 09:58:31 'poison message: retrying orders-3@8841207 (attempt 61790), partition blocked'). Top patterns over 07:20-09:10 are deserialize failure (133) and poison-message retry (130).
  - `F9` ✔ Settlement throughput dropped to ~zero at the same 07:42 boundary: settlement-service request_rate was ~61-63 req/s through 07:36, then fell to avg 0.39 (max 0.41) at 07:42 and stayed ~0.40 req/s through 09:54. This is the moment settlement posting effectively stopped.
  - `F12` ✔ settlement-service resources: CPU rose roughly 2.5x at the same 07:42 boundary (from ~27-29% baseline to avg 68.52%, sustained ~70% through 09:54), consistent with a busy retry loop rather than an idle/stalled process. Meanwhile db_pool_in_use stayed flat at ~6 connections (min 5.21, max 6.78) for the whole window, with no DB-pool exhaustion.
**Rejected because:** Broker inbound volume is flat (~2500-2590 msg/s across onset, F16) and order-service request_rate is flat at ~225-237 req/s with no drop after its deploy (F17), so producers kept producing. The consumer is demonstrably busy retrying rather than idle (F10/F12: CPU 2.5x, 61790 retry attempts), and errors explicitly reference a received v2 message ('header says v2'), proving messages are arriving — the opposite of starvation.
