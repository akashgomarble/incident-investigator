# Incident investigation report: INC-010
*System: multi_agent | outcome: **root_cause_identified** | ended: critic_accepted*

## Summary
Settlements stopped because order-service v2.16.0 (dep-6010, deployed 07:40Z) changed the OrderExecuted event contract to schema v2 (rename qty->quantity, add venue), and settlement-service's v1 consumer could not deserialize the resulting message at offset orders-3@8841207; it then poison-looped that same offset with "partition blocked", so nothing was settled and consumer lag grew monotonically. The chain is fully grounded in verified observations (only deployment in window with exactly that payload change; first and only consumer ERROR is the v1/v2 parse failure naming missing field 'qty'; then a retry loop pinned to one offset; onset ordering matches). The reporter's suspected poll-settings change cfg-3004 (500->200 max.poll.records at 07:35Z) is coincident at most — it changes batch size, not message parsing, and cannot produce a schema-version parse error. Alternatives are contradicted by direct measurement: broker rebalance (under_replicated_partitions 0 at all buckets, steady ~2500 msg/s, cpu ~35%) and ledger-db/output degradation (flat db_pool_in_use ~6, flat latency_p99, zero 'db' ERROR lines). Confidence 0.75 (high) — capped because the single hop "offset 8841207 was produced by the v2 code path at/after 07:40Z" could not be closed with any available data source and remains a bounded assumption.

## Probable root cause
**order-service v2.16.0 emits OrderExecuted schema v2; settlement-service v1 consumer cannot parse it and poison-loops** -- bad_deployment in `order-service`, triggered by `dep-6010` (confidence 0.75, high)

### H1: order-service v2.16.0 emits OrderExecuted schema v2; settlement-service v1 consumer cannot parse it and poison-loops
The 07:40Z deployment dep-6010 of order-service v2.16.0 changed the OrderExecuted event contract (renamed qty->quantity, added venue, bumped event schema version header to v2) on the shared kafka topic. settlement-service's consumer, still on the v1 schema, fails deserialization on the first v2 message, then repeatedly retries the same offset, blocking the partition — so no settlements post and lag grows monotonically. The fault originates in the upstream producer's released contract change, not in the consumer's poll settings.

**Causal chain**
1. order-service v2.16.0 (dep-6010) deployed at 07:40Z with 'OrderExecuted event: rename qty->quantity', 'add venue', 'event schema version header v2'; status live, not rolled back. [F1, F13]
2. order-service continues producing normally (~230 req/s), so v2 OrderExecuted messages land on the shared kafka topic settlement-service consumes. [F12, F4, F15, F22]
3. Consumer lag jumps at onset (~07:32-07:40Z) from a ~40-65 baseline to avg 1137 (max 2544) and climbs to ~60k by 09:56Z; settlement throughput collapses from ~62 req/s to ~0.4 req/s (zero posted). [F7, F8]
4. Earliest ERROR 07:42:14Z: settlement-service cannot parse OrderExecuted — its schema is v1 while the message header says v2, missing required field 'qty' — on offset orders-3@8841207. This is a consumer-side parse failure, not a missing-message problem. [F9, F31, F32]
5. From 07:44:51Z the consumer poison-message-retries the same offset (tens of thousands of attempts, 'partition blocked'); all 409 ERROR lines are only these two patterns on the single offset 8841207, so later offsets never reach the parser. [F10, F33, F34, F36]
6. Ordering: the producer contract change (07:40Z) precedes the parse error (07:42:14Z); the poll-size change cannot produce a schema-version parse error. [F16, F3, F14, F11]
7. Offset orders-3@8841207 was produced by the v2 code path (not directly observed; deploy timestamp not emit time). *(assumed)*

No change on either application would then be the origin.

**Causal chain**
1. kafka is a shared (platform-owned) broker that settlement-service consumes from via queue-consume. [F4, F15]
2. A broker event (partition reassignment/maintenance) strips the consumer's assignment, halting consumption. *(assumed)*
3. Consumer lag grows monotonically and settlement throughput goes to ~0.4 req/s. [F7, F8]

## Data gaps
- The definitive link 'offset orders-3@8841207 was produced by the v2 code path at/after 07:40:00Z' could not be closed: no producer emit timestamp, no raw/deserialized payload, no kafka offset metric, and no schema-registry. This is the main reason confidence is capped at 0.75 rather than higher.
- No producer-side raw event body was retrievable: order-service logs contain zero lines matching 'quantity' or 'orders-3' over 04:00-09:59Z, so the literal v2 field name/header on the failing message rests on the consumer error text alone (F35).
- No schema-registry / topic-schema component or telemetry exists in this environment, so the registered schema version for OrderExecuted over time and any consumer compatibility-mode setting could not be read or ruled in/out as an alternative fault point (F19, F24).
- Kafka exposes only cpu_pct, messages_in_per_s and under_replicated_partitions — no partition-reassignment, rebalance, leader-election or consumer-group-state metrics. H3 (broker lost assignment / in-sync rebalance) can therefore only be excluded indirectly via under_replicated_partitions=0 and steady throughput, not by a direct signal (F25, F26, F27).
- No order-service ERROR-level logs were retrieved (only WARN), so it cannot be fully confirmed that the v2 producer emitted without errors — only that its traffic/rate is normal (F12, gaps).
- Onset-bucket telemetry for some signals (settlement-service error_rate, kafka WARN/leader-election logs, per-partition timestamp range for orders-3) was not captured due to tool-call budget exhaustion, so the onset window is bracketed by lag/throughput rather than by a direct per-partition signal.
- Because the partition is blocked at offset 8841207, no later offset on orders-3 was ever parsed, so the logs cannot distinguish 'only v2-header messages fail' from 'every subsequent offset fails' — the observed 100% failure is 213 repeats of one offset, not a sample of distinct messages.
- Deployment dep-6010 exposes only a single deployed_at timestamp (no rollout start vs completion), so the exact deploy window relative to the failing offset cannot be established from the deployment API.

## What would change this conclusion
- Evidence that offset orders-3@8841207 was produced BEFORE 2026-05-12T07:40:00Z (i.e. by pre-v2 code), which would break the causal link to dep-6010 and point back to a consumer-side or broker-side mechanism.
- A raw payload dump for offset 8841207 showing a v1-compatible body (field 'qty' present) or no v2 header, which would falsify the schema-mismatch mechanism and re-open H2 (poll settings) or other causes.
- A schema-registry record showing OrderExecuted was upgraded to v2 independently of dep-6010 (e.g. a registry-side compatibility-mode change), which would move the fault origin off the producer deploy.
- Direct broker evidence of a partition reassignment / rebalance / lost assignment in the 07:30-07:45Z window (e.g. a rebalance or consumer-group-state metric stepping, or leader-election WARN logs), which would revive H3 as the cause of the stall.

- A separate, previously unseen change (producer hotfix, topic config, or consumer deployment) in the 07:30-07:45Z window that also alters OrderExecuted message framing or parsing.
