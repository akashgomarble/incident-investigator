# Incident investigation report: INC-007
*System: multi_agent | outcome: **inconclusive** | ended: critic_inconclusive*

## Summary
The fault is confidently localized inside auth-service's own two-change window — deploy dep-5710 (v7.3.0, 14:00Z) and signing-key rotation cfg-2705 (14:01Z), both live and unrolled-back — with a clean, ramp-free error-rate step at exactly 14:02:00Z, while infra, traffic, resource and shared-dependency explanations are all excluded. But the origin cannot be separated between the two surviving hypotheses: H2 (key rotation before key material was fully effective, confidence 0.46) and H1 (jjwt 0.11→0.12 / TokenValidator rewrite, confidence 0.40) remain a near coin-flip, because the per-replica/per-pod dimensions, rollout fractions, and per-pod key-load fields that would discriminate them do not exist in this environment. Compounding this, the single quantitative anchor (the 36% error_rate) is labelled '% of requests (HTTP 5xx)' on both auth-service and api-gateway, while the reported symptom is 401 invalid_token (4xx), and no 4xx/status-class counter exists anywhere — so the link between the verified 5xx surge and the reported 401 surge is unverified. H3 (shared dependency) and H4/H5 are rejected on the evidence. Recommendation is a safe, reversible mitigation of the later change first, plus the specific discriminators (a 4xx/401 counter, per-pod version/key telemetry, log pipeline restoration) that would close the gap.

## Probable root cause
**Inconclusive** -- the evidence does not single out one cause. See ranked hypotheses and data gaps.

### H2: Scheduled signing-key rotation cfg-2705 (k-2025-10→k-2026-04) went live before key material was fully loaded
The security-automation key rotation at 14:01Z flipped jwt.signing.key_id to k-2026-04, but the corresponding key material/JWKS state was not uniformly effective across auth-service's validation path, so a stable fraction of otherwise-valid tokens fail as invalid_token. Origin is the key-material/config state. First fix: revert/hold the rotation (point key_id back to k-2025-10, or dual-publish both keys) rather than roll back the deploy. Nudged slightly above H1 because it is the later of the two changes (closer to the 14:02Z onset), requires no pod restart (consistent with F17 restarts=0), and is the one change whose prior near-identical incident (HIST-108) presented the exact same symptom.

**Causal chain**

2. The new key id becomes effective before all validation paths hold the matching key material, so a fraction of valid tokens (e.g. those signed under the other key version) fail validation. *(assumed)*
3. The resulting invalid_token fraction steps abruptly at 14:02Z — exactly 1 minute after the rotation and 2 minutes after the deploy — with no ramp. [F28, F29]
4. No revert of the rotation occurred, so the plateau persists ~1h55m. [F15, F22]

### H1: auth-service deploy dep-5710 (jjwt 0.11→0.12 breaking parser API + TokenValidator rewrite) rejects valid tokens

Origin is the newly deployed code. First fix: roll back dep-5710. Held just below H2: it is the earlier of the two changes (2 minutes before onset vs 1), and a parser/validator code change would normally be accompanied by pod restarts, yet restarts are 0 across the window (F17) — an observation that mildly disfavours a code-rollout mechanism and mildly favours a restart-free config change.

## What would change this conclusion
- A reduction in the auth-service error_rate immediately after reverting/holding cfg-2705 (or dual-publishing both keys) would confirm H2 as the origin; failure to improve would shift the conclusion to H1 (dep-5710) and make the deploy rollback the correct fix.
