## Summary
The origin of INC-007 is well-bounded to the auth-service change pair at 14:00–14:01Z but cannot be narrowed further: H1 (dep-5710, jjwt 0.11→0.12 validator rewrite, 14:00:00Z, confidence 0.40), H2 (cfg-2705 signing-key rotation k-2025-10→k-2026-04, 14:01:00Z, 0.38) and H6 (their interaction, 0.22) all name an origin in the same auth-service change window, all lie 1–2 minutes before the 14:02Z error step, and all predict the same observables — a single clean step to a stable ~36% fast-401 plateau with flat request_rate, CPU, memory and latency, zero restarts, and ~21% propagated to api-gateway. The evidence needed to separate them is structurally unavailable, not merely unqueried: error_rate has no per-instance/replica/AZ label, no route or endpoint label exists on any service, dep-5710's record carries no rollout/replica fields, no JWKS/key-publish artifact or key-store service exists in the registry, and auth-service logs are unsearchable due to the identity-namespace pipeline outage. The remaining alternatives are properly retired — H3 (shared redis-cache) is excluded on change evidence and mechanism, H4 has no TTL/skew artifact and the failure does not decay, H5 has no positive evidence, H7 is contradicted by flat latency/CPU/memory and zero restarts. Because the three live hypotheses imply materially different fixes (roll back dep-5710 vs re-publish/accept both key ids), reporting a root cause at ~40% confidence would be a coin flip and is not shippable; the honest verdict is inconclusive with a safe mitigation that covers the whole change window.

### H1: auth-service v7.3.0 JWT library upgrade (jjwt 0.11→0.12) broke token validation for a class of tokens
dep-5710 (auth-service v7.3.0, 14:00:00Z) rewrote TokenValidator against the breaking jjwt 0.12 parser API. The rewritten validator rejects a CLASS of otherwise-valid tokens (parser/claim/algorithm/skew behaviour change) as invalid_token, producing ~36% fast 401s on auth-service; api-gateway, its sole caller, inherits ~21%. Fault originates in the auth-service release. The critic's major objection stands: the middle hop is assumed and the specific rejected class is unnamed — the ~1/3 share is inferred from the aggregate error_rate alone, and a class-based rejection would predict a share set by token-population mix, which is plausible but unverified. Only an explicit log/parser error or a per-class token test separates this from H2.

**Causal chain**

2. The rewritten validator rejects a stable class/fraction of still-valid tokens and returns 401 invalid_token *(assumed)*
3. auth-service error_rate steps from 0.16–0.31% baseline to ~36% in a single clean minute at 14:02, ~2 min after the deploy (onset is NOT the deploy minute) [F19, F22, F25, F39]

### H6: Key-rotation rollout gap: cfg-2705 published k-2026-04 while pods running the NEW v7.3.0 image carried a build-time default key id / JWKS snapshot
New competing hypothesis that re-frames the co-timing rather than treating the two changes as rivals: dep-5710 (14:00) replaced the validator AND its bundled key/JWKS assumptions; cfg-2705 (14:01) then rotated the key id one minute later. If v7.3.0's new TokenValidator hardened key resolution (e.g. strict kid matching, no fallback to the previous key — exactly the kind of change a 'breaking parser API' rewrite introduces) while the fleet's key material was mid-transition, the two changes interact: neither alone produces the failure, but the deploy's stricter resolution plus the just-rotated key id breaks a stable fraction of tokens. This predicts the same observables as H1/H2 but differs in the FIX: the resolution is to make the validator tolerate both key ids (or re-rotate after the deploy settles), not to blindly roll back the deploy or blindly re-publish the old key. It is an ORIGIN-level variant only insofar as the fault is the combination originating in the 14:00–14:01 change pair on auth-service; on current evidence it cannot be separated from H1/H2.

**Causal chain**
1. dep-5710 (14:00:00Z) rewrites TokenValidator against the jjwt 0.12 'breaking parser API' — the rewrite is the kind that hardens/strictens key or algorithm resolution [F7, F13, F41]
2. cfg-2705 (14:01:00Z) rotates the signing key id k-2025-10 → k-2026-04 one minute later, so key material was mid-transition exactly when the stricter validator went live [F8, F14, F42]
3. The strict validator rejects tokens signed under the previous/partially-propagated key id as invalid_token, a stable fraction of validations, with no fallback path *(assumed)*
4. The combined effect appears as a single clean step at 14:02, ~1–2 min after both changes, and stays flat for 1.5h because neither input self-corrects [F19, F22, F25, F26, F27]

## Data gaps
- Per-instance / per-replica / per-AZ and per-endpoint error_rate for auth-service is structurally unavailable — the metric is a single service-level {ts,avg,max} series with no label axis (F24, F40), and error_rate_by_route / error_rate_by_endpoint / request_rate_by_operation / error_rate_per_path all return not_found on both auth-service and api-gateway (F36-F38). This is the single named discriminator between H1 and H2 and it cannot be measured on the exposed telemetry.
- auth-service logs are unsearchable (backend 503, identity-namespace pipeline down), so the '401 invalid_token' text, the rejected kid, and any jjwt parser exception could not be read (F29), and no log-side clock exists to time a key publish.
- No rollout state exists for dep-5710 (no updated/replicas/pod-replacement fields, canary vs full unknown) (F30, F31, F35), so it cannot be determined whether the deploy was partial or whether it replaced all pods before/after cfg-2705.
- No JWKS/key-publish timestamp or key-store service exists in the registry or dependency graph (F32, F33, F34), so when k-2026-04 first became fetchable relative to the 14:02 step is unobservable.
- No dependency-level metric was ever read for redis-cache, user-db or kyc-provider; their exclusion rests on zero deployment/config artifacts (F11, F15, F43, F45) rather than on healthy error/latency series, so a silent dependency fault is unsupported rather than disproven.
- Thread-pool, connection-pool and GC metrics are not exposed (only the 7 flat metrics of F36), so an internal resource mechanism could not be fully excluded, though flat p99 latency argues against a latency-bearing saturation (F6).
- The stale red herring services 'session-store' and 'user-service' returned not_found (tc-007, tc-008), meaning the intended dependency checks never resolved to real services; kyc-provider has has_telemetry=false so its runtime behavior is unobserved despite its artifact surface being queryable (F45).

## What would change this conclusion
- An auth-service ERROR log line at 14:02Z showing a jjwt parser/claims/skew exception would move the conclusion to H1 (dep-5710) as root cause.
- An auth-service log or JWKS-fetch record showing an unknown/old kid (k-2025-10) rejection, or evidence that only a subset of pods had loaded k-2026-04, would move the conclusion to H2 (cfg-2705).
- Per-replica error_rate showing the ~36% concentrated in a subset of replicas (rather than uniformly across all replicas) would favour the cfg-2705 partial-adoption / H6 interaction signature over a uniform validator rejection.
- A per-route breakdown showing the failures confined to a validation/introspection endpoint while login/token-mint stays clean would favour a validator-side class rejection; failures uniform across all routes would favour a key-state split.
- A successful per-class token test proving the v7.3.0 validator rejects valid tokens while the pre-v7.3.0 validator accepts them (or the reverse) would directly attribute the fault to dep-5710.
- Evidence that the re-published/dual-key mitigation drops the error rate to baseline would confirm the key-id path (H2/H6) as the causal change and would falsify a pure parser defect (H1).
- Discovery of a change artifact on a service not covered by the sweeps (including kyc-provider, redis-cache or user-db) coinciding with 14:02Z would reopen the possibility of an origin outside the auth-service change pair.
