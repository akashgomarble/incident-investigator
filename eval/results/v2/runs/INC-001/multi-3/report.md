# Incident investigation report: INC-001
*System: multi_agent | outcome: **root_cause_identified** | ended: critic_accepted*

## Summary
H1 (confidence 0.78, high) is accepted as the root cause: deployment dep-5101 (order-service v2.14.0, live at 12:10:00Z, not rolled back) replaced OrderRules.validateMargin() with a new MarginCheckValidator in the POST /v1/orders validation path, and the new validator throws NullPointerException ('marginProfile is null', MarginCheckValidator.java:88) on all F&O orders, surfacing as HTTP 500. The evidence chain is short and verified at every hop: dep-5101 is the only deploy/config change across all services in the window, its changelog is exactly a margin-check rewrite scoped to F&O orders, the NPE is thrown inside the class it introduced, onset tracks the deploy (12:10Z deploy → 12:12Z metric step → first error 12:12:31Z), and the failure persists as a flat ~18% error plateau for ~104 minutes with no traffic, latency, CPU, pool, cache or DB correlate. Competing origins are contradicted by data: all six non-order services stay flat at ~0.1–0.32% with no step at 12:12Z, redis-cache and ledger-db legs are flat, and no saturation/load signature exists. Residual limitation: no source diff was retrievable, so the defect mechanism (missing null guard vs. a field the new code no longer populates/defaults) is inferred from log text alone — if the latter, a data backfill may be needed in addition to rollback.

### H1: dep-5101 margin-check rewrite throws NPE on F&O orders (leading)
order-service v2.14.0 (dep-5101, deployed 12:10:00Z, live, no rollback) replaced OrderRules.validateMargin() with a new MarginCheckValidator in the order validation chain. The new validator dereferences marginProfile without a null guard, or no longer populates/defaults it the way the removed legacy path did, so an F&O order whose marginProfile is absent throws NullPointerException at MarginCheckValidator.validate and is returned as HTTP 500 'marginProfile is null'. Fix: roll back dep-5101. Sub-reading unresolved: missing null guard vs. unpopulated field (may imply a data backfill in addition to rollback).

### H2: Upstream/dependency stops supplying marginProfile for FNO accounts

Origin is a dependency fault (one of ledger-db, pricing-engine/market-data-service, or redis-cache) with no order-service change as proximate cause; the new validator is then only the instrument that exposed it. Fix: repair/backfill the upstream supplier rather than roll back dep-5101.

1. order-service's outbound dependencies are ledger-db (shared db), pricing-engine (http, which itself calls market-data-service and redis-cache), exchange-gateway, kafka; marginProfile could originate in any of four candidates, so this origin has four possible loci. [F5, F31]
2. The supplying component begins returning null or ceases writing marginProfile for FNO accounts — no supporting telemetry whatsoever; this hop is entirely assumed. *(assumed)*
3. order-service's margin path receives null and throws NullPointerException at MarginCheckValidator.validate, surfacing as HTTP 500 'marginProfile is null'. [F10, F13, F28]

## What would change this conclusion
- Evidence that the same FNO accounts or orderType had successful margin checks before 12:10Z under the old code path (e.g. a pre-onset success log for account 99733 or 10578) would confirm H1 as a deterministic code regression; conversely, a demonstrated pre-existing null/absent marginProfile for those accounts before the deploy would move the origin to a data/upstream cause and change the fix to repair/backfill rather than rollback.
- Retrieved dep-5101 source or diff showing that MarginCheckValidator reads marginProfile from an HTTP/cache/DB source that was changed elsewhere — or that the legacy validator populated/defaulted marginProfile — would shift the mechanism and possibly the origin, and would determine whether rollback alone is sufficient.
- A deployment or data-plane/backfill change discovered on any marginProfile-supplying component (ledger-db, pricing-engine, market-data-service, redis-cache) in 12:00–12:15Z, or a non-flat health signal on redis-cache/kafka/ledger-db over the onset window, would revive H2/H3 and point the fix upstream.
- A step change at 12:12Z in any of the six non-order services' error rate (currently all flat ~0.1–0.32%), or a multi-writer anomaly on ledger-db, would indicate a shared-component origin and contradict the single-service FNO-only signature.
- Evidence of a traffic surge, latency rise, CPU or DB-pool saturation at 12:12Z (currently request_rate ~230 req/s, p99 ~148–153ms, cpu ~40%, pool ~14 with no step) or a process restart/rollover at 12:10–12:12Z would support H4/H5-style explanations and weaken the deploy-attributable account.
- Showing that the 'marginProfile is null' errors stop without any rollback, or that they predate the deploy in unread log pages, would break the temporal attribution to dep-5101; equally, failure of the error rate to fall after rollback would require reopening the dependency hypotheses.
