# Incident investigation report: INC-008
*System: multi_agent | outcome: **root_cause_identified** | ended: critic_accepted*

## Summary
Login slowness and 503s on auth-service are caused by CPU saturation at a provisioning ceiling: a ~3.8x request-rate surge (≈390 → ~1500 req/s) starting 06:50-06:53Z pinned auth-service CPU at ~97% with memory flat, saturated the worker pool (active=64/64, queues to 98763), and filled the server accept queue, so POST /v1/auth/login was rejected with 'accept queue full' 503s and p99 rose to ~3.8s; the autoscaler wanted 14 replicas but was capped at maxReplicas=8. This is H1 at confidence 0.60 (medium), and it is clearly ahead of the alternatives. The reporter's bcrypt-regression theory (H3) is decisively excluded — there was no auth-service deployment or functional config change in the window — and the shared redis-cache/portfolio-service path (H2) is now affirmatively contradicted by flat redis and neighbour telemetry. Confidence is capped by one unresolved hop: the origin of the surge (genuine external load vs retry amplification, H5 at 0.15) cannot be measured with the available telemetry.

## Probable root cause
**Auth-service CPU saturation from a genuine load surge exceeding provisioned capacity (maxReplicas=8 cap)** -- capacity_saturation in `auth-service`, triggered by `null` (confidence 0.60, medium)

### H1: Auth-service CPU saturation from a genuine load surge exceeding provisioned capacity (maxReplicas=8 cap)
auth-service hit a CPU-bound capacity ceiling at ~06:50-06:55Z. Request rate rose ~3.8x (390 -> ~1500 req/s) driving cpu_pct ~38%->~97% with memory flat, saturating the worker pool (active=64/64, queue up to 98763) and the server accept queue, so POST /v1/auth/login was rejected 503 ('accept queue full') and p99 rose to ~3.8s. The autoscaler TRIED to compensate and could not: desired replicas 14 exceeded maxReplicas 8 (F29), and restarts stayed 0 with the process live at the ceiling (F28). The fault is that a load surge outgrew the provisioned replica cap; there is no faulty code/config on auth-service, and the shared redis-cache path is affirmatively healthy (F31-F33).

**Causal chain**
1. A ~3.8x surge in request rate to auth-service begins at ~06:50-06:51Z (390 -> ~1500 req/s) [F11, F24, F38]
2. auth-service CPU saturates in lockstep (~38%->~97% pinned, memory flat, restarts 0) — a live process at a capacity ceiling, not a crash loop or GC event [F10, F28, F7]

6. No auth-service deployment or auth-relevant config change exists in the window; the only auth change is a non-functional log.level flip [F1, F13, F14, F2, F3]

On this reading the surge is a feedback symptom and the origin is retry behaviour (or whatever caused the first failures) rather than provisioned capacity. The critic rightly notes this was dismissed on an indirect aggregate-rate argument; however the gateway-ingress evidence (F25/F38/F41) still tilts against a single-caller retry origin, and no retry counter can be measured (F37).

### H4: user-db (postgres) degradation causing login slowness
auth-service's sole DB dependency is user-db (postgres, shared:false). If user-db degraded (slow queries, connection exhaustion), login requests needing user lookups would block, raising latency and consuming auth-service CPU/threads until the accept queue filled.

**Causal chain**
1. user-db is auth-service's only DB edge and is not shared, so only user-db itself degrading can produce login slowness via this path [F5, F3]
2. user-db slowness blocks login DB lookups, backing up auth-service CPU/threads into accept-queue saturation and 503s *(assumed)*
3. The observed surface is inconsistent with blocked DB calls: no timeout or connection-refused errors, memory flat, CPU pinned, worker pool CPU-bound, autoscaler capped [F9, F10, F29]

**Supporting evidence**
  - `F5` ✔ user-db is NOT a shared component: its only edge is from auth-service, so auth-service is its sole consumer and a neighbour cannot reach auth-service through it (it can only be the fault if user-db itself degraded).
**Contradicting evidence**
  - `F9` ✔ The 503 error signature is NOT a timeout or connection-refused: every auth-service ERROR log is 'request rejected: accept queue full, returning 503 (POST /v1/auth/login)' — 59 matches 06:55:42-07:14:54Z in the first query and 372 total matches spanning 06:55:42Z to 08:58:57Z. Only the POST /v1/auth/login endpoint string appears; no other endpoint appears in any matched ERROR pattern.
  - `F10` ✔ auth-service CPU saturated at the same onset: cpu_pct was steady ~36.8-38.6% through the 06:40 bucket, then rose to avg 84.31/max 97.33 at 06:50 and pinned at ~96.7-97.7% for the remainder (last 96.97). Memory was flat throughout (~51-53%, min 46.97/max 57.07), so this is CPU-bound, not memory/GC-driven.
  - `F29` ✔ Endpoint/caller breakdown from auth-service logs: the only error/rejection endpoint is POST /v1/auth/login — top pattern 'request rejected: accept queue full, returning <n> (POST /v<n>/auth/login)' count 104, first_seen 06:55:42Z. The first new warning appears at 06:54:53Z 'worker pool saturated (active=64/64, queue=39035)' and the pool stays pinned at 'active=64/64' with queues up to 98763, and the autoscaler cannot help: 'autoscaler: desired replicas 14 exceeds maxReplicas 8; cannot scale further' (first_seen 06:57:15Z). No /v1/auth/refresh or other endpoint appears in any matched log pattern.
**Assumptions**

**Rejected because:** F9 shows no timeout or connection-refused errors — all 503s are 'accept queue full'; F10 shows memory flat with CPU pinned ~97%; F29 shows the worker pool is CPU-bound at 64/64 with the autoscaler capped. Inconsistent with blocked downstream calls.

## Data gaps
- Per-caller / per-client-IP / per-user-agent request breakdown is structurally unavailable for both auth-service and api-gateway, and logs carry no client identity (F36, F39) — this is the single gap capping confidence, since it is the axis that would discriminate H1 (broad exogenous load) from H5 (concentrated retry amplification).
- No per-endpoint request/latency metric exists; the 'isolated to POST /v1/auth/login' claim rests on that string being the only endpoint in ERROR logs (F9, F40), not on a positive check that /v1/auth/refresh or /userinfo traffic was normal or elevated.
- No retry / upstream-attempt / connection-attempt metric on api-gateway (F37) and no gateway log records at all, so retry volume cannot be measured directly; the anti-retry argument is an inference from gateway ingress rates (F25, F38, F41).
- redis-cache has no latency_p99_ms metric (F30), so redis slowness is inferred absent from flat CPU / hit ratio / connections rather than directly measured; redis evictions_per_min and memory_pct were available but not retrieved before the query budget ran out.
- auth-service exposes no DB/connection-pool, thread-count or GC metric (F36), so CPU-bound hashing versus downstream DB blocking cannot be fully separated from auth-service's own telemetry.
- pricing-engine and market-data-service latency and request_rate for the onset window were not retrieved (budget exhausted), so whether the ~3.8x traffic surge was edge-wide or auth-specific is unconfirmed.
- kyc-provider has has_telemetry:false, so any contribution from the external KYC call path is unmeasurable from this dataset.
- It was not established whether the maxReplicas=8 cap was introduced recently (no evidence places any autoscaling config change near onset), and it is unclear whether the change backends would surface out-of-scope events (feature flags, infra changes) that could have preceded the surge.
- Blast radius outside auth-service/api-gateway remains unverified: no evidence shows whether other services or non-login endpoints degraded in the same window.

## What would change this conclusion
- New per-caller or per-client-IP telemetry showing the ~3.8-4.1x surge is dominated by one or a few retrying clients/sources — that would move H5 (retry amplification) above H1 and shift the fix from adding capacity to fixing the retry source.
- Direct evidence of a shared-infrastructure fault at onset — e.g. a redis-cache latency spike, failover, hit-ratio collapse or eviction/memory-pressure event, or a degradation step in portfolio-service/pricing-engine/market-data-service — would revive H2 and point at the shared cache or its neighbour rather than auth-service capacity.
- Discovery of an unlogged auth-service deployment or a functional auth config/feature-flag change (bcrypt/JWT/cache related) near onset would revive H3 (bcrypt regression) and justify a rollback.
- Evidence that the maxReplicas=8 cap was itself changed or mis-configured just before onset (e.g. a recent autoscaling config change) would recast the root cause from demand-driven saturation to a configuration regression, changing the remediation to a config revert.
- Evidence that api-gateway itself retries auth-service (gateway-side retry logs or a retry counter showing attempts exceeding inbound requests) would flip the surge from cause to symptom and redirect the fix to the gateway.
- A user-db or kyc-provider degradation (slow queries, connection exhaustion, KYC timeouts) appearing at onset would contradict the CPU-bound signature and revive H4 / the external-dependency explanation.
- Demonstration that the same surge did not affect any other edge-served service (i.e. traffic is auth-specific) versus an edge-wide surge would refine whether the trigger is global demand or login-specific behaviour.
