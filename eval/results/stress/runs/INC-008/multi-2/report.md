# Incident investigation report: INC-008
*System: multi_agent | outcome: **root_cause_identified** | ended: critic_accepted*

## Summary
Root cause: auth-service (SEV-2, INC-008) was saturated by a ~3.9x external login-demand surge that outgrew its fixed capacity — no code or config regression occurred. Starting in the 06:50Z bucket, offered login demand through api-gateway stepped up ~3.9x (auth-service ~395 -> ~1470-1538 req/s), coincident to the bucket with p99 rising from ~90ms to ~3.8s and CPU pinning to ~96-98%; the 64-thread worker pool hit 64/64 with accept-queue backlog up to ~98k, the autoscaler wanted 14 replicas but was capped at maxReplicas=8, and app-level admission control began rejecting connections with 'accept queue full' 503s at 06:55:42Z. The reporter's bcrypt-regression theory (HIST-101) is not reproduced: deployment sweeps covering 01:00-09:00Z found no auth-service release, and the only config change anywhere was a 03:40Z log-verbosity edit ~3h10m pre-onset. The gateway is a demonstrated unsaturated pass-through, and the shared redis-cache dependency was eliminated by direct measurement (hit-ratio flat/locally high, evictions and clients flat, CPU ~21-23% while auth pinned ~96%, zero WARN+ logs). Confidence in the top hypothesis is medium (0.70), capped by the unresolvable per-route attribution detail. Fix direction: relieve/raise auth-service capacity and throttle or absorb the external login demand — not an auth-service rollback.

## Probable root cause
**External login demand surge outgrew auth-service capacity (no change required)** -- capacity_saturation in `auth-service`, triggered by `null` (confidence 0.70, medium)

### H1: External login demand surge outgrew auth-service capacity (no change required)
Starting in the 06:50Z bucket, offered login demand through api-gateway steps up ~3.9x (auth-service ~395 -> ~1470-1513 req/s). auth-service is provisioned for ~400 req/s with a fixed 64-thread worker pool and maxReplicas=8; it saturates (pool 64/64, accept-queue backlog ~98k, autoscaler wants 14 but is capped at 8), CPU pins to ~96-98%, tail latency inflates to ~3.8s, and the app's own admission control rejects connections with 'accept queue full' 503s from 06:55:42Z. No deployment or config change coincides with onset, so the origin is auth-service capacity being outgrown by offered load, not a code or config regression. The upstream generator of the demand (external traffic event, retry storm, client bug) is unidentified and is not a service-level fault in the inspected graph.

**Causal chain**

2. The demand enters through api-gateway, whose request_rate steps up in the same 06:50Z bucket (~1228 -> ~4790-4991 req/s) while the gateway itself stays unsaturated (CPU ~40-44%, memory flat ~56-62%, restarts 0, zero ERROR logs). [F24, F25, F27, F29]

### H5: api-gateway as the fault origin for the demand surge (collapsed into H1)

The gateway is therefore not a distinct origin: it is the conduit for the same external offered load that saturates auth-service, yielding the same fix direction as H1. Collapsed into H1 to avoid double-counting one origin.

**Causal chain**
1. api-gateway request_rate steps up at 06:50Z from ~1228 to a ~4790-4991 req/s plateau (~3.9x). [F24, F25]

3. The added gateway demand is passed downstream; auth-service request_rate rises ~3.9x in the same bucket, saturating its worker pool. [F6, F4, F5]
4. The gateway's own 5xx and p99 rises (both 06:54Z) lag its request step (06:50Z) and mirror auth-service, a pass-through signature rather than a gateway self-fault. [F26, F28, F29]
