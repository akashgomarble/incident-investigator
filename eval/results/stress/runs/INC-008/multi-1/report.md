# Incident investigation report: INC-008
*System: multi_agent | outcome: **inconclusive** | ended: critic_inconclusive*

## Summary
The verified terminal mechanism of INC-008 is auth-service resource saturation: a ~3.75x login request-rate surge drove CPU to ~97%, filled the worker pool (64/64) and the accept queue, producing accept-queue-full 503s on POST /v1/auth/login and a p99 step from ~90ms to ~3.8s at ~06:54Z, with the autoscaler pinned at maxReplicas. The bcrypt-regression theory from the report is correctly rejected: two independent deployment queries show zero auth-service releases, and the only config change (cfg-2801) merely moved log.level INFO->WARN. However, the origin of the surge cannot be established: H1 (externally-generated load) rests on an assumption that is structurally unmeasurable (auth-service logs carry no client identity; api-gateway ingress is permanently unavailable; query_metrics is circuit-open), while H2 (shared redis-cache read-path degradation) reaches the identical terminal state and its decisive metrics (hit-rate, evictions, connections, latency, replica status) were never obtainable. Round 3 did demote H2's failover/cold-cache path via a clean redis-cache INFO sweep and clean log-level checks on three of four cache consumers, so H1 is the working hypothesis at ~0.50 confidence, but this is absence-of-evidence in an incomplete data set, not a positive measurement of cache read-path health. Outcome is therefore inconclusive, with safe mitigations plus the specific discriminating measurements that would settle H1 vs. H2.

## Probable root cause
**Inconclusive** -- the evidence does not single out one cause. See ranked hypotheses and data gaps.

### H1: Externally-generated login traffic surge saturates auth-service CPU -> accept-queue 503s
At ~06:48Z auth-service login request rate rose ~3.75x (~400 -> ~1500 req/s), saturating auth-service CPU at ~97%, filling the worker pool (64/64, queue up to 98763) and the accept queue, which returned 503 on POST /v1/auth/login; p99 stepped from ~90ms to ~3.8s at the same 06:54Z bucket and the autoscaler hit its maxReplicas ceiling at 06:57:15Z. No auth-service deployment or code change exists anywhere in the window, and the only component in the topology besides auth-service that could originate this is redis-cache, which is now shown to be healthy throughout the onset (alive, persisting, no failover/eviction/restart/cold-cache signature). The remaining origin is therefore load arriving at auth-service from outside its code and outside its dependencies. The terminal mechanism and the absence of any deploy/config/dependency trigger are verified; the exact provenance of the load (distinct-client flood vs. repeat/retry storm from an upstream caller) is structurally unmeasurable and is stated as an unresolved detail rather than a separate hypothesis.

### H2: Shared redis-cache degradation (cold-cache/contention) stalls auth-service logins into CPU saturation

Origin would be the shared cache, not auth-service. This hypothesis has been substantially refuted in round 3: the redis-cache INFO-level sweep the critic requested (05:00-06:54Z and 05:00-08:59Z, full-store data_range, partial=false) shows no failover, replica promotion/resync, cold-cache, eviction-error, connection-refused, restart or readiness change, and RDB persistence continued uninterrupted with increasing write volume; the same cache's other three consumers show zero coincident WARN/ERROR. It is retained as active only because redis-cache health metrics (hit-rate, evictions, connections, latency) were never obtainable, so a latency-only, log-invisible read-path stall cannot be disproven.
