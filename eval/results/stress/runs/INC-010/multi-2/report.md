# Incident investigation report: INC-010
*System: multi_agent | outcome: **root_cause_identified** | ended: critic_accepted*

## Summary
Settlement posting stopped because order-service v2.16.0 (dep-6010, 07:40:00Z) began emitting OrderExecuted events in a v2 schema (field renamed qty->quantity, new 'venue' field, v2 schema-version header) that settlement-service's v1 deserializer cannot parse; the first failure is at 07:42:14Z, 2m14s after the deploy. The consumer treats the record at orders-3@8841207 as a poison message and retries the same offset in a tight loop (tens of thousands of attempts), pinning CPU ~70% and blocking the partition, so request_rate collapses to ~0.4 req/s and consumer lag climbs monotonically to ~60k. The reporter's suspected config change (cfg-3004, max.poll.records 500->200) is refuted on mechanism — a batch-size parameter cannot produce a deserialization error or a partition-blocked spin. Confidence is medium (0.69): every obtainable discriminator (tight timing, change-content match, blast radius confined to the one v1 decoder, flat kafka partition health, refuted alternatives) points to this cause, but the producer-side wire artifact was never directly observed.

## Probable root cause
**order-service v2.16.0 emits v2-schema OrderExecuted events that settlement-service cannot deserialize, blocking the orders-3 partition** -- bad_deployment in `order-service`, triggered by `dep-6010` (confidence 0.69, medium)

### H1: order-service v2.16.0 emits v2-schema OrderExecuted events that settlement-service cannot deserialize, blocking the orders-3 partition

The partition is blocked, no further records are consumed, request_rate collapses to ~0.4 req/s, and consumer lag grows monotonically to ~60k. Category: bad_deployment (producer schema change).
