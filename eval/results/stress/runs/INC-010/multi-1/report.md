# Incident investigation report: INC-010
*System: multi_agent | outcome: **root_cause_identified** | ended: critic_accepted*

## Summary
Root cause (confidence 0.78, high): order-service deployment dep-6010 (v2.16.0 "Order events v2", live 07:40:00Z) began emitting OrderExecuted messages in schema v2 (qty→quantity, version header v2) onto the shared kafka topic, while settlement-service still parses schema v1. The first such message at offset orders-3@8841207 fails deserialization ("missing required field 'qty', schema v1 expected, header says v2") and becomes a permanent poison message — 213 identical errors and 196 "partition blocked" retries — so the consumer cannot advance the partition, producing zero settlements and monotonically growing lag. Onset timing is decisive: lag was flat through the 07:35 bucket, jumped in the 07:40 bucket (avg 515 → 60k by 09:55), and throughput collapsed from ~62 req/s to ~0.4 req/s, with the first error at 07:42:14Z, two minutes after the deploy rollout completed at 07:40:01Z. The competing hypotheses are contradicted by direct measurement: the poll-settings change (cfg-3004) cannot produce a per-offset schema failure; broker telemetry is flat (under-replicated partitions 0, steady ingest ~2527 msg/s, CPU flat); and settlement-service shows no restarts and no DB-pool pressure (the CPU rise at 07:42 is consistent with poison-message retry load). Mitigation is therefore to restore the schema contract (roll back dep-6010 or, preferably, make the consumer tolerant/skip or park the bad offset), not to tune the consumer.

## Probable root cause
**order-service v2.16.0 OrderExecuted schema break (qty→quantity, v2 header) poisons settlement-service's consumer on partition orders-3** -- bad_deployment in `order-service`, triggered by `dep-6010` (confidence 0.78, high)

### H1: order-service v2.16.0 OrderExecuted schema break (qty→quantity, v2 header) poisons settlement-service's consumer on partition orders-3
order-service deployment dep-6010 (v2.16.0 'Order events v2', live at 07:40:00Z) began publishing OrderExecuted messages in schema v2 (field qty renamed to quantity, version header v2) to the shared kafka topic that settlement-service consumes. settlement-service still expects schema v1, so it fails to deserialize the message at offset orders-3@8841207 ('missing required field qty, schema v1 expected, header says v2'), that offset becomes a poison message retried forever, and because the consumer cannot advance past it the partition is blocked — producing zero settlements and monotonically growing lag. Consumer CPU rises to ~69% in the same bucket as the first error, consistent with busy-retrying the poisoned offset.

**Causal chain**
1. order-service v2.16.0 deploys at 07:40:00Z with an OrderExecuted schema change: rename qty->quantity, add venue, schema version header v2 (rollout complete 07:40:01Z, no rollback) [F1, F13, F10, F21, F20]
2. order-service publishes those v2 OrderExecuted events to the shared kafka broker, which settlement-service consumes (order-service 'queue-produce', settlement-service 'queue-consume', kafka shared=true) [F14, F3, F23]
3. settlement-service receives the v2 message and its v1 deserializer rejects it: 'missing required field qty (schema v1 expected, header says v2)' at orders-3@8841207, first at 07:42:14Z [F9, F17, F12, F22]
4. The bad offset cannot be skipped: poison-message retries ('poison message: retrying orders-3@8841207 (attempt ~92490), partition blocked') block the partition, so no further records are processed [F9, F11]
5. Consumer busy-retries the poisoned offset rather than idling: cpu_pct jumps from ~27% to ~69% in the exact 07:42 bucket of the first error and stays elevated [F30]
6. Processed throughput collapses from ~62 req/s to ~0.4 req/s in 07:40-07:54 and consumer lag climbs monotonically from ~36-55 to ~60k+ by 09:55Z (zero settlements posted) [F8, F7]
