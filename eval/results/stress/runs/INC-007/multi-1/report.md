# Incident investigation report: INC-007
*System: multi_agent | outcome: **inconclusive** | ended: critic_inconclusive*

## Summary
The incident is real, localized to auth-service's token-validation path, and per the reviewed analysis the root cause is NOT adequately established: H1 (JWT library/TokenValidator regression from dep-5710) at 0.45 and H2 (scheduled signing-key rotation cfg-2705 published before all validators adopted it) at 0.40 remain effectively tied and name different origins and fixes. What is solid: a single-minute step in auth-service error_rate from ~0.2% to ~36% at 2026-04-15T14:02:00Z with flat throughput (~400 req/s) and p99 (~90 ms), a flat ~2h plateau (latest 15:56Z), and an independent, time-aligned ~21% error plateau at the unchanged caller api-gateway, which rules out a log-pipeline reporting artifact (H5). Fleet-wide sweeps show the only changes all day are auth-service dep-5710 v7.3.0 at 14:00Z ('jjwt 0.11 -> 0.12 (breaking parser API)', 'TokenValidator rewritten') and cfg-2705 at 14:01Z (jwt.signing.key_id k-2025-10 -> k-2026-04); both are still live and neither was ever reverted. Every decisive discriminator is unreachable in this run: no per-instance/pod, endpoint or token-issuer dimension exists, no diff/JWKS-source/rotation-mode metadata exists, the deployed library version is self-contradictory, and the single-change rollback test could not be run with read-only tooling (logs also unsearchable). H3 (clock skew/cert) and H4's resource-exhaustion arm are not supported; H4's pod-restart arm is not closed out. Immediate action is a safe mitigation plus the rollback experiment: roll back dep-5710 first (H1 is the marginally better fit on shape), then re-test with cfg-2705 reverted if the error persists.

### H1: JWT library upgrade (dep-5710) introduced a token-validation regression
auth-service deploy dep-5710 v7.3.0 at 14:00:00Z replaced the JWT parser (jjwt 0.11 -> 0.12, described as a breaking parser API change) and rewrote TokenValidator. The new/unmigrated validation path emits a wrong invalid_token verdict for a persistent subset of otherwise-valid tokens, producing a step from ~0.2% to ~36% error_rate at 14:02:00Z that plateaus for ~2h without converging, with throughput and p99 latency untouched. The deterministic, converging-never nature of the plateau fits a code fault better than a propagation race. NOTE the mechanism hop remains unevidenced: no diff, no clock-skew/TTL/strictness defaults, and the deployed library version is self-contradictory, so this is a timing-and-shape argument, not a mechanism proof.

**Causal chain**
1. Deploy dep-5710 v7.3.0 goes live at 14:00:00Z as the only fleet deployment that day, with a breaking jjwt parser API change and a rewritten TokenValidator; never rolled back. [F1, F13, F16, F22, F32, F33, F37, F38, F40]
2. The rewritten validator applies different parser semantics (clock-skew default / claim strictness) to a class of valid tokens, inverting them to invalid_token. *(assumed)*
3. auth-service error_rate steps from 0.16% (14:01Z) to 36.08% (14:02Z), exactly 2 minutes after the deploy, then holds 35-39% through 15:59Z with no decay. [F7, F8, F17, F27, F28]
4. The fault is a wrong-verdict, not load or resource: throughput flat ~390-417 req/s, p99 flat ~86-95 ms, cpu_pct ~38%, memory_pct ~52%, rate_limited ~2/min. [F9, F10, F29, F30]
5. api-gateway, the caller of auth-service, shows an independent contemporaneous ~21% error plateau in the same window, confirming a real user-facing fault rather than a reporting artifact. [F11]

### H2: Scheduled signing-key rotation (cfg-2705) published a new key_id before all validators/consumers adopted it
security-automation rotated jwt.signing.key_id from 'k-2025-10' to 'k-2026-04' at 14:01:00Z as a single un-staged key assignment on auth-service. A fraction of token validations then resolve the wrong key (or a validator holds/expects the previous key_id), yielding invalid_token for ~1/3 of validations, one minute before the 14:02:00Z error step. This matches the HIST-108 precedent (lead only). The hypothesis carries an unresolved internal weakness: a key-propagation race should converge as validators reload, yet the error is a flat 35-39% plateau for ~2h with no decay, which requires an unobserved permanently-stalled (or per-pod-frozen) reload.

**Causal chain**
1. cfg-2705, the only config change fleet-wide on 2026-04-15, rotates jwt.signing.key_id k-2025-10 -> k-2026-04 on auth-service at 14:01:00Z; single key-value assignment with no dual-key/grace/overlap field; never reverted. [F2, F14, F19, F20, F35, F39, F41, F43, F44]
2. The new key_id is live before every validator/consumer has adopted it (or a subset keeps using the old key_id), so those validations resolve the wrong key and return invalid_token. *(assumed)*
3. If the keys are resolved per-pod (HIST-108-style JWKS reload), only lagging pods would fail - but the plateau is flat, so any such partition must be frozen for ~2h. [F8, F17, F28]
4. auth-service error_rate steps to ~36% at 14:02:00Z, 1 minute after the rotation, with unchanged throughput/latency/resources, and holds through 15:59Z. [F7, F8, F9, F10, F15, F27, F29]
5. api-gateway, the caller, inherits a contemporaneous ~21% error plateau. [F11]

## What would change this conclusion
- Reverting dep-5710 alone and observing auth-service error_rate fall from ~36% back toward the ~0.2% baseline within minutes would establish H1 as the root cause and overturn the inconclusive outcome.
- Reverting cfg-2705 (re-publishing key 'k-2025-10' and the previous signing key) with error_rate recovery while dep-5710 stays live would establish H2 as the root cause.
- A per-instance/per-pod error breakdown showing failures concentrated in ~1/3 of instances (rather than uniform across the fleet aggregate) would favor H2's propagation mechanism over H1's deterministic code fault.
- A per-token-issuer or issuance-epoch breakdown showing failures clustered around the 14:01Z key rotation would favor H2; a break confined to a token class independent of issuance time would favor H1.
