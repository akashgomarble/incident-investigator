# Incident investigation report: INC-012
*System: multi_agent | outcome: **root_cause_identified** | ended: critic_accepted*

## Summary
The incident was caused by ledger-db disk exhaustion, not by the payment-service v6.0.0 release: the shared ledger-db datastore filled its filesystem (89.42% at 13:00Z -> 98.84% at 14:44Z -> 100% at 14:52Z) while an inactive replication slot ('analytics_cdc') retained ~78GB of WAL, after which every write failed with 'No space left on device'. The disk was effectively full ~8 minutes BEFORE the first client-visible error (15:00:26Z) and before/at the 14:46:50Z deploy completion, and the failure crossed to order-service and settlement-service, which never received v6.0.0; the same disk-space signature hit all three services, and the rollback at 15:12Z did not restore service (errors persisted to 16:57:21Z). Confidence in the top hypothesis is 0.82 (high), clearly ahead of the rejected alternatives (config/flag change 0.05, independent infra fault 0.05, bad deployment 0.02). Two caveats cap the confidence: the WAL-retention -> disk-fill hop is corroborated by log text but not by an independent pg_wal/slot byte metric (the ledger-db metric endpoint failed), and the impact was not uniform across all four ledger-db writers — portfolio-service, an untouched fourth writer, escaped with no error jump and no disk-space signature (unexplained). v6.0.0 is a bystander; the ledger-db replication slot / disk capacity is the origin to remediate.

## Probable root cause
**ledger-db disk exhaustion from an inactive replication slot retaining WAL (HIST-114 mechanism)** -- resource_exhaustion in `ledger-db`, triggered by `null` (confidence 0.82, high)

### H1: ledger-db disk exhaustion from an inactive replication slot retaining WAL (HIST-114 mechanism)
The shared ledger-db PostgreSQL datastore ran out of disk space because the inactive replication slot 'analytics_cdc' retained ~78GB of WAL (F14, F18). Disk climbed monotonically from 89.42% at 13:00Z to 98.84% at 14:44Z and hit 100% at the 14:52Z bucket (F13) — before the v6.0.0 deploy completed at 14:46:50Z and ~8 min before the first client-visible error at 15:00:26Z. With the filesystem full, PostgreSQL could not extend WAL/data files (F14, F25), so every writer's INSERT/UPDATE failed with 'No space left on device' (F9, F15, F16). payment-service v6.0.0 is a coincidental bystander: its new MANDATE_HOLD writes merely make it one of several victims. Origin is the ledger-db datastore, not the release.

**Causal chain**
1. Inactive replication slot analytics_cdc stops advancing the WAL, so WAL segments are retained and accumulate (~78,423 MB). [F14, F18]
2. Retained WAL + normal data growth push ledger-db disk from 89.42% (13:00Z) to 98.84% (14:44Z) to 100% at 14:52Z — saturation predating the 14:46:50Z rollout completion. [F13, F17, F8]
3. With the filesystem full, ledger-db cannot extend WAL/data files: 'PANIC: could not write to file pg_wal/xlogtemp' (153) and 'could not extend file base/16402/2619: No space left on device' (139) flood from 15:01:01Z; 292 ERROR entries, no other pattern. [F14, F25, F30]
4. All clients writing ledger-db begin failing: payment-service 'ledger write failed: could not extend file: No space left on device' (15:00:26Z), order-service 'INSERT INTO orders failed: No space left on device' (15:00:42Z), settlement-service likewise. [F9, F15, F16]
5. Cross-service error rates spike: payment-service 0.17% -> 60.65%; order-service ~0.2% -> 47.9%; settlement-service -> 54.8%. [F7, F16]
6. payment-service throws exactly one error signature, a disk-space error, with zero schema/entry-type/validation rejection anywhere. [F9, F15, F27, F28, F29]
7. The condition persists after the payment-service rollback (15:12Z) and to the end of data (16:57:21Z), so rollback did not resolve it. [F26, F2]

**Supporting evidence**

  - `F14` ✔ ledger-db itself logged disk-exhaustion: 'disk usage 95%' at 14:15:45Z and 'disk usage 98%' at 14:48:20Z, plus repeated 'replication slot analytics_cdc is inactive; retaining 78423 MB of WAL' (14:16:25Z onward), then from 15:01:01Z an ERROR flood 'PANIC: could not write to file pg_wal/xlogtemp...: No space left on device' (153) and 'could not extend file base/16402/2619: No space left on device' (139).

  - `F4` ✔ The shared ledger-db is written to by four services -- order-service, portfolio-service, payment-service and settlement-service all have 'db' edges into ledger-db -- so a ledger-db-side change or problem would be a cross-service blast radius, not payment-only.
  - `F9` ✔ All 179 ERROR logs in 15:00:26Z-15:59:55Z collapse to exactly one signature: 'ledger write failed: ERROR: could not extend file: No space left on device (payment <id>)'; first occurrence 15:00:26Z, no other error pattern present.

**Assumptions**

  - No independent exogenous consumer of disk space existed.
  - portfolio-service's escape from the blast radius is explained by a different ledger write path (async/buffered/different partition) or no write attempts in the window; this is not resolved by evidence and does not bear on the origin.
  - The disk remains pinned at 100% beyond 15:24Z; the metric range retrieved stops there, but the ledger-db ERROR flood continuing to 16:57:21Z implies the condition persisted.
