# Incident investigation report: INC-012
*System: multi_agent | outcome: **root_cause_identified** | ended: critic_accepted*

## Summary
Root cause: the shared postgres 'ledger-db' ran out of disk (measured disk_used_pct 96.58% @14:20Z → ≥98% @14:38Z → pinned 100% from 14:59Z) because the inactive replication slot 'analytics_cdc' retained tens of GB of WAL (33916 MB @14:34:05Z → 77371 MB @14:49:47Z), until Postgres PANIC'd on its own pg_wal and base/ files (15:01Z) and clients surfaced verbatim 'No space left on device'. All four shared-DB writers' evidence places the origin at ledger-db, and the failure began independently of payment-service v6.0.0. Confidence 0.66 (medium, capped): the mechanism, component and fix are each directly observed, but two gaps keep it short of high — the slot's inactivity has no identified actor, and one co-writer (portfolio-service) did not degrade. v6.0.0 is coincidental: the resource trend precedes the 14:46Z deploy, the errors are physical storage errors not schema/enum rejections, and rollback at 15:12Z did not reduce errors through 16:57:54Z. The precedent-backed fix (HIST-114) is to drop/recreate the stalled slot to release retained WAL and add slot-lag/inactivity alerting.

## Probable root cause
**Shared ledger-db disk exhaustion from WAL retained by an inactive replication slot** -- resource_exhaustion in `ledger-db`, triggered by `null` (confidence 0.66, medium)

### H1: Shared ledger-db disk exhaustion from WAL retained by an inactive replication slot
The shared postgres 'ledger-db' ran out of disk space because the replication slot 'analytics_cdc' went inactive and retained tens of GB of WAL. Write paths terminating in ledger-db began failing with 'No space left on device', surfacing as payment-service ledger write failures (~60% error rate). payment-service v6.0.0 is coincidental: the resource trend started ~12 min BEFORE the deploy, and rolling the deploy back did not clear the errors. Confidence is capped because the SHARED-db scope claim (all four writers fail together) is inferred from the shared:true flag and error text, not observed co-writer behaviour — the very query that separates this from H3 was never run.

**Causal chain**
1. Replication slot 'analytics_cdc' becomes inactive and begins retaining WAL (33916 MB by 14:34:05Z, 69518 MB by 14:46:32Z, 77371 MB by 14:49:47Z) [F11]
2. Retained WAL fills the ledger-db data volume; measured disk_used_pct is already 96.58% at 14:20Z, ≥98% from 14:38Z, and pinned at 100.0% from 14:59Z [F10, F11, F28, F29]
3. Postgres PANICs: 'could not write to file pg_wal/xlogtemp.37478: No space left on device' (15:01:01Z) and 'could not extend file base/16402/2619: No space left on device' (15:01:39Z) [F10]
4. Client writes terminating in ledger-db fail and are surfaced verbatim as 'ledger write failed: ERROR: could not extend file: No space left on device' by payment-service (uniform 59/59 and 266/266 ERROR patterns; no mandate-specific or validation text) [F8, F9]
5. The failing path is shared: order-service ('INSERT INTO orders failed: No space left on device', first 15:00:42Z) and settlement-service (error rate 54.04% in the same 15:00Z bucket) fail on the same disk signature within ~16 s / the same 3-min bucket as payment-service, while portfolio-service — a co-writer — does not degrade [F24, F25, F26, F27, F4, F15, F29]
6. Because the origin is the DB, rollback of v6.0.0 at 15:12Z does not restore payments; errors persist at ~60% through 16:57:54Z [F17, F12]

### H5: Unmanaged/abandoned replication-slot consumer as an unowned out-of-band change
The origin is an unowned, out-of-inventory component behind the 'analytics_cdc' slot: no service in the platform owns or consumes that slot, so whatever process stopped consuming WAL (a decommissioned CDC sink, a paused pipeline, a dead client) is the true trigger. Because no deploy or config change for any service is recorded on 2026-06-01, the change that inactivated the consumer must be out-of-band / unmanaged — which also explains why it appears nowhere in the change ledger. This is distinct from H1 (which treats the retention policy/dropped slot as the fix target) in that it names a different origin: the unmanaged consumer, and would call for ownership/monitoring remediation, not merely clearing WAL.

**Causal chain**
1. An unmanaged consumer stops advancing the 'analytics_cdc' replication slot, so WAL is retained (33916 MB@14:34Z → 77371 MB@14:49Z) [F11, F19, F20]

4. Retained WAL fills the volume; disk_used_pct → 100%, Postgres PANICs and ledger writes fail platform-wide [F28, F10, F24, F25, F27]
