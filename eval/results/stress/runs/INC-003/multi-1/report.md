# Incident investigation report: INC-003
*System: multi_agent | outcome: **root_cause_identified** | ended: critic_accepted*

## Summary
The evidence supports H1 (confidence 0.55, medium): an outage at the external exchange partner API (api.exchange-partner.example) propagating through exchange-gateway, which is the shared non-shared choke point in front of order-service and market-data-service. Exchange-gateway's error rate rose in the 10:49Z bucket with its first partner-host connect-timeout log at 11:01:25Z, ahead of order-service's first 504 at 11:02:45Z, and all 349 order-service errors name exchange-gateway. The order-service v2.15.2 release is not the cause: the 11:16Z rollback produced no recovery, and both order-service (~31%) and exchange-gateway (~43-46%) have stayed flat through 12:57-12:58Z with partner timeouts continuing. The conclusion is limited by one irreducible inference - exchange-api has no telemetry, so a fault internal to exchange-gateway's egress path (H5, 0.22) would look observationally identical - but scoped deploy/config queries for exchange-gateway returned zero changes, leaving the partner-side origin as the best-supported explanation.

## Probable root cause
**External exchange-partner API outage propagating through exchange-gateway** -- dependency_failure in `exchange-api (external exchange partner, reached via exchange-gateway)`, triggered by `null` (confidence 0.55, medium)

### H1: External exchange-partner API outage propagating through exchange-gateway
The external exchange partner API (api.exchange-partner.example, behind exchange-gateway) began failing/timing out around 11:01Z, causing exchange-gateway 5s upstream connect timeouts and 503s; exchange-gateway then returned 504s to its callers, so order-service's placeOrder submit path (which synchronously calls exchange-gateway) timed out and ~30% of order submits failed. The fault originates outside the company; exchange-gateway is the first internal casualty, and its non-shared position between partner and callers explains the multi-service blast radius (order-service + market-data-service) with no internal shared component involved.

**Causal chain**
1. External exchange-api/partner degrades or becomes unreachable (connect timeouts, 503s) — origin, no telemetry available (has_telemetry=false), so only exchange-gateway's client-side view exists *(assumed)*
2. exchange-gateway error_rate rises from ~0.2% to 43-46% and logs 'upstream connect timeout after 5000ms host=api.exchange-partner.example' (163 placeOrder + 146 quoteSnapshot) and 'exchange-api returned 503', first at 11:01:25Z; circuit breaker opens 11:03:26Z [F3, F4, F19, F20, F21]
3. order-service's synchronous call to exchange-gateway on the submit leg now blocks ~5s and returns a gateway timeout [F2, F9, F16, F23]
4. order-service emits 349 ERRORs 'exchange-gateway call failed: <n> Gateway Timeout (placeOrder)' starting 11:02:45Z and latency_p99 jumps from ~150ms to ~5340ms in the 11:02 bucket [F1, F2]
5. Same path reaches market-data-service, the other direct gateway callee, which shows a matching but milder client-side escalation (0.23% -> ~6.5%) in the 10:57-11:03 buckets, while pricing-engine (off-path) stays flat [F31, F33, F36]
6. Reported symptom: order submit failure rate ~30% with 504s, sustained with no recovery at the 11:16Z release rollback [F1, F2, F25, F26, F27, F28, F29]
