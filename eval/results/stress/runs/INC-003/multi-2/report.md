# Incident investigation report: INC-003
*System: multi_agent | outcome: **root_cause_identified** | ended: critic_accepted*

## Summary
The incident is a failure of the external exchange partner api.exchange-partner.example (vendor-owned, no telemetry), not a defect in order-service v2.15.2. Every hop of the causal chain below the shared origin is verified: order-service's 504s are 100% "exchange-gateway call failed: 504 Gateway Timeout (placeOrder)" (F8); exchange-gateway's own upstream_error_rate steps 0.3% -> 45-46% locating the fault below it (F10); logs pin the failing endpoint to the single host api.exchange-partner.example with 5000ms connect timeouts plus genuine L7 503s carrying x-partner-request-id (F11/F31/F32/F33); and the shared-edge scope is confirmed by market-data-service and api-gateway stepping in the same bucket while pricing-engine on a separate path stays flat (F19/F21/F24). Confidence is high (0.80). The reporter's prime suspect, dep-5333, is contradicted by mechanism mismatch and by the absence of any recovery in the ~1h37m after its rollback (F8/F14).

### H2: External exchange partner (api.exchange-partner.example) outage — dependency_failure, matching HIST-103
The external exchange API api.exchange-partner.example (vendor-owned, has_telemetry=false, F30) began failing/timing out around 10:54Z. exchange-gateway's calls to that single host block on the 5s connect timeout and also receive genuine L7 503 responses, so exchange-gateway returns 504s to every consumer on the exchange-gateway->exchange-api edge. order-service's placeOrder call therefore fails ~30%, and market-data-service and api-gateway step at the same boundary, while the only service on a disparate path (pricing-engine) stays flat. order-service (and its v2.15.2 release) is only the loudest victim. The only unverified link remains the ORIGIN of the timeout (partner-side vs internal edge), which H2 and H3 share; evidence favoring partner-side: HIST-103's recorded partner-side attribution (F25/F26), zero recorded changes on the failing edge across ~6.5 months (F27/F28), and F11's real L7 503s from the partner host (a pure DNS/connect break would not yield partner-branded 503s with x-partner-request-id).

**Causal chain**
1. External exchange partner degrades around 10:54Z (unreachable/slow); no recorded internal change exists on this edge and the partner has no telemetry, so by elimination and by precedent the event is external [F11, F9, F16, F27, F28, F30]
2. Genuine L7 responses from the partner host (503 Service Unavailable with x-partner-request-id=) show the partner itself is answering and rejecting, not merely an unroutable name — this argues against a pure DNS/connect break on our side [F11, F31, F32]
3. exchange-gateway's own upstream_error_rate (failures of its downstream) steps ~0.3% -> 45-46%, locating the fault below exchange-gateway rather than in its serving path [F3, F10]
4. Every error signature in exchange-gateway logs names exactly one host, api.exchange-partner.example (connect timeouts op=placeOrder 163 / op=quoteSnapshot 146, plus 503s 161), recurring every 20-60s for the whole window; no other host appears [F11, F31, F32, F33]
5. The blocking 5000ms timeout drives exchange-gateway latency_p99 from ~130ms to ~5000ms and error_rate to 43-45%; circuit breaker opens 11:03:26Z at failure ratio 0.47 [F9, F11]
6. Every consumer of the shared exchange-gateway->exchange-api edge degrades in lockstep: market-data-service (0.24%->5.68%, F19) and api-gateway (0.23%->5.42%, F21) step at the same ~11:00Z boundary, and only this edge is common to all stepping services while pricing-engine (disparate path) stays flat [F19, F21, F22, F24]
7. order-service's placeOrder calls exchange-gateway, blocks on the 5s timeout and returns 504; order-service latency_p99 mirrors the step to ~5300ms [F8, F12]
8. order-service error_rate steps from ~0.2% to ~30% at 11:01Z and holds — a step, not a ramp; first ERROR log line 11:02:45Z [F7]
9. Identical signature to HIST-103 ('Order failures during exchange partner outage'), whose recorded root cause was an external exchange API outage on the partner side and whose resolution was failing over to a secondary exchange route [F17, F25, F26]

### H3: Internal network/DNS/egress degradation or out-of-band timeout/endpoint setting on the exchange-gateway -> partner edge
The exchange-gateway -> api.exchange-partner.example edge fails not because the partner itself degraded but because an internal network/DNS/egress path to the partner broke, or an endpoint/timeout setting was tightened out-of-band, producing the same 5000ms connect timeouts. Category is infrastructure_failure (or config_change if a setting was changed); the fix differs from waiting on the partner. It is not eliminated: no internal-edge change is RECORDED (F27/F28 only cover the change logs), and the properties that distinguish it from H2 — a shared egress path failing across multiple hosts, or a DNS/connect-pool error signature — were never directly tested (F34: INFO host= enumeration and WARN timeout/DNS queries both returned 503; the only enumeration of hosts comes from ERROR/WARN data). Counter-evidence: F11/F31 show genuine L7 503 Service Unavailable responses from the partner host with x-partner-request-id, and the errors name exactly one host, which a pure DNS/egress break would not produce and which a shared-egress failure would likely widen beyond one host.
