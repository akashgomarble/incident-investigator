# Incident investigation report: INC-008
*System: multi_agent | outcome: **inconclusive** | ended: critic_accepted*

## Summary
Login slowness/503s trace to a saturation/retry-amplification loop inside auth-service: its p99 jumped >40x (85-95ms -> ~3.8s) in the 06:53-06:54Z bucket, CPU rose 38%->~97%, the 64-worker pool filled (active=64/64, accept queue to ~98.7k) and the autoscaler was hard-capped at maxReplicas=8, so auth-service emitted its own "accept queue full ... returning 503" on /v1/auth/login. The trailing ~3.8x inbound request ramp at auth-service (and at api-gateway) begins at or after the latency jump and is confined to auth-service while order/payment/market-data stay flat, so the load surge is an effect of the slowdown, not its cause. Every rival hypothesis has positive contradictions: zero auth-service deployments in-window or in the prior two weeks (rules out the reporter's bcrypt-release suspicion), a single logging-only config change 3h13m before onset, shared redis-cache telemetry flat with three co-tenants uninjured, and user-db showing only a connections step while slow queries/lag/CPU stayed flat. Confidence in the top hypothesis is only 0.45 (below the 0.50 threshold) because the trigger that made the FIRST requests slow at 06:53Z remains unattributed: no deployment, config/flag/pool/timeout change, shared-cache event or downstream metric degradation exists, and auth-service exposes no GC/thread metric. The saturation mechanism is well evidenced; the first cause is not, so this report is honestly inconclusive with defined discriminators.

## Probable root cause
**Inconclusive** -- the evidence does not single out one cause. See ranked hypotheses and data gaps.

### H3: Retry-amplification saturation loop at a fixed-capacity auth-service ceiling (proximate mechanism confirmed, first-cause unattributed)
At 06:53-06:54Z auth-service's p99 latency collapsed (85-95ms -> ~3.8s) BEFORE any load rise; the resulting slow/failing logins triggered client/gateway retries that ramped inbound rate ~3.8x (392 -> ~1500 req/s, and api-gateway 1239 -> ~4900 req/s only AFTER the latency onset). The fixed 64-worker pool plus maxReplicas=8 autoscaler ceiling meant capacity could not grow, so the accept queue filled and auth-service self-generated 503 'accept queue full' on /v1/auth/login. The load surge is an EFFECT of the slowdown (a self-amplifying retry loop), NOT an exogenous surge; the trigger that made the FIRST requests slow at 06:53Z is not established by current evidence. The 'no faulty change' / 'organic surge' framing of the previous version is hereby withdrawn.
