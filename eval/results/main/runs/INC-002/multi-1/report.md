# Incident investigation report: INC-002
*System: multi_agent | outcome: **root_cause_identified** | ended: critic_accepted*

## Summary
The portfolio-page timeouts and api-gateway 504s were caused by config change cfg-2207, which reduced portfolio-service's JDBC pool (db.pool.max_size) from 50 to 5 at 09:52:00Z (confidence 0.85, high). Pre-existing demand of ~11.9 concurrent connections exceeded the new ceiling of 5, so the pool pinned at exactly 5.0 from the 09:53 bucket onward, producing Hikari "Connection is not available ... total=5, active=5, idle=0, waiting=43" errors and stepping p99 from ~173ms to ~4251ms on portfolio-service and, in the same bucket, to ~4419ms on api-gateway, which returned 504s proxying /v1/portfolio/*. The reporter's HTTP/2 gateway upgrade (dep-5220, 08:00Z) is coincidental: it preceded onset by ~1h52m and no HTTP/2/TLS error signature or gateway resource saturation exists. Shared datastores were verifiably normal across onset, ruling out a dependency-failure explanation. Any immediate mitigation should be restoring the pool size (or reverting cfg-2207); the gateway deploy is not the cause.

## Probable root cause
**cfg-2207 shrank portfolio-service JDBC pool 50→5, causing pool exhaustion → downstream timeouts → gateway 504s** -- config_change in `portfolio-service`, triggered by `cfg-2207` (confidence 0.85, high)

### H1: cfg-2207 shrank portfolio-service JDBC pool 50→5, causing pool exhaustion → downstream timeouts → gateway 504s
At 09:52:00Z infra-automation applied cfg-2207 to portfolio-service, reducing db.pool.max_size from 50 to 5. Because the pre-existing in-use connection level was ~11.9 (>5), the pool snapped to its new ceiling immediately: portfolio-service's db_pool_in_use dropped to and pinned at exactly 5.0 from the 09:53 bucket, and within ~79s (matching the 3000ms Hikari acquire timeout) portfolio-service logged HikariPool-1 'Connection is not available... total=5, active=5, idle=0, waiting=43'. Requests to /v1/portfolio/* blocked for seconds; portfolio-service latency_p99 stepped from ~173ms (09:52 bucket) to 4251ms (09:53 bucket) with flat CPU (~35%). api-gateway, which proxies to portfolio-service, logged upstream timeouts and returned 504s, its p99 stepping in the same 09:53 bucket. The gateway HTTP/2 upgrade is coincidental.

**Causal chain**

## What would change this conclusion
- Evidence that portfolio-service's db.pool.max_size was NOT actually applied as 5 (e.g. the change failed, or was overridden) — then the pool pinning at exactly 5.0 would need another explanation and H1 would lose its decisive numeric fingerprint.
- A confirmed HTTP/2 or TLS error/reset signature in the un-truncated gateway logs at 09:53Z, or a gateway-side connection/stream limit being hit, which would support the dep-5220 regression and weaken H1.
- Retrieved redis-cache metric series showing a hit-ratio collapse, eviction spike or CPU spike coinciding with 09:50-09:53Z, which would promote a dependency-degradation explanation (H3-like) back into contention.
- Evidence of ledger-db primary failover or refused connections (INFO-level logs, a failover event) coinciding with onset, reproducing the HIST-102 mechanism and making the pool exhaustion a downstream symptom.

- Recovery observed without reverting cfg-2207 (and without any corrective action), which would indicate the pool config was not the operative cause.
