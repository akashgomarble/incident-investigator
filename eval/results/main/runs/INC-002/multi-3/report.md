# Incident investigation report: INC-002
*System: multi_agent | outcome: **root_cause_identified** | ended: critic_accepted*

## Summary
The portfolio-page timeouts (INC-002, SEV-2) were caused by config change cfg-2207, which reduced portfolio-service's DB connection-pool max_size from 50 to 5 at 2026-03-10T09:52:00Z; pre-change concurrency (~11.4-12.4 avg, max 13.3 connections in use) already exceeded the new ceiling by ~2.3x, so the pool saturated at exactly 5 (active=5, idle=0, waiters 22-57), requests queued and hit Hikari's hard 3000ms acquire timeout, portfolio-service p99 stepped to ~4.1-4.3s, and api-gateway faithfully reported 504 upstream timeouts on /v1/portfolio/*. Confidence in this root cause is high (0.86, critic-accepted). The reporter's suspicion - the 08:00Z gateway HTTP/2 envoy upgrade dep-5220 - is rejected: it precedes the true onset by ~1h52m with no rollback, gateway CPU and p99 were flat until 09:53/09:54Z, the 504s are attributed downstream to portfolio-service, and a transport change cannot produce JDBC pool exhaustion pinned at the new ceiling. Shared ledger-db/redis-cache degradation is contradicted: slow_queries, CPU and replication lag are flat, redis connected_clients is flat, and ledger-db connections_active decreased (61.8 -> 54.5, the wrong direction). The immediate mitigation is to revert cfg-2207.

## Probable root cause
**portfolio-service DB connection-pool shrink (cfg-2207) exhausted the pool** -- config_change in `portfolio-service`, triggered by `cfg-2207` (confidence 0.86, high)

### H1: portfolio-service DB connection-pool shrink (cfg-2207) exhausted the pool
cfg-2207 set portfolio-service db.pool.max_size from 50 to 5 at 09:52:00Z ('cost-optimisation profile small', author infra-automation). Pre-change baseline concurrency (~11.4-12.4 avg, max 13.3 connections in use) already EXCEEDED 5 by ~2.3x, so the reduced ceiling caps the pool below unchanged demand. The Hikari pool saturates (total=5, active=5, idle=0, waiting 22-57), acquire attempts queue and hit the hard 3000ms timeout; portfolio-service latency steps to ~4.1-4.3s and api-gateway faithfully reports 504 upstream timeouts on /v1/portfolio/*. The recorded 09:48 onset of F8 is a coarser-bucket edge artifact: at 1-minute resolution the gateway is flat through 09:53:00Z and steps at 09:54:00Z (F32), portfolio-service p99 steps at 09:53:00Z (F34), both AFTER cfg-2207's 09:52:00Z stamp. The pool shrink is the last and only change on the portfolio path immediately at onset; it is not amplification of an upstream slowdown (request_rate flat, waiting bounded, in_use pinned exactly at the new ceiling, ledger-db/redis-cache flat).

## Data gaps
- No ledger-db query-latency or error_rate metric exists (only connections_active, cpu_pct, disk_used_pct, replication_lag_ms, slow_queries_per_min), so DB-side query latency/errors could not be measured directly; ledger-db health rests on slow_queries_per_min and replication_lag_ms proxies.
- No db_pool_waiting, db_pool_idle or db_pool_max_size metric exists for portfolio-service; waiters (22-57), idle=0 and the ceiling of 5 were recovered only from Hikari log lines and the exact 5.0 saturation pin, not from a max_size time series.
- redis-cache hit_ratio_pct, evictions_per_min and cpu_pct were never retrieved (tool budget exhausted), so the H3 rejection for redis-cache is partial - a hit-ratio collapse or eviction spike at 09:52Z cannot be excluded, though it would not by itself produce JDBC pool exhaustion on portfolio-service.
- No HPA/scale/autoscale event query was available, so the absence of a scal-ing event affecting portfolio-service between 08:00Z and 09:52Z could not be verified by direct query (config and deployment absence were verified).
- The config API exposes only a single changed_at field with no apply/reload/audit record, so the effective pool-rebuild timestamp for cfg-2207 cannot be separated from the 09:52:00Z stamp by tooling; only telemetry bracketing (09:50 partial bucket, 09:55 pin) is available.
- No metric resolution finer than 60s exists, and the 09:52Z db_pool_in_use bucket is a 5-minute aggregate spanning the config change, so the exact within-minute collapse from ~12 to 5 and the sub-minute ordering of config apply vs first failing request cannot be resolved.
- Gateway connection/socket/stream (envoy) metrics were never retrieved - only cpu_pct, error_rate, latency_p99_ms, memory_pct, request_rate, restarts are exposed - so the claim that dep-5220 produced no transport-tier signature at onset rests on the absence of gateway p99/error movement and downstream-attributed timeouts, not on connection metrics. Gateway memory_pct was also not retrieved.
- Neither api-gateway nor portfolio-service exposes a per-endpoint/route metric dimension, so /v1/portfolio/* could not be isolated in metrics; the 09:53 onset is measured on service-level aggregates, with the endpoint-specific corroboration coming only from the /v1/portfolio/holdings log lines.
- Telemetry for external nodes exchange-api, bank-partner-api and kyc-provider is unavailable (has_telemetry:false), and gateway ERROR-level log retrieval was truncated/level-filtered, so an unknown-signature contribution from those hops cannot be fully enumerated.
- No restarts/reload counter was sampled finely enough to confirm by metric that no process restart accompanied the pool rebuild (no per-restart event log was retrievable).

## What would change this conclusion
- Reverting cfg-2207 (db.pool.max_size back to 50) fails to clear the saturation: if db_pool_in_use stays pinned at 5 with waiters persisting and p99 stays ~4s after the revert, H1 is false and attention must shift to H2/H3.
- A redis-cache step at ~09:52Z in the unmeasured series (hit_ratio_pct collapse, evictions_per_min spike, or cpu_pct saturation) that could hold or starve portfolio-service requests would revive H3 as a co-cause.
- A ledger-db signature at onset not visible in the retrieved metrics - e.g. a query-latency spike or error burst in ledger-db logs for 09:40-10:20Z, or a failover/blip matching the HIST-102 precedent - would revive the shared-dependency hypothesis.
- Gateway-side envoy/stream/socket evidence showing connection or stream exhaustion (max concurrent streams, upstream connection resets) beginning at 09:53Z would restore H2 as a contributing cause; note a transport fault alone still cannot explain total=5/active=5 PoolExhaustion unless it induced connection-hold behavior.
- Discovery of an earlier, unlogged pool-affecting event for portfolio-service (a scale/HPA event or a config apply not returned by the registry) between 08:00Z and 09:52Z that already lowered the effective pool size or raised concurrency would break the change-to-onset ordering.
- Sub-minute telemetry showing the first Hikari acquire failure strictly BEFORE 09:52:00Z (i.e. before cfg-2207's stamp) would falsify the causal ordering, indicating the pool was already failing for another reason.
- Evidence that baseline concurrency actually stayed below 5 (contradicting the ~11.4-12.4 avg / max 13.3 pre-change db_pool_in_use) would remove H1's core mechanism, since the 5-connection ceiling would then have headroom.
- Proof that pre-change ERROR-level pool-exhaustion logs existed (contradicting zero ERRORs in 08:00-09:52Z) would show the pool was already stressed before the change and weaken attribution to cfg-2207.
