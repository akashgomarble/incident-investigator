# Incident investigation report: INC-010
*System: multi_agent | outcome: **root_cause_identified** | ended: critic_accepted*

## Summary
Settlement posting stopped because a single v2-schema OrderExecuted record at orders-3@8841207 cannot be deserialized by settlement-service, which still expects schema v1 ("missing required field 'qty' (schema v1 expected, header says v2)"); the record is retried under a "partition blocked" state, pinning partition orders-3, so commits/throughput collapse to ~0.4 req/s and aggregate lag climbs monotonically to ~61.6k with no recovery after ~136 minutes (H1, confidence 0.62, the only hypothesis consistent with the full evidence set). The producer is structurally pinned to order-service v2.16.0 (deployed 2026-05-12T07:40Z), the only in-window deployment across all services, whose declared changes are exactly qty->quantity, +venue, and the v2 header; no other producer or earlier order-service deploy/config exists on topic 'orders'. Competing hypotheses are positively contradicted: H2 by zero rebalance/poll-timeout/max.poll.interval log entries, H3 by flat broker ingest (~2535 msg/s) with zero under-replicated partitions plus two unaffected co-tenants, H4 by growing lag with healthy producer throughput, H5 by the absence of any downstream error/latency signal and an error signature that names one exact partition/offset. Confidence is capped because two hops remain inferred rather than observed: that v2 bytes were on the wire at/just before the 07:36-07:40Z break (no schema-registry timestamp, no canary/rollout record, no producer emission evidence), and that the record hard-blocks rather than skip-and-continues (no per-partition committed-offset telemetry exists).

## Probable root cause
**order-service v2.16.0 schema change emits an undecodable v2 record that poison-blocks partition orders-3** -- bad_deployment in `order-service`, triggered by `order-service v2.16.0 (2026-05-12T07:40:00Z)` (confidence 0.62, medium)

### H1: order-service v2.16.0 schema change emits an undecodable v2 record that poison-blocks partition orders-3
order-service v2.16.0 (the only in-window deploy, F1/F25/F26) changed the OrderExecuted schema (qty->quantity, +venue, version header v2). settlement-service, still expecting v1, cannot deserialize the first v2 message on partition orders-3 at offset 8841207; the record is retried indefinitely ('poison message ... partition blocked'), the partition never advances, consumption/commits stall, settlement throughput collapses to ~0.4 req/s, and aggregate consumer lag grows monotonically to ~61k.

**Causal chain**
1. order-service v2.16.0 (the only deployment in-window, and the only producer-graph producer on 'orders' besides payment-service) ships the OrderExecuted schema v2: qty->quantity, add field venue, version header v2 [F1, F25, F26, F27]
2. order-service begins emitting v2 messages onto topic 'orders' at/around the 07:40Z deploy *(assumed)*
3. settlement-service consumer still expects v1 and fails to deserialize the v2 record: 'missing required field qty (schema v1 expected, header says v2)' [F9, F10, F30, F32]
4. The offending record at orders-3@8841207 is retried continuously and reported as 'poison message ... partition blocked', so the partition makes no forward progress [F9, F30, F31, F34, F35, F38, F39]
5. Consumption halts: settlement request_rate collapses from ~62 to ~0.4 req/s and stays pinned with no recovery [F8, F40]
6. Aggregate consumer lag grows monotonically while the producer and broker keep flowing at a healthy rate [F7, F17, F22, F33, F40]
7. The same offset 8841207 is re-read for ~136 min (07:42:14Z-09:58:31Z) with attempt counters reaching tens of thousands, the strongest available substitute for a frozen committed offset [F31, F33, F35, F39]
