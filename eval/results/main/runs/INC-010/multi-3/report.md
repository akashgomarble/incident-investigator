# Incident investigation report: INC-010
*System: multi_agent | outcome: **root_cause_identified** | ended: critic_accepted*

## Summary
Top hypothesis H1 (confidence 0.72, medium): order-service deployment dep-6010 (v2.16.0) shipped a breaking OrderExecuted schema change (qty renamed to quantity, header bumped to v2) that settlement-service's v1 deserializer rejects, causing an uncommitting poison-message retry loop on partition orders-3 and zero settlements posted. The mechanism is strongly evidenced: the only two changes in 24h are cfg-3004 (07:35:37Z) and dep-6010 (07:40:01Z); lag is provably flat in the 4 minutes after the config change and jumps in the 07:42 bucket, ~1-2 min after dep-6010 completed; and all 409 ERROR entries begin at 07:42:14Z citing 'missing required field qty (schema v1 expected, header says v2)' on a single pinned offset orders-3@8841207. Competing hypotheses (poll-settings stall, broker/partition fault, producer burst, shared-dependency failure) are each contradicted by mechanism-consistent evidence. The residual weakness is that the producer→topic hop is established from consumer-side error content plus timing rather than producer telemetry (order-service exposes no produced-messages metric and logs no explicit v2 emission), which caps but does not block the verdict.

## Probable root cause
**Order-service v2 breaking schema change poisons settlement-service consumer** -- bad_deployment in `order-service`, triggered by `dep-6010` (confidence 0.72, medium)

### H1: Order-service v2 breaking schema change poisons settlement-service consumer
order-service deployment dep-6010 (v2.16.0) shipped a breaking OrderExecuted event schema (qty renamed to quantity, header bumped to v2). settlement-service is still on schema v1 and its deserializer rejects the v2 message at offset orders-3@8841207 ('missing required field qty'). The consumer enters an uncommitting hot retry/poison-message loop on partition orders-3, blocking the partition, so zero settlements post and consumer lag climbs. The mechanism is strongly evidenced by timing and error content; the producer->topic hop remains inferred (no per-topic routing, no producer-side v2 emission log).

**Causal chain**
1. order-service deploys dep-6010 (v2.16.0) with breaking event schema: qty->quantity, added venue, header schema version v2 [F1, F2]
2. order-service produces these new-format events onto the shared kafka topic; settlement-service consumes a topic off that same shared broker [F3, F4, F24]
3. dep-6010 rollout completes 07:40:01Z, ~1 min before the lag jump bucket and ~2 min before first settlement error — tightest temporal match [F16]
4. settlement-service (schema v1) fails to deserialize the v2 message at orders-3@8841207 [F10, F17]
5. Poison message blocks partition orders-3 with a hot, non-monotonic retry loop; CPU step-changes to ~68-71% in-process, no restarts/DB churn [F13, F11, F18]
6. Blocked partition => request_rate collapses to ~0.4 req/s and lag climbs to ~60k; service HTTP 5xx stays flat (failures are consumer-side only) [F9, F8, F12]
