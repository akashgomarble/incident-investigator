# Incident investigation report: INC-009
*System: multi_agent | outcome: **root_cause_identified** | ended: critic_accepted*

## Summary
Root cause identified with high confidence (0.80): portfolio-service v4.5.0 (dep-5905, deployed 2026-05-05T08:56Z by k.shah) introduced a new unindexed query on trades filtered by account_id + executed_at against the shared ledger-db, executed as a sequential scan over ~48.2M rows on every call. That scan is the single slow-query signature in ledger-db's log over 08:45-11:00Z (360 occurrences, first at 08:58:38Z), and it accounts for the CPU step from ~30% to ~96%, the slow-query rate step from ~1/min to ~140/min, and ~190 held active connections all at the 08:58 minute. This contention starves order-service's INSERT INTO orders path, driving db_pool_in_use from ~14 to ~46 and p99 from ~150ms to ~5s with statement timeouts starting 09:00:42Z. The reported DBA autovacuum change (cfg-2903, 08:00Z) is a red herring: it produced no observable vacuum activity on trades/orders, and the storm post-dates it by ~58 minutes with no mechanical effect. order-service itself had no deployment or config change in the week.

## Probable root cause
**portfolio-service v4.5.0 unindexed trades query saturates shared ledger-db and starves order-service writes** -- bad_deployment in `portfolio-service`, triggered by `dep-5905` (confidence 0.80, high)

### H1: portfolio-service v4.5.0 unindexed trades query saturates shared ledger-db and starves order-service writes
The sole deployment in the window, portfolio-service v4.5.0 (dep-5905, 08:56Z), introduced a new unindexed query on trades filtered by account_id + executed_at against the shared ledger-db. That query executes as a sequential scan over ~48.2M rows on each call, driving ledger-db CPU to ~96% and slow queries from ~1/min to ~140/min and holding ~190 active connections. ### H3: ledger-db infrastructure/resource failure (IOPS throttling or volume IO) independent of both changes
The shared ledger-db's underlying storage hit an IOPS/burst-credit or IO-throttling limit, throttling all queries and producing the CPU/slow-query/connection step change; order-service's timeouts are downstream. Same mechanism as HIST-110.

**Causal chain**
1. Ledger-db underlying volume IOPS throttled (burst credits exhausted) *(assumed)*
2. Throttled IO drives slow queries ~1/min -> ~140/min and CPU to ~96% [F11, F9]
3. Throttled/contended DB blocks order-service writes -> statement timeouts and 5s p99 *(assumed)*

**Supporting evidence**
  - `F6` ✔ Precedent lead only: HIST-110 (2026-01-15) had the identical symptom set — order-service + ledger-db, 'order latency','statement timeouts','slow queries' — but its recorded root cause was 'Cloud volume burst credits exhausted; IOPS throttled', fixed by moving to provisioned IOPS, not by autovacuum. HIST-111 (2025-05-22) shows a related pattern on the same DB: an unindexed new report query caused sequential scans and slowed ledger-db.
