# Incident investigation report: INC-006
*System: multi_agent | outcome: **root_cause_identified** | ended: critic_accepted*

## Summary
Root cause identified with medium-high confidence: redis-cache lost its entire dataset at ~13:22Z (hit_ratio 95.9%→10.8%, memory_pct 71.4%→6.1% with slow refill, connected_clients 312.9→41.8 with reattach, all at flat redis CPU ~22% and with no eviction signature), producing a cache-miss storm that drove market-data-service into rebuild-from-exchange loops (6.8–8.1s each) and CPU saturation (~46%→90% with flat memory), so its synchronous responses to pricing-engine exceeded deadline and quotes slowed to 2–3s. The verified evidence is a server-side data-emptiness event at the shared redis-cache node — the only shared=true component called by both pricing-engine and market-data-service — and cannot be produced by an app-side cache client, which leaves the runner-up hypothesis (market-data internal resource pressure primary) unsupported. pricing-engine, api-gateway and downstream screens are victims; exchange-gateway and order-service are exonerated by flat latency/error/traffic, and no code or config change coincides with onset. Residual uncertainty is limited to which cache-side sub-variant caused the emptiness (restart vs failover/empty-replica promotion vs FLUSH), because redis-cache exposes no uptime/restart/replica/keyspace metrics; the mechanism and the mitigation are identical across sub-variants.

## Probable root cause
**redis-cache emptied (restart/failover/empty-replica promotion) → cache-miss storm → market-data CPU saturation → quote latency** -- infrastructure_failure in `redis-cache` (confidence 0.72, medium)

### H1: redis-cache emptied (restart/failover/empty-replica promotion) → cache-miss storm → market-data CPU saturation → quote latency
The fault originates in redis-cache: at ~13:22Z the cache instance lost its entire dataset (memory_pct collapsed 71.4%→6.1%, hit_ratio 95.9%→10.8%, connected_clients 312→42 with reattach) while CPU stayed flat — the signature of a restart/flush/empty-replica promotion, NOT eviction or load. With quote:<n> keys gone, market-data-service is forced into rebuild-from-exchange-feed loops (6.8-8.1s each), driving its CPU to ~90%; its synchronous responses to pricing-engine then exceed the deadline, so quotes take 2-3s. This is the HIST-107 'cold cache storm after redis failover' mechanism.

**Causal chain**
1. At ~13:22Z redis-cache loses its whole keyspace — memory_pct 71.4%→6.1% (refills slowly to 16.5% by 14:00Z), hit_ratio 95.9%→10.8%, connected_clients 312.9→41.8 then reattach to ~300-320 by 13:26Z — while cpu_pct stays flat 20-24%. An instant, near-total emptiness with flat CPU rules out eviction/saturation and matches a restart, FLUSH, or empty-replica full-resync. [F26, F27, F28, F29, F31]
2. With quote:<n> keys absent, market-data-service emits the cache-miss storm: 'quote:<n> not in redis-cache, rebuilding from exchange feed snapshot (6864-8100ms)', 289 occurrences, first line 13:22:25Z — seconds AFTER the redis step. [F11, F13]
3. The synchronous rebuild work drives market-data-service CPU from ~46% to 89.8% avg / 94% max at 13:22Z (staying 78-87%) with p99 stepping 39.8ms→1917ms, while its memory_pct stays flat (~58.8%) — so the CPU spike is rebuild work, not GC/allocator pressure. [F10, F30, F31]
4. pricing-engine's outbound calls to market-data-service stretch to 8456ms, producing the single ERROR pattern 'quote computation deadline exceeded: market-data-service took <n>ms' (192 outbound errors, first 13:23:57Z). [F9, F12]
