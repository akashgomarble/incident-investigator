# Incident investigation report: INC-004
*System: multi_agent | outcome: **root_cause_identified** | ended: critic_accepted*

## Summary
The three OOMKilled restarts of notification-service are best explained by H1 (confidence 0.72, medium): the in-memory TemplateCache introduced in notification-service v3.8.0 (dep-5402, 2026-03-21T00:00Z) causes a deterministic, load-independent live-heap accumulation that fills the pod in ~22h and triggers a periodic OOM restart. This is supported by a new, near-linear ~0.037%/min memory sawtooth with identical ~46–50% post-restart baselines across all three cycles that begins only after the deploy (F31–F34), by old-gen heap WARNs with rising full-GC pauses immediately preceding the OOM (F17), and by flat CPU and request rate throughout the ramp (F36). The reporter's Kafka-replay theory (H2) is rejected: Kafka's own telemetry is flat (cpu, messages_in_per_s, under-replication), no replay/restart appears in Kafka logs, and the other observable Kafka consumer shows no lag spike or WARNs. The final hop — that the accumulating allocation is specifically the unbounded/unevicted TemplateCache rather than another allocation in the same commit (H5) — remains unproven because no artifact body or cache-size metric is obtainable, which is why confidence is capped below 0.85.

## Probable root cause
**In-memory template cache (v3.8.0) leaks memory, filling the heap until periodic OOM** -- bad_deployment in `notification-service`, triggered by `dep-5402` (confidence 0.72, medium)

### H1: In-memory template cache (v3.8.0) leaks memory, filling the heap until periodic OOM
notification-service v3.8.0 (dep-5402, 2026-03-21T00:00Z) introduced an in-memory TemplateCache (ConcurrentHashMap keyed by template+locale+userSegment). Post-deploy, the pod exhibits a NEW deterministic memory sawtooth: from an identical ~46-50% post-restart baseline, heap climbs monotonically at ~0.037%/min for ~22h until it reaches ~98% and the container is OOMKilled, then repeats. The ramp is uncorrelated with load (cpu/request_rate flat, F36) and begins only after the deploy (F34), so the growth is a fixed-rate accumulation internal to the service — consistent with cache entries (or another per-render allocation added in the same commit) accruing without eviction. The mechanism that the accumulation is specifically the TemplateCache and that the cache lacks eviction remains UNPROVEN (no code artifact, no cache-size metric).

**Causal chain**
1. dep-5402 (v3.8.0) deployed 2026-03-21T00:00Z adds an in-memory TemplateCache (ConcurrentHashMap keyed by template+locale+userSegment) via the render path; no eviction/TTL/size/TTL parameter is recorded [F1, F8, F19, F20, F21, F22]
2. Immediately after 03-21T00:00Z the memory profile changes from a flat ~47-50% baseline to a new monotonic linear ramp that did not exist in the prior 7h+ [F33, F34]
3. Each inter-restart interval shows the identical baseline (~46-50%) and the identical slope (~0.037%/min ≈ +1.85pp/95min) sustained over ~22h, i.e. a deterministic accumulation rather than a load-driven one [F31, F32]
4. Load indicators are flat during the ramp (cpu ~24-26%, request_rate ~128-143 req/s), so the growth is not driven by volume/fan-out [F36]
5. Old-gen heap fills; full-GC WARNs with escalating pauses (4152ms→6488ms) recur immediately before the OOM, indicating the growth is reclaiming-resistant (live) heap [F17]
6. Heap exceeds the pod memory limit → container OOMKilled (exit 137) → restart resets memory_pct to ~46% [F13, F14, F16]
7. After each restart the accumulation restarts and reaches the limit again ~22-23h later, reproducing the cycle (3 OOMs: 03-21T22:59Z, 03-22T21:59Z, 03-23T19:59Z) [F13, F14, F31, F32]
8. Consumer lag and email delays are secondary effects of the pod being GC-throttled/down for the 24h before each restart, not the cause [F15, F36]
