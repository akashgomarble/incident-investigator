# Incident investigation report: INC-004
*System: multi_agent | outcome: **root_cause_identified** | ended: critic_accepted*

## Summary
The three OOMKilled (exit 137) restarts of notification-service are caused by an unbounded in-memory TemplateCache introduced by dep-5402 v3.8.0 on 2026-03-21T00:00Z (H1, confidence 0.84, high). The leak is directly measured, not inferred: the only cache-instrumentation surface shows the cache growing monotonically 51,750 -> 196,650 entries at ~5h45m intervals with evictions=0, and it collapses to near-zero only immediately after each OOM restart, in lockstep with the memory_pct sawtooth (47-48% -> 98.44% -> reset). Temporal order and scope both point the same way: the first anomalous memory rise begins at the deploy boundary after a flat Mar 20, and only notification-service sawtooths and restarts while the sibling consumers of the same shared Kafka (settlement-service, order-service) stay flat with zero restarts. The reporter's Kafka-replay theory (H2, rejected) is defeated by the fact that two of the three OOMs predate today's 18:00Z retention change. Residual, non-blocking weaknesses keep confidence below 0.9: the growth onset at the deploy instant is an emission-onset argument rather than a measured 00:00 cache datapoint, and the container memory limit / -Xmx is unreadable from every surface tried, so H5 (shrinking headroom) is excluded by absence-of-record rather than by a measured fixed ceiling.

## Probable root cause
**Unbounded in-memory TemplateCache leak introduced by dep-5402 v3.8.0** -- bad_deployment in `notification-service`, triggered by `dep-5402` (confidence 0.84, high)

### H1: Unbounded in-memory TemplateCache leak introduced by dep-5402 v3.8.0
notification-service's dep-5402 v3.8.0 (2026-03-21T00:00Z, 'Add in-memory template cache for email rendering') introduced an unbounded TemplateCache (ConcurrentHashMap keyed by template+locale+userSegment) on the render path with no eviction. Distinct keys accumulate linearly, resident memory climbs until the container hits its ceiling, and the kernel OOM-kills it (exit 137). The ~22-23h OOM cadence is the time for the cache to refill the container from baseline to the ceiling; the restart is the only mechanism that resets the cache. The leak is verified by direct measurement; the exact onset instant is inferred from the RSS curve because cache logs begin ~5.75h after the deploy, and the ceiling value itself (container limit / -Xmx) is unmeasured.

**Causal chain**
1. dep-5402 v3.8.0 deploys an in-memory TemplateCache on the email render path at 2026-03-21T00:00Z; it is still live and was not rolled back [F2, F23, F37]
2. The first anomalous memory rise begins exactly at the 2026-03-21T00:00Z boundary, after memory was flat ~47-48% through all of 2026-03-20 (inference from the RSS curve, not from a cache datapoint at 00:00) [F10, F9, F44]
3. Cache logs do not exist before the deploy and begin at 2026-03-21T05:45:44Z (first-ever line = 51,750 entries, evictions=0), so emission onset is consistent with cache creation at the deploy, though no numeric 00:00 reading exists [F35, F36, F38, F39]
4. The TemplateCache itself grows monotonically and linearly with evictions=0: 51,750 -> 103,500 -> 155,250 -> 196,650 entries at ~5h45m intervals across the whole window [F29, F30]
5. Cache growth tracks the container RSS climb; the only WARN in the window is old-gen heap pressure ('heap usage >90% (old gen), full GC took Nms'), beginning ~1.4h before the first OOM and recurring before each subsequent one [F32, F43, F9]
6. The cache resets to near-zero after each OOM restart, in lockstep with the RSS sawtooth — the restart is the only reset mechanism for the cache [F31, F33]
7. The container is OOMKilled (exit 137) three times, at ~21:59-22:59 daily on three consecutive days; two of the three predate today's Kafka maintenance [F7, F8]
8. Consumer lag spikes coincide with each OOM cycle rather than running continuously high, so lag is a consequence of the restart/backlog, not its cause [F11]
9. Scope test: only notification-service shows the sawtooth and restarts; sibling consumers of the same shared kafka (settlement-service, order-service) are flat (44-56% / 51-67%) with zero restarts and undisturbed lag across the window [F18, F19, F20, F21]
