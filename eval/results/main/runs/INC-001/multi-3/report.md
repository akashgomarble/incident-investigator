# Incident investigation report: INC-001
*System: multi_agent | outcome: **root_cause_identified** | ended: critic_accepted*

## Summary
Order placement 500s are caused by dep-5101, the order-service v2.14.0 deploy at 12:10:00Z that added MarginCheckValidator to the validation chain and removed legacy OrderRules.validateMargin(): the new margin path dereferences a null marginProfile at MarginCheckValidator.java:88, throwing an NPE that surfaces as HTTP 500 on POST /v1/orders for F&O orders only (H1, confidence 0.74). The change is the only order-placement-touching change in 24h, precedes onset by ~2 min, and the failure is an NPE raised at the exact class/line the deploy added on the exact order type it targeted. Scope is fully closed: the unrestricted error query returns exactly 426 ERRORs resolving into exactly two signatures summing to the total (224 NPE + 202 "marginProfile is null") with no residual, and no non-FNO or non-NPE 5xx signature exists. Competing hypotheses are positively contradicted by flat CPU/connection-pool metrics (rejecting saturation) and flat ledger-db/kafka metrics with flat peer services (rejecting shared-dependency and sampling-artifact explanations). One hop remains unproven by design — whether marginProfile is locally constructed as null rather than returned null by an unregistered margin/account client — and the decisive code/config artifacts do not exist (deployment artifact has no diff; config API is empty for order-service), but this does not change the ranking or the remediation, so confidence is capped at 0.8 with H1 clearly ahead.

## Probable root cause
**order-service v2.14.0 MarginCheckValidator regression throws NPE for F&O orders** -- bad_deployment in `order-service`, triggered by `dep-5101` (confidence 0.74, medium)

### H1: order-service v2.14.0 MarginCheckValidator regression throws NPE for F&O orders
dep-5101 (order-service v2.14.0, deployed 12:10Z, rollout complete 12:10:08Z) added a new MarginCheckValidator to the validation chain and removed the legacy OrderRules.validateMargin(). Only the F&O flow populates/reaches the new margin path; the marginProfile consumed at MarginCheckValidator.java:88 is null and the new code dereferences it, throwing a NullPointerException that escapes the validation chain and surfaces as HTTP 500 on POST /v1/orders. The escalation is now firmly supported by timing (deploy precedes onset by ~2 min), code-site identity (NPE at the exact line the deploy added), and scope (ERROR set is 100% FNO with zero residual signature). The unresolved hop is *why* marginProfile is null — the evidence shows no downstream call/error context, no timeout/RPC/circuit-breaker precursor, and no log line naming a source (F25–F28), which is consistent with an in-process/local null but does not positively prove it.

**Causal chain**
1. dep-5101 deploys order-service v2.14.0 at 12:10:00Z, adding MarginCheckValidator and removing legacy OrderRules.validateMargin(); rollout complete 12:10:08Z [F1, F13, F28]
2. Only F&O orders reach the new MarginCheckValidator path (legacy margin validation removed), so only FNO order types can hit the new code [F1, F2]
3. For F&O orders the marginProfile consumed at MarginCheckValidator.java:88 is null; the new validator dereferences it with no callee/remote frame present [F9, F25, F26, F28]

### H2: marginProfile is supplied by an unlisted margin/account dependency returning null

Because no order path reaches the NPE without dep-5101, H2 is properly a code×dependency co-cause rather than a standalone alternative: the deploy introduced the exposure, a dependency (or an unregistered/misconfigured client binding) supplies the null. Decisive evidence is code/config-side (validator DI/constructor wiring, line-88 statement, presence of a registered margin/account runtime client) and was not obtainable in this round — the dependency graph returns no margin-*/account-* node or edge (F44), the config API is empty for order-service (F45), and the deployment artifact exposes no diff (F43).
