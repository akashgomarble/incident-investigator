# Incident investigation report: INC-007
*System: multi_agent | outcome: **inconclusive** | ended: critic_inconclusive*

## Summary
The incident is real and well characterized: auth-service error_rate stepped hard from ~0.2% to ~36-37% between 14:00:00Z and 14:02:00Z (fast-failing 401 invalid_token on /v1/token/validate), with flat latency, CPU, request rate and restart count (F7, F8, F10, F11, F13, F14, F15, F16, F17). Exactly two auth-service changes land inside that onset bucket — deploy dep-5710 v7.3.0 at 14:00:00Z and the jwt.signing.key_id rotation k-2025-10 -> k-2026-04 at 14:01:00Z — and 60 seconds apart with the first failure logged at 14:02:22Z, temporal order cannot separate them (F1, F2, F3, F21, F42). After three review rounds the top hypotheses H1 (stale/rotated key id), H2 (jjwt 0.11->0.12 parser rewrite) and H3 (partial rollout explaining the constant ~1/3 fraction) remain statistically tied at low confidence (0.33/0.33/0.32), and H6 remains live at 0.18; the two decisive discriminators do not exist in reachable data — gateway logs carry exactly ONE collapsed failure pattern with no key-id/JWKS/parser text, no ERROR-level entries, and no sibling service surfaces detail (F37, F38, F39, F41), auth-service logs are unreachable (F40), and no source exposes per-pod/instance/revision state or a JWKS/active-key-id view (F22, F25-F28, F30, F45, F46, F48). The dependency branch is the one thing that was actually measured and cleared: redis-cache and user-db are flat across onset (F32, F33, F34, F35, F36), so this is auth-service-local. Conclusion: inconclusive — the fault is not a shared-dependency fault, but the key-rotation, parser-upgrade and partial-rollout explanations cannot be separated with the evidence available.

## Probable root cause
**Inconclusive** -- the evidence does not single out one cause. See ranked hypotheses and data gaps.

### H1: JWT signing-key rotation publishes k-2026-04 while some validators still hold the stale key id
The scheduled signing-key rotation at 14:01Z swapped jwt.signing.key_id k-2025-10 -> k-2026-04 while part of the auth-service fleet still resolved tokens against the previous key id, so those validations rejected otherwise-valid tokens as invalid_token, producing a partial (~1/3) fast-fail 401 rate. HIST-108 mechanism. NOTE: the change record evidences only ONE key-id transition (F23/F44); the stale-cache / two-key premise is assumed, not observed, and no JWKS/key-store state is queryable (F45/F48).
