# Incident investigation report: INC-003
*System: multi_agent | outcome: **root_cause_identified** | ended: critic_accepted*

## Summary
Root cause identified: the external exchange partner (api.exchange-partner.example, reached via exchange-api/exchange-gateway) became unresponsive starting ~11:01Z, producing 5000ms upstream connect timeouts and 503s at exchange-gateway, which surface as 504s on order-service's submit path (~30% error rate, p99 ~150ms -> ~4.3s). Confidence is medium (0.78): the downstream chain, the caller-independent blast radius (order-service and market-data-service, the gateway's two independent callers, both degrade in the 11:01Z bucket while non-callers stay flat) and the absence of any gateway-internal resource saturation (CPU/memory/request_rate flat, zero restarts, only upstream_latency_ms exploding 120ms -> ~9000ms) are all observed; the final hop is inferred because exchange-api has has_telemetry:false. The order-service v2.15.2 release (dep-5333) and the pricing-engine cfg-2290 change are not the cause: the release cannot produce failures in two other never-deployed services, and its 11:16Z rollback did not restore service. Shared platform components (ledger-db/redis-cache/kafka) are contradicted or off the failing call path. Do not expect the rollback to have fixed this — the remediation is exchange route failover, not order-service rollback.

## Probable root cause
**External exchange partner / exchange-api outage causing exchange-gateway upstream timeouts** -- dependency_failure in `exchange-api / external exchange partner (via exchange-gateway)`, triggered by `null` (confidence 0.68, medium)

### H2: External exchange partner / exchange-api outage causing exchange-gateway upstream timeouts
The external exchange provider (api.exchange-partner.example / exchange-api) degraded at ~11:01Z, causing 5000ms upstream connect timeouts and 503s at exchange-gateway, which surface as 504s on order-service's submit path and as stale-quote warnings / elevated error rate (but not latency) at market-data-service. Residual uncertainty: the failing hop is beyond exchange-api (has_telemetry:false), so the partner-side origin is inferred from exchange-gateway's upstream_latency_ms proxy, not directly observed.

**Causal chain**
1. exchange-gateway's upstream call to the external partner stalls: 'upstream connect timeout after 5000ms host=api.exchange-partner.example op=placeOrder' from 11:01:25Z, then 'exchange-api returned 503' from 11:02:20Z; circuit breaker OPEN at 11:03:26Z. [F9]
2. exchange-gateway p99 latency jumps ~130ms -> 4625ms avg and error rate to ~44.7% steady, dominated by the stuck 5000ms upstream call. [F10]
3. The latency is on exchange-gateway's upstream_latency_ms (120ms -> ~7450-9500ms) while its own cpu (~27-32%), memory (~40-49%), request_rate (~272 req/s) and restarts (0) stay flat across onset -> the stall originates outside the gateway process, not from internal resource saturation. [F29, F24, F25, F26, F27]
4. exchange-gateway had zero deployments and zero config changes in the preceding week, and no deployment/config change occurred for ANY service in the 10:50-12:59 onset window -> no internal change introduced the fault and the shared platform components were untouched. [F14, F16, F17, F19, F23]
5. A second, structurally independent caller of exchange-gateway degrades on the same 11:01 bucket: market-data-service error_rate 0.24% -> ~6.5% with its sole log signature 'stale quotes ... via exchange-gateway'; it shares no datastore with exchange-gateway. (Severity differs: its own p99 stays ~40ms flat and it emitted zero ERROR logs, so the shared element is the exchange-gateway/exchange-feed path, not an identical failure mode.) [F30, F31, F32, F33, F15, F35]
6. order-service, calling exchange-gateway for placeOrder, receives 504 Gateway Timeout -> ~30% error rate and 4286ms p99, all 349 error logs being the single downstream-blaming signature. [F8, F7]
7. order-service v2.15.2 rollback at 11:16Z did not restore service; errors persisted to 12:58Z, consistent with an external cause the rollback cannot touch. [F13, F1]
