# Evaluation

How the two systems were judged, what was measured, the results, and what the numbers do not show.
Every table here is generated by `python eval/run_eval.py`; the generated copies, the per-run
reports and the full traces are under `eval/results/`.

The numbers below are the final round (`v4` and `stress`, 20 Nov 2026). Earlier rounds are
summarised under "History".

The outcome rule was tightened after these runs (third review): a team run that stops while the
Critic is still asking for evidence, or before any review finished, is now reported as
"inconclusive". Replaying that rule on the saved traces changes no `v4` outcome. In `stress` it
turns two correct team answers into abstentions (22/24 becomes 20/24). The tables below are the
runs as they were made.

## Method

**One layer: code scoring against an answer key.** Each incident has a `ground_truth.json` that the
agents cannot reach (their tools read only logs, metrics, deployments, config changes, topology and
past incidents). After a run, `eval/scoring.py` compares the report with it. No model is involved
in scoring.

| Measure | Definition |
|---|---|
| Root-cause accuracy | Outcome is "identified", and the top hypothesis names an accepted service and an accepted category. For the undeterminable incident: the outcome is "inconclusive" and the run formed at least one hypothesis (a run that failed before weighing any suspect gets no credit). |
| Wrong but stated as identified | Outcome is "identified" and the answer is wrong. The costly error for an on-call engineer. |
| Abstained although answerable | Outcome is "inconclusive" on an incident that has a determinable cause. |
| Triggering change identified | The top hypothesis carries the exact deployment or config id from the answer key. |
| Cited findings verified | Share of findings cited anywhere in the report whose quote is present in the cited tool output. |
| Causal-chain hops grounded | Share of steps in the top hypothesis's causal chain backed by a verified finding. |
| Key-evidence recall | Share of the answer key's decisive strings (an id, an error message) that appear in the cited findings. |
| Cost | Tool calls, model calls, tokens and wall-clock time per incident. |

**No model judge and no human labels.** With an answer key, the main number needs neither. The cost
of that choice: nothing scores the quality of the prose summary or of the recommended actions. See
"What the evaluation does not tell you".

**Systems compared**, all with the same model, tools, scripted faults, budgets, evidence rules and
scorer:

- `multi`: the six-agent team.
- `single`: one agent with all six tools, up to 16 model turns.
- `nocritic`: the team with the Critic removed (one pass, no review; code caps confidence at 0.6 as
  unreviewed). An ablation, to see what the review loop buys.
- A scripted "blame the most recent change" rule, as a floor: it scores 3 of 12.

**Model.** `deepseek-ai/DeepSeek-V4.1-Flash` for every agent in every system.

## Test cases

12 synthetic incidents on one simulated trading platform ([DATASET.md](DATASET.md)). Eleven have a
determinable cause; INC-007 is built so that "inconclusive" is the only correct answer. Most carry
a trap: a reporter who suspects the wrong thing (6), an innocent deployment or config change close
to the onset (8), a symptom that shows in a different service from the cause (5), or a misleading
past incident (2). Four have tool failures scripted in.

## Results

### Headline (`v4`: 12 incidents, 3 trials each, no random faults)

| | Team | Single agent | Team without Critic |
|---|--:|--:|--:|
| Root-cause accuracy | 89% (32/36) | 94% (34/36) | 86% (31/36) |
| 95% interval | 75%-96% | 82%-98% | 71%-94% |
| Wrong but stated as identified | 0 runs | 2 runs | 1 run |
| Abstained although answerable | 4 runs | 0 runs | 4 runs |
| Correct on the undeterminable incident | 3/3 | 1/3 | 3/3 |
| Correct service ranked first | 100% | 100% | 94% |
| Triggering change identified | 83% | 100% | 89% |
| Cited findings verified | 99% | 100% | 99% |
| Causal-chain hops grounded | 96% | 99% | 93% |
| Key-evidence recall | 90% | 94% | 81% |
| Mean stated confidence | 0.68 | 0.84 | 0.55 |
| Tool calls per incident | 44.6 | 23.4 | 23.1 |
| Model calls per incident | 27.3 | 6.0 | 12.8 |
| Tokens per incident | 224,553 | 84,673 | 81,706 |
| Latency per incident, mean | 280 s | 71 s | 128 s |

Generated table: [`eval/results/v4/EVAL_RESULTS.md`](../eval/results/v4/EVAL_RESULTS.md).

**Reading it.** The three intervals overlap, so accuracy does not separate the systems at this
sample size. The single agent is as accurate as the team or better, at 38% of the tokens and a
quarter of the latency. The team does not earn its cost on accuracy.

**The two systems fail in opposite directions.**

- *The team's four misses are all abstentions.* It ranked the correct service first every time and
  then answered "inconclusive": INC-008 twice, INC-003 once, INC-006 once. It never named a wrong
  cause.
- *The single agent's two misses are both confident and wrong.* On INC-007, where two changes land
  at the same moment and the data to separate them is permanently unavailable, it named a root
  cause in 2 of 3 runs (confidence 0.62 and 0.55). The team answered "inconclusive" 3 of 3.

Two runs are too few to size this, and in the previous round the single agent got INC-007 right 3
of 3. It is the direction the design predicts, and it is not established.

### What the Critic buys (ablation)

| | Team | Team without Critic |
|---|--:|--:|
| Root-cause accuracy | 89% (32/36) | 86% (31/36) |
| Wrong but stated as identified | 0 | 1 (INC-006, blamed a downstream service) |
| Key-evidence recall | 90% | 81% |
| Causal-chain hops grounded | 96% | 93% |
| Tokens per incident | 224,553 | 81,706 |
| Latency per incident | 280 s | 128 s |

The review loop accounts for 64% of the team's tokens. It buys three points of accuracy (one run,
inside the noise), nine points of evidence recall, and one fewer wrong claim.

The more useful comparison is the ablation against the single agent. The two cost the same (82k and
85k tokens), and the single agent is more accurate (94% against 86%). Splitting the work across
specialists therefore loses something that one agent holding the whole context keeps, and the
Critic spends 2.7 times the tokens to win part of it back.

### Under random tool faults (`stress`: 12 incidents, 2 trials each)

30% of tool calls fail once (a retry succeeds). 10% of distinct calls fail on every attempt, so
retries cannot hide them. The fault pattern differs per trial.

| | Team | Single agent |
|---|--:|--:|
| Root-cause accuracy | 92% (22/24) | 100% (24/24) |
| 95% interval | 74%-98% | 86%-100% |
| Wrong but stated as identified | 0 | 0 |
| Random faults injected per incident | 27 | 14 |
| Calls recovered by a retry, per incident | 10.9 | 5.5 |
| Calls that still failed after retries, per incident | 9.0 | 4.0 |
| Calls refused by the circuit breaker, in total | 28 | 8 |
| Key-evidence recall | 96% | 90% |
| Tokens per incident | 236,507 | 84,597 |

Generated table: [`eval/results/stress/EVAL_RESULTS.md`](../eval/results/stress/EVAL_RESULTS.md).

Neither system lost accuracy against its own fault-free result, neither stated a wrong cause, and
no run crashed. Both go through the same tool executor (retries, time limit, circuit breaker), so
this shows the executor and the "record a gap" behaviour work. It does not show the team handling
faults better than the single agent.

### Is stated confidence informative?

Correct runs out of runs, by the confidence stated for the top hypothesis, `v4` and `stress` pooled:

| Stated confidence | Team | Single agent |
|---|--:|--:|
| 0.75 and above | 20/20 | 51/51 |
| 0.50 to 0.74 | 30/33 | 6/8 |
| below 0.50 | 4/7 | 1/1 |

Every high-confidence answer from either system was correct. The middle band is where the errors
are. In the lowest band a correct run is one that rightly answered "inconclusive". This is a
ranking check, not calibration: the bands are too thin to say that 0.7 means 70%.

### History

| Round | Code | Team | Single agent |
|---|---|--:|--:|
| `main` | first version | 94% (34/36) | 100% (36/36) |
| `v2` | after one prompt fix; single-agent runs reused from `main` | 100% (36/36) | 100% |
| `v3` | after the first code review | 97% (35/36) | 100% (36/36) |
| `v4` | after the second code review | 89% (32/36) | 94% (34/36) |

Both systems scored lower in `v4` than in `v3`. Three things changed between them and the data
cannot separate them: the second code review's fixes, the provider's behaviour on the day (mean team
latency rose from 180 s to 280 s with the same concurrency), and run-to-run variation. The `v3` and
`v4` intervals overlap for both systems.

One pattern is specific: INC-008 (capacity ran out with no triggering change) went from 3 of 3 for
the team in `v3` to 1 of 3 in `v4` and 1 of 2 in `stress`. In the failed runs the Critic accepted
the analysis, but the Reasoning Agent itself stated 0.45, under the 0.5 threshold. The ablation
shows the same 0.45 without any Critic, so the Critic is not the cause. I did not tune the prompt
again to recover it; see the first limitation below.

## Bugs and corrections the evaluation produced

1. **Split hypotheses caused abstentions** (`main`). The Reasoning Agent wrote one origin as two
   near-identical hypotheses, the near-tie rule fired, and two runs abstained. Fixed in the
   Reasoning and Critic prompts; `v2` is the re-run.
2. **A scorer false negative** (`main`). A single-agent run named the external exchange by hostname
   and was marked wrong. The hostname was added as an accepted answer and the run re-scored. Before
   that the single agent stood at 35/36.
3. **A run cut short could still claim a root cause** (weaker-model run; fixed after the final
   round). The outcome rule looked only at the confidence cap, so a team run that ended while the
   Critic was still asking for evidence, or before any review, could say "identified". Such a run
   is now "inconclusive". Replayed on the saved traces: all six wrong-but-confident team runs of
   the weaker-model round become abstentions, at the cost of five correct ones there, two in
   `stress`, one each in `main` and `v2`, and none in `v3` or `v4`. A Critic outage and the
   no-Critic ablation still answer, flagged and capped at 0.6.
4. **The random-fault mode could not stress anything** (this round). Random faults always succeeded
   on the first retry, and every trial used the same fault pattern. Added faults that persist
   across retries and a per-trial seed.
5. **A failed run was scored correct on the undeterminable incident** (third review). Both
   single-agent INC-007 runs of the weaker-model round ended on a provider timeout with no
   hypothesis, and "not identified" counted as correct. The scorer now requires a hypothesis.
   Re-scored: that round's single agent drops from 25% to 17% (4/24). No other round changes.
6. **Re-using a results folder with other flags relabelled old runs** (third review). Saved runs
   are re-scored, not re-run, so `--chaos` or a different model on an existing `--name` wrote a
   table headed with settings the runs never had. The harness now records the model and fault
   rates per folder and refuses a mismatch.
7. **Hypotheses could overwrite each other** (third review). When the Reasoning Agent reused an
   id inside one answer, the later hypothesis replaced the earlier one. It now gets a fresh id
   and a warning.
8. **Agents ask for things that do not exist.** With no faults injected, the team still gets 3.2
   "not found" errors per incident (the single agent 0.8) from querying services or metrics that are
   not in the topology. These are wasted calls, not failures of the tools. Not fixed.

## What the evaluation does not tell you

- **The prompts were tuned on these 12 incidents.** There is no held-out set. The `v4` drop on
  INC-008 is what an untuned result looks like; tuning it away would make the number better and the
  evidence worse.
- **Whether the report helps an engineer.** Nothing scores the summary's wording or whether the
  recommended actions are sensible. A report can score "correct" with a poor write-up.
- **Whether quotes were interpreted correctly.** A verified finding proves the quoted text is in
  the tool output, not that the sentence around it reads it correctly. A quote of only the tool
  name or call id also verifies (52 of 11,524 verified quotes in earlier rounds).
- **Small differences.** 36 runs per system gives intervals about 20 points wide. One or two runs
  move a headline by 3 to 6 points.
- **Real incidents.** The data is synthetic and written by the author of the system. A strong model
  solves almost all of it alone, so the set cannot show where a team should start to pay off:
  larger topologies and evidence that does not fit one context.
- **Latency in absolute terms.** One provider, one evening, four investigations at once. Three team
  runs in `v4` and four in `stress` overran the 420 s limit (longest 544 s), because the limit is
  checked between model calls.
- **Other models.** One model. The weaker-model run in an earlier round was dominated by provider
  timeouts and is not conclusive.
- **The tightened outcome rule in live runs.** It is covered by tests and by replay on saved
  traces, not by a fresh evaluation round.

## Measures considered and not used

| Measure | Why not |
|---|---|
| A model judge of the report | The answer key already decides right and wrong; a judge would add a second, softer verdict on the same question. It would be the right tool for write-up quality, which is unmeasured. |
| Text similarity to a reference narrative | Two correct diagnoses share few words. Accuracy is a structured match on service and category. |
| "Correct cause in the top 3" as the headline | Reported, but an engineer acts on the top answer and the outcome label. |
| Stated confidence as a quality score | It is the system's own claim. It is checked against correctness, not counted as a result. |
| Pass or fail per incident across trials | Hides the run-to-run variation that the per-run counts show. |

## Reproduce

```bash
python eval/run_eval.py --name v4 --systems multi,single,nocritic --trials 3
python eval/run_eval.py --name stress --systems multi,single --trials 2 --chaos 0.3 --chaos-hard 0.1
```

A run whose report already exists is re-scored, not re-run, so the commands above regenerate the
tables from the committed traces at no cost and without an API key. Each results folder records
the model and fault rates it was made with (`config.json`); the harness refuses to re-use a folder
with different ones. Delete a results folder to run it again.
